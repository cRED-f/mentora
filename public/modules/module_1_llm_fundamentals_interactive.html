LESSON 01 / 10

Foundation models, LLMs & generative AI

Define the boundaries of each term, then connect pretraining to real deployment decisions.

A Interviewer questions

  1. A pretrained model can write text and classify reviews. Which labels—foundation model, LLM, generative model—apply, and why?
  2. Does every foundation model use a Transformer? Does every LLM generate useful text?
  3. Why does a single broadly pretrained model support tasks absent as explicit labels in its training set?
  4. What changes when you replace a task-specific classifier with a prompt-driven foundation model?

B Deep technical explanation

Three overlapping, nonidentical ideas. A foundation model is broadly pretrained and adaptable across downstream tasks; its modality may be text, image, audio, or combinations. An LLM models sequences of linguistic tokens (frequently code and other serialized data as well). Generative AI describes systems that produce new content by learning a distribution or a conditional mapping; it includes image diffusion and audio generation. Many decoder-only LLMs belong to all three groups, but a contrastively trained vision-language foundation model may not be a text generator.

Pretraining: θ* = argminθ 𝔼x∼D[ℒ(x; θ)] → reusable representation and/or conditional distribution

Pretraining usually optimizes a proxy objective, not a direct “truth” objective. That distinction explains why fluent generation, calibrated confidence, verifiable factuality, and tool-use safety require separate work. Pretraining does not install a database of guaranteed correct statements; knowledge is distributed imperfectly across learned parameters.

Traditional task-specific ML

Collect task-labeled examples → engineer or learn features → train model → fixed output contract. Easy to constrain, but new tasks often need new training.

Foundation-model engineering

Select pretrained model → define task with prompts/context/tools → evaluate → optionally adapt weights → deploy with guardrails and monitoring. Faster task reuse, new failure surface.

Changing the interface from per-task weights to natural-language instructions is profound, but the resulting model is stochastic and may follow unwanted instructions from retrieved or user-controlled text. Production systems therefore separate model capability, grounding, authorization, and evaluation.

C Interview-ready spoken answer

A foundation model is a broadly pretrained reusable model; an LLM is a language-centered instance, and generative AI is the broader class of content-creating systems. Broad pretraining transfers representations across tasks, so engineering shifts from fitting a model per task toward context design, adaptation, retrieval, evaluation, and controlled deployment. Reuse is powerful, but factuality and security are not guaranteed by pretraining.

D Follow-up pressure test

  1. A vision encoder produces vectors. Is it a foundation model even if it never generates a sentence? Explain adaptation.
  2. Why is zero-shot classification not proof that a pretrained model contains reliable ground truth?
  3. What becomes easier—and harder—to test when one shared model backs ten business workflows?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: A company wants support classification, summarization, and reply drafting. A team suggests one large LLM for every request.

Plan: Define per-task correctness and failure cost; measure simple baselines (rules or small classifiers), LLM quality, p95 latency, data-handling risk, and per-request cost on the same held-out set. Route deterministic classification to a cheaper verified path if it meets targets, while drafting can use a generative model with retrieval and review.

Acceptance: Maintain an explicit gold set by workflow; compare task-specific error rates and cost at matched quality, report confidence intervals, and test refusal, PII, and prompt-injection cases before traffic rollout. Do not invent “one-model” savings without a measured baseline.

F Interview takeaways

  • Foundation ≠ language ≠ generative; know the overlaps.
  • A training objective is a proxy, not a factuality guarantee.
  • Evaluate tasks separately even when a common model serves all of them.
LESSON 02 / 10

How foundation models changed AI engineering

Move from model-centric projects to compound systems and measurable operational contracts.

A Interviewer questions

  1. Describe how the development lifecycle differs between a 2018 custom NLP classifier and a modern LLM feature.
  2. Where do prompts end and software-enforced policy begin?
  3. When does fine-tuning beat retrieval or deterministic software?
  4. How do you establish return on model complexity rather than rely on vendor benchmark claims?

B Deep technical explanation

The major shift is separation of learned general capability from application-specific state. Pretraining is an expensive upstream activity; application teams compose a pretrained model with retrieval, business logic, APIs, schemas, auth, and evaluators downstream. This is an engineering abstraction, not a claim that no custom training is needed.

  1. Specify the task: Inputs, output schema, who can invoke it, cost of false positives/negatives, failure policy.
  2. Establish baselines: Rules, search, small models, hosted LLM, and human workflow where relevant.
  3. Supply missing knowledge: Retrieval for mutable facts; tools for live or exact calculations; fine-tuning for recurring behavior/style/domain patterns.
  4. Build a harness: Validation, permission checks, rate limiting, retries, caching, deterministic operations, logging, and human approval for irreversible actions.
  5. Evaluate and roll out: Golden tests, adversarial and multilingual slices, calibration where meaningful, shadow testing, canaries, rollback.

Why this design works: A language model is good at interpreting ambiguous instructions and synthesizing text, while conventional software is superior at enforcing invariants, transactions, and permissions. A good architecture allocates responsibility accordingly.

NeedFirst-choice mechanismTypical failure
Fresh private factsRetrieval plus permissionsStale or unauthorized context
Stable response formatSchema-constrained decoding + validatorSemantically wrong valid JSON
Exact arithmeticVerified tool / deterministic codeBad tool arguments
Consistent specialized behaviorPrompt baseline then fine-tune if supported by evalsOverfit and forgetting

C Interview-ready spoken answer

Foundation models turn many ML applications into systems engineering problems: we reuse learned capabilities and invest in grounding, reliable APIs, data contracts, evaluation, and safety boundaries. I use the simplest baseline that meets the requirement, then add RAG, fine-tuning, or agents only if evaluation identifies a measurable gap.

D Follow-up pressure test

  1. Why not fine-tune whenever output quality is poor?
  2. What metric tells you retrieval is the bottleneck rather than generation?
  3. What must be enforced outside the prompt even if the model looks highly compliant?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: A support assistant answers with outdated prices and occasionally reveals another tenant’s policy.

Diagnose: Split answer accuracy into retrieval currency, retrieval authorization, grounding, and model generation. Trace document IDs, version timestamps, effective user identity, and source attribution per response.

Fix: Enforce tenant/ACL filters at retrieval and again at data access; add version-aware indexing and cited responses. Do not rely on “do not reveal private data” prompt text as the authorization boundary.

Validate: Cross-tenant access tests must return zero unauthorized documents; measure freshness delay and answer faithfulness on a timestamped golden dataset. Roll out with a kill switch.

F Interview takeaways

  • LLM application quality is a pipeline property, not just a model property.
  • Prompt instructions are not security boundaries.
  • Choose RAG for mutable knowledge, tools for exact state, fine-tuning for repeated behavior.
LESSON 03 / 10

How LLMs learn patterns and generate language

Follow the path from training examples and gradients to a probabilistic output at inference.

A Interviewer questions

  1. What exactly is updated during next-token pretraining?
  2. If an LLM is trained on a billion sentences, does it retrieve the nearest sentence at runtime?
  3. Why can cross-entropy improve while factuality on a specialized task remains poor?
  4. Where does sampling enter relative to the Transformer forward pass?

B Deep technical explanation

Training path. (1) Text is tokenized into integer IDs; (2) chunks are arranged as training sequences; (3) embeddings, positional information, attention, and MLP layers compute hidden states; (4) a language-model head produces a logit for each vocabulary token at each position; (5) the target is the actual next token in the data; (6) cross-entropy measures prediction error; (7) backpropagation computes gradients and an optimizer updates parameters. The same weights are shared across positions, and attention provides contextual interactions.

L(θ) = −(1/N) Σt=1…N log pθ(xt | x<t)

For the true token y, cross-entropy equals −log p(y); a probability of 0.8 yields about 0.223 nats, while 0.1 yields about 2.303 nats. Gradients push the distribution toward observed continuation tokens, not toward an external truth oracle. Sequence correlations let the network internalize syntax, code patterns, statistical facts, and some procedures.

Inference path. Freeze weights; tokenize prompt; run the model to get logits for the next token; transform logits into a probability distribution; select a token via greedy or stochastic decoding; append token; repeat until a stopping condition. Serving frameworks usually cache earlier K/V projections so later steps do not recompute the entire prefix. The cache stores contextual intermediate activations, not a second copy of model weights.

Important trap: Next-token training does not mean the model literally predicts whole words, stores its entire dataset verbatim, or searches the internet automatically. Text generation is conditionally autoregressive; the deployment may add external retrieval or tools.

C Interview-ready spoken answer

An LLM is trained to assign high probability to the next token conditioned on earlier tokens. It runs the training sequence through a Transformer, computes vocabulary logits, applies cross-entropy against observed next tokens, and updates weights through backpropagation. At inference the weights stay fixed; the system selects one token from the predicted distribution, appends it, and repeats. Fluent prediction is not itself a correctness guarantee.

D Follow-up pressure test

  1. Derive the loss if the correct token has probability 0.02 rather than 0.2.
  2. Which parts execute once during prompt processing, and which execute repeatedly during output generation?
  3. If two generated continuations have equal semantics but different wording, what does token-level loss measure?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: A domain assistant speaks fluently but produces unsupported contract clauses.

Hypotheses: Missing evidence, misleading retrieved passages, sampling variance, or model prior overriding context. Instrument document coverage, cited spans, model/prompt version, decoding parameters, and claim-to-source entailment. Test retrieval oracle passages to isolate retrieval versus generation.

Options: Tighten retrieval, enforce evidence-linked claims and abstention, evaluate a specialized model, or require human review. Do not assume lower temperature makes fabricated claims true.

Acceptance: On a held-out set with unanswerable cases, report factual-support rate, false-answer rate, and abstention recall; compare against pre-change baselines.

F Interview takeaways

  • Cross-entropy trains probabilities, not truth directly.
  • Training updates θ; inference holds θ fixed and repeatedly selects tokens.
  • Quality diagnosis separates evidence failure from generation failure.
LESSON 04 / 10

Autoregressive models & next-token prediction

Master conditional factorization, teacher forcing, decoding dependence, and latency consequences.

A Interviewer questions

  1. Write the probability of a sequence as a product of conditional probabilities.
  2. What is teacher forcing, and why can training run token positions in parallel while inference is sequential?
  3. Does causal attention mean input tokens are processed serially during prefill?
  4. Where does exposure bias arise and when does it matter?

B Deep technical explanation

An autoregressive (AR) model factorizes a joint sequence distribution using the chain rule. For tokens x₁...xₜ, it uses the left prefix to predict each next token, normally with a causal mask preventing positions from reading future tokens.

p(x₁, …, xₜ) = ∏t=1…T p(xt | x1, …, xt−1)

Teacher forcing: During training, feed the entire ground-truth sequence, shifted by one target position. Although each position is only allowed to depend on its prefix, causal attention allows the GPU to evaluate predictions for many token positions in a single parallel forward pass. During generation, the next token is unknown, so it must be generated before the following token can be conditioned on it. This creates a serial dependency even when an individual step is GPU-parallel.

Cost: For full dense attention, attention score work during prefill has O(T²·d) flavor, while single-token decode attends across its current cached context, O(T·d) attention work per step (details depend on head shape). Long generation also carries a KV-cache memory burden approximately proportional to layers × context × KV-heads × head-dim × bytes. This distinction matters when sizing throughput.

Failure: Training mostly sees real prefixes, while decoding consumes its own sampled outputs; distribution shift can amplify early mistakes. A hallucinated premise in one step can influence later steps. Mitigations depend on task: constrained decoding, external verification, robust training, and evidence-grounding.

C Interview-ready spoken answer

Autoregressive models factor sequence probability into next-token conditionals. During training, teacher forcing supplies the correct prefix so causal Transformer positions can be evaluated in parallel. During inference each newly sampled token becomes part of the prefix, so output steps are sequential; a KV cache avoids unnecessary recomputation of earlier attention states.

D Follow-up pressure test

  1. Why is an autoregressive Transformer still massively parallel during prompt prefill?
  2. What becomes slower as the sequence grows, even with a KV cache?
  3. What is the difference between a causal attention dependency and an RNN’s hidden-state recurrence?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: Interactive code completion misses the latency target even though GPU utilization appears moderate.

Instrument: Separate time to first token, queue delay, prefill time, tokens/s in decode, generation length, and KV-cache usage. A 2,000-token answer may simply be dominated by serial output generation.

Fix options: Cap unnecessary output length, use an adequately sized faster model, dynamic batching, appropriate speculative decoding, or workload-specific prefix reuse. Validate task completion at matched output budgets: aggressively shortening output can reduce utility.

Acceptance: Report p50/p95 TTFT and per-token latency, task success, throughput, and cost per completed task under a documented concurrency distribution.

F Interview takeaways

  • Chain rule gives the exact factorization; model architecture approximates each conditional.
  • Parallel training positions ≠ parallel autoregressive output tokens.
  • Measure TTFT and decode latency separately.
LESSON 05 / 10

Autoregressive vs. masked language modeling

Contrast objectives, context visibility, output behavior, and suitable tasks.

A Interviewer questions

  1. Why can BERT inspect both left and right context but a causal next-token decoder cannot?
  2. Could a masked encoder generate a paragraph just by sampling next tokens? What would be missing?
  3. Explain masked token prediction mathematically and its training/inference mismatch.
  4. Which objective would you choose for intent classification versus free-form answer generation?

B Deep technical explanation

Autoregressive objective: predict the next token using only earlier tokens, maximizing p(xₜ | x₍<t₎). Attention masking enforces causality. This naturally supports left-to-right open-ended decoding and streaming.

Masked language modeling (MLM): corrupt selected positions with a mask or replacement, then predict the original token from both left and right observed context, as in BERT-style encoder pretraining. A common illustrative loss is:

LMLM = −Σi∈M log pθ(xi | corrupted(x), i)

The MLM loss covers masked positions M; it is not generally a normalized joint probability of all tokens, and filling multiple masks independently may miss dependencies between them. Importantly, SentencePiece is tokenization, not a modeling objective; do not confuse the input encoder with a language-model training task.

DimensionAutoregressive decoderMasked encoder
VisibilityLeft prefix via causal attentionLeft and right observed tokens
Primary targetNext token at each positionReconstruct selected masked tokens
Natural fitFree-form generation, code completionClassification, token tagging, contextual encoding
Inference limitationSerial generation stepsNo native left-to-right generator head/objective

Encoder-decoder denoising models, such as T5-style systems, can instead combine rich input understanding with autoregressive output generation. Bidirectional attention does not automatically mean better quality for every task: it changes what information is visible and what objective the model learned.

C Interview-ready spoken answer

Autoregressive modeling learns the distribution of the next token from earlier tokens and aligns directly with streaming generation. Masked language modeling hides selected tokens and uses both surrounding sides to reconstruct them, which is useful for contextual representations and understanding tasks. A BERT-style masked encoder is not automatically a general-purpose paragraph generator; architecture and training objective must align with the desired output.

D Follow-up pressure test

  1. Can you compute a joint sequence likelihood from independent MLM predictions in the same way as AR factorization?
  2. Why doesn't bidirectional attention inherently leak future tokens for a classification task?
  3. What architectural change lets an encoder represent source text while another network produces a sequence?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: A financial institution needs document category prediction and a human-readable justification.

Design: Benchmark a small bidirectional encoder for categories and a generative decoder for justification, versus one generative model for both. Compare accuracy, calibration, latency, explanation faithfulness, and total operational complexity.

Guardrail: Generate justifications from cited evidence rather than assuming a classifier’s feature attribution is a legally sufficient explanation.

Acceptance: Pre-register class-specific F1, critical-class recall, p95 latency, and unsupported-claim rate; prefer simpler architecture if it meets thresholds.

F Interview takeaways

  • Attention visibility follows the training objective and task.
  • MLM reconstruction is not left-to-right joint likelihood modeling.
  • Do not choose architecture by popularity alone; match objective to output contract.
LESSON 06 / 10

Encoder-only, decoder-only & encoder-decoder Transformers

Choose architecture from data flow, attention masks, and output characteristics—not model branding.

A Interviewer questions

  1. Draw data flow and attention patterns for all three Transformer families.
  2. What exactly is cross-attention in an encoder-decoder model?
  3. Why can encoder-decoder translation outperform a naive decoder-only setup on some constraints?
  4. When do you need contextual embeddings instead of generation?

B Deep technical explanation

Encoder-only: Source tokens attend bidirectionally to other source tokens (subject to padding and other task masks). Layers build contextual representations. Classification often pools a designated output or uses sequence representations; token tagging uses per-token states. Typical examples include BERT-style encoders.

Decoder-only: A single causal stack maps prompt plus generated prefix to next-token logits. The prompt and output occupy one token stream. This unification simplifies prompting, in-context learning, chat, and streaming, but output tokens are produced sequentially and must be constrained for strict formats.

Encoder-decoder: An encoder processes the source; a causal decoder attends to its own earlier target tokens and attends across the entire encoded source via cross-attention: Q comes from decoder states, while K,V come from encoder states. This is naturally suited to source-conditioned transformations such as translation and summarization, including objectives trained for those workflows.

Attention(Q,K,V) = softmax(QKᵀ / √dk + mask) V

Practical design questions include input-output asymmetry, sequence lengths, deployment ecosystem, and evaluation. Decoder-only models can also excel at translation or classification; the architecture is a strong inductive bias, not an absolute capability boundary.

Complexity nuance: A self-attention layer over length n typically constructs O(n²) token-pair scores in the straightforward implementation; FlashAttention reduces memory traffic and avoids materializing the full scores, but does not generally make dense exact attention asymptotically linear in arithmetic cost.

C Interview-ready spoken answer

Encoder-only Transformers produce bidirectionally contextualized representations and are strong candidates for understanding tasks. Decoder-only Transformers use causal self-attention and naturally generate text one token at a time. Encoder-decoder models encode the source and generate with a causal decoder whose cross-attention queries that source. I choose based on the output contract, latency, task training, and measured quality—not a rigid architecture slogan.

D Follow-up pressure test

  1. Name the source of Q, K, and V in decoder cross-attention.
  2. What happens to caching in an encoder-decoder inference server?
  3. Why can a decoder-only model still perform classification effectively?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: A document service performs tagging, translation, and extractive fact lookup.

Option A: One decoder-only model with tailored prompts: fewer providers, flexible tasks, potentially higher per-request cost.

Option B: Encoder for tagging, translation-optimized encoder-decoder, retrieval plus verified extraction: more operational components, potentially stronger specialization.

Validation: Compare exact-match or F1 for extraction, translation adequacy on human-reviewed data, p95 latency, throughput, and cost. Include malformed input, code-switching, and large documents in test slices.

F Interview takeaways

  • Encoder = source representation; decoder = causal generation; encoder-decoder = source-conditioned generation.
  • Cross-attention uses decoder Q and encoder K/V.
  • Architecture is a bias, not an impossibility theorem.
LESSON 07 / 10

RNNs vs. Transformers

Reason from computation graphs to scaling, memory, and long-range dependency behavior.

A Interviewer questions

  1. Why can a Transformer process training positions in parallel but a vanilla RNN cannot?
  2. Is attention always cheaper than recurrence for long sequences?
  3. What does the longest sequential dependency path imply for optimization?
  4. Which architecture might win for tiny streaming devices or extremely long sequences?

B Deep technical explanation

RNN computation: an RNN updates a hidden state in sequence: hₜ = f(Wₕhₜ₋₁ + Wₓxₜ). This creates a length-T sequential path through time, inhibiting training parallelism across positions. Vanishing/exploding gradients complicate long-range dependencies; gated LSTM/GRU variants improve stability but retain recurrence.

Transformer computation: self-attention allows position i to interact directly with another accessible position j in a layer. During training all positions can be projected and processed in large matrix operations. Causal masks preserve valid autoregressive information flow without requiring an RNN-style sequential hidden-state update during prefill.

PropertyRNN / gated recurrenceDense self-attention Transformer
Across-position trainingSequential recurrent dependencyHighly parallel within a layer
Long-range interactionThrough hidden-state chainDirect token-pair interaction
Long-context computeOften O(T·d²) recurrent computeO(T²·d + T·d²) typical per layer
Working state at inferenceFixed-size hidden state for a standard RNNGrowing KV cache for causal attention

These complexities are simplified: embedding size, head dimensions, layers, variants, kernel efficiency, and hardware control practical crossover points. New state-space or hybrid architectures change the comparison. It is incorrect to say Transformers always beat every recurrent approach at any context length.

C Interview-ready spoken answer

An RNN compresses its history into a recurrent hidden state, which creates a serial dependency across time. A Transformer uses attention to let each position directly mix information from other permitted positions, so training can parallelize across the sequence and optimize long-range interactions more effectively. The trade-off is quadratic dense attention computation and growing KV state; recurrence or hybrid methods may win in tight-memory or streaming settings.

D Follow-up pressure test

  1. Why does a causal Transformer not violate temporal ordering during training?
  2. How does KV-cache growth differ from recurrent state size?
  3. When would a state-space model deserve benchmarking rather than assuming attention is best?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: A wearable needs streaming anomaly detection on long sensor traces with strict memory limits.

Plan: Benchmark a gated RNN, lightweight attention, and possibly a modern state-space model on the same event-labeled stream. Measure detection recall, delay to detect, battery/energy, on-device peak memory, and robustness under sensor dropout.

Choice: If far-back exact interactions matter, attention may help; if constant-memory streaming is paramount, recurrence may dominate. Validate against the real device, not only desktop GPU speed.

F Interview takeaways

  • RNN sequence dependence harms prefill parallelism.
  • Attention has direct interactions but costly long-context scaling.
  • Hardware and task shape, not fashion, determine the winner.
LESSON 08 / 10

Inside ChatGPT: request-to-response lifecycle

Separate what is general to LLM-backed chat systems from product-specific internals that are not public.

A Interviewer questions

  1. Trace a chat request from client input through token generation and streaming UI.
  2. Which components are inside the model, and which belong to the serving application?
  3. Where might tools or retrieval enter without changing the base model weights?
  4. Explain TTFT, KV reuse, stop conditions, and failure handling in one coherent flow.

B Deep technical explanation

Reference architecture, not a claim about ChatGPT’s private implementation. (1) Client submits text and conversation context; (2) server authenticates, authorizes, and applies rate limits; (3) an orchestrator forms model messages and may select a model; (4) a tokenizer converts serialized context into token IDs; (5) prompt processing (prefill) builds hidden states and usually KV cache; (6) final prompt position yields next-token logits; (7) decoding samples/selects output tokens iteratively; (8) the application may invoke tools and re-enter generation; (9) output is streamed, validated/filtered where configured, persisted, and rendered.

TTFT ≈ queue + input handling + prefill + first decode + network/stream overhead

API providers may implement tool calls as a structured output event followed by a server-side tool execution and a subsequent model turn. A model has no inherent permission to browse a user's filesystem, call a database, or guarantee a transaction; the surrounding application grants and enforces those capabilities.

Failure boundaries include truncation, context overflow, malformed tool arguments, authorization errors, timeouts, partial stream disconnects, retries that duplicate side effects, and stop condition bugs. Production handling should use request IDs, bounded deadlines, idempotency keys for writes, and clear error statuses.

What we cannot infer: The exact ChatGPT model routing, internal prompts, kernel scheduling, caching, or proprietary safety implementation for any specific request. These vary and are not fully observable from the client. Explain the standard architecture without presenting product-specific speculation as fact.

C Interview-ready spoken answer

A typical ChatGPT-like request is authenticated, assembled into model context, tokenized, prefetched through a Transformer, and decoded autoregressively. The service streams tokens and may orchestrate retrieval or tool calls between model turns. The application—not the model weights—handles permissions, persistence, deadlines, and tool side effects. I would distinguish this standard design from proprietary implementation details I cannot verify.

D Follow-up pressure test

  1. What exactly causes TTFT to rise when a prompt grows?
  2. If the network disconnects after a payment tool call, how do you prevent duplicate charges?
  3. Does enabling streaming reduce total compute or only perceived responsiveness?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: Users see responses stop after a tool invocation; some retries duplicate actions.

Diagnose: Trace client request ID → orchestration turn → tool call ID → tool outcome → resume step; record disconnects, deadlines, and whether tool calls were acknowledged. Separate interrupted streams from model completion failures.

Fix: Persist workflow state; add idempotency keys and a deduplication ledger for side effects; handle reconnects with safe resume and clear UX. Retrying a full conversation blindly is unsafe for write operations.

Acceptance: Exactly-once business effect under replay tests (achieved through idempotent processing), no unauthorized tool calls, and monitored completion rate and p95 end-to-end latency.

F Interview takeaways

  • Model forward pass is only one stage of a chat product.
  • TTFT includes queueing and network as well as inference.
  • Never assert private ChatGPT internals as verified facts.
LESSON 09 / 10

Open-source, open-weight & closed-source deployment trade-offs

Reason about licenses, risk, TCO, customization, and hosting reality.

A Interviewer questions

  1. Why is downloadable model weight access not synonymous with open-source?
  2. How do you calculate when self-hosting beats pay-per-token APIs?
  3. Which privacy claims require contractual and operational verification?
  4. What does a migration plan look like if a model provider or license changes?

B Deep technical explanation

Terminology: An open-source model has a license and accompanying accessible materials that satisfy relevant open-source criteria; in AI, the scope may include code, weights, and training details, and definitions differ. An open-weight model provides downloadable parameters, but may restrict commercial use, redistribute restrictions, or omit training data/code. A closed model typically gives hosted API access without weights. Treat each license and provider policy as its own contract.

Model controlLimited to exposed API settingsMore control over weights, quantization, tuning

Failure modesRate limits, API outages, upstream changesGPU failure, OOM, patching, capacity issues
Illustrative monthly TCO ≈ GPU hours × $/GPU-hour + ops + storage + network + observability

Compare that against API input/output-token charges on your actual request lengths and cache hit rates. Benchmark under peak concurrency and at matched quality; price per token alone obscures batch throughput and idle GPU hours. Regulatory or privacy suitability requires legal/security review, not a marketing label.

C Interview-ready spoken answer

I distinguish open-weight availability from an actual open-source license, then compare hosted and self-hosted models across measured quality, latency, volume, data residency, licensing, and operations. APIs reduce time to market and capacity burden; self-hosting increases control but introduces GPU utilization and reliability risks. I use workload-specific TCO and rollback plans instead of assuming either is always cheaper or safer.

D Follow-up pressure test

  1. At what sustained utilization might fixed GPU capacity overtake variable API cost?
  2. How would you test vendor portability beyond implementing a common API signature?
  3. Does local inference alone prove that prompts cannot leak? What about logs, telemetry, and dependencies?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: An enterprise wants to move confidential summarization from a hosted provider to local inference.

Plan: Inventory data sensitivity, retention requirements, licenses, eval suite, prompt lengths, and traffic. Evaluate a shortlist of open-weight models with quantization variants on identical test documents.

Risks: Quantization-induced quality loss, underutilized GPUs, missing hardware redundancy, model provenance, logging leaks. Introduce traffic shadowing and a reversible switch.

Acceptance: Meet agreed factuality and throughput thresholds, prove data-flow restrictions via audit and network tests, and show 30-day modeled TCO with sensitivity to utilization.

F Interview takeaways

  • Open weights do not automatically imply open source or unrestricted licensing.
  • Costs must include utilization, engineering, and operational risk.
  • Provider swap is a behavior/evaluation project, not just a URL edit.
LESSON 10 / 10

SLMs, LLMs & Large Reasoning Models (LRMs)

Compare parameter scale, inference-time computation, latency, and practical model routing.

A Interviewer questions

  1. Is an LRM always larger in parameter count than a non-reasoning LLM?
  2. How can inference-time compute improve complex task performance without retraining?
  3. When should an SLM outperform a stronger LLM on product utility?
  4. What would you evaluate before turning on a longer reasoning budget?

B Deep technical explanation

SLM: A small language model is usually chosen for lower memory footprint, faster/local inference, predictable cost, or a narrow specialty. There is no universal parameter-count cutoff. LLM: A broad term for higher-capacity language models, also without a fixed public numerical boundary. LRM: Usually refers to language models designed or optimized for more capable multi-step reasoning, often through specialized training and/or inference-time computation; an LRM need not be the largest model by parameter count.

Inference-time compute: Hard questions can benefit from generating intermediate reasoning tokens, searching over candidate solutions, using verifiers, or invoking tools. This spends extra compute at inference rather than relying only on a single immediate answer. Gains are task-dependent; longer reasoning can also introduce errors, excessive latency, and cost. It does not guarantee truth or faithful explanations of internal computations.

Expected task utility = quality benefit − λ·latency − μ·cost − ν·risk (illustrative objective)

Routing: Use a deterministic fast path for trivial extraction, a smaller validated model for bounded tasks, and a stronger reasoning-capable model for harder multi-step inputs. A classifier for complexity is itself imperfect: route conservatively when mistakes are expensive and keep a fallback or escalation path.

Request shapeCandidate pathWhat to measure
Tag a short support ticketRule / compact encoder / SLMF1, latency, price
Draft a nuanced policy explanationGeneral-purpose LLM + retrievalFaithfulness, review time
Solve multi-step symbolic reasoningReasoning-capable LLM + verifierVerified success, budget, tail latency

Model names and labels change faster than these design principles. Do not assume “reasoning” is a guaranteed separate architecture; often the underlying model remains Transformer-based autoregressive generation, augmented by training and inference-time strategy.

C Interview-ready spoken answer

SLMs emphasize cost, footprint, and specialization; LLMs offer broader capacity; LRMs emphasize stronger multi-step problem solving through training and inference-time computation. These categories overlap rather than form three clean size bins. I route tasks using measured quality under latency and cost constraints, and reserve expensive reasoning for requests whose verified outcomes justify it.

D Follow-up pressure test

  1. Why might a reasoning model be worse for a deterministic schema extraction service?
  2. How would you validate a complexity router without circularly using the same model as judge?
  3. Does showing intermediate text prove the model reasoned correctly? How would you verify the final result?

A strong response should justify the mechanism, name limits, offer alternatives, and explain how to measure a claim.

E Production scenario

Scenario: A research assistant costs too much because every simple query triggers long-form reasoning.

Diagnose: Stratify traffic by task complexity, output length, model selection, verified success, p95 latency, and average spend. Construct independent task labels and measure router false negatives on hard/high-risk cases.

Fix: Establish conservative routing policies and verify cheap-path confidence; escalate uncertain cases to a more capable model. For answerable questions with exact evidence, retrieval plus concise generation may dominate long inference-time deliberation.

Acceptance: No unacceptable degradation on high-risk slices; document matched-quality cost and latency with confidence intervals, plus fallback frequency and routing error rate.

F Interview takeaways

  • SLM, LLM, and LRM labels overlap.
  • More reasoning tokens do not imply correct reasoning.
  • Optimize verified end-to-end task utility, not parameter count or benchmark score alone.
