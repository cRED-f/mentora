LESSON 01 / 14
From hidden states to vocabulary logits
Follow the exact final projection, tensor dimensions, weight tying, and per-token score semantics.
A Interviewer questions
  1. Given [B,N,D] hidden states and vocabulary V, derive the output tensor and parameter count with/without tied embeddings.
  2. Why are logits not probabilities, and why does the last row drive next-token inference?
  3. What happens to memory and bandwidth when V is 200k instead of 32k?
  4. Can a positive logit be less likely than a negative logit? Explain.
B Deep technical explanation
Trace the decoder to the next token. After L causal Transformer blocks, the final position contains a context-dependent hidden vector hₜ ∈ ℝᴰ. The output projection W_out ∈ ℝᴰˣⱽ forms unnormalized scores zₜ = hₜ W_out + b, so a batch of full-sequence outputs has shape [B,N,V]. In some models a final RMSNorm or LayerNorm precedes the projection. At generation time, only the last unconsumed token-position logits are needed for deciding the next token; training typically scores many positions in parallel.


H ∈ ℝ[B,N,D], W_out ∈ ℝ[D,V]   →   Z = H W_out + b ∈ ℝ[B,N,V]


  1. Obtain hidden states: token embeddings, positions, causal attention and MLPs produce H.
  2. Normalize and project: compute the matrix product to V candidate-token scores per position.
  3. Apply rules: optional vocabulary constraints, bad-token masks, and repetition/logit biases transform logits, depending on implementation.
  4. Compute probabilities: apply temperature and stable softmax to finite logits.
  5. Select a token: greedy, beam search, or stochastic sampling.
  6. Advance: append the token, update per-layer KV cache, and repeat until EOS/stop/budget.


Weight tying: input embedding E ∈ ℝ[V,D]; tying uses W_out=Eᵀ and saves approximately VD independent parameters. Untied output adds another VD (biases excluded). With V=128,000,D=4096, one untied matrix is about 524.3 million parameters, or 1 GiB at 2 bytes each; the final output activation for B=1 and one step is another V scores, and a full [B,N,V] logit tensor can be huge if materialized unnecessarily.


Complexity: full sequence output projection is O(BNDV) operations, incremental projection O(BDV). The large vocabulary matrix may influence decoding memory bandwidth and top-k selection time. Sharded vocabularies must account for globally correct normalization/selection. Traps: reading logits as confidence scores, accidentally projecting a padding position, using wrong last-token indices in a padded batch, confusing output tokens with Unicode words, and assuming weight-tying is mandatory. A logit difference—not its absolute sign—drives the probability ratio.
C Interview-ready spoken answer
Final hidden states have width D, but the LM head projects each into V vocabulary logits. These are relative scores, not probabilities; at inference I select from the correct final position, apply decoding constraints and softmax, choose a token, then advance the autoregressive state. For a large vocabulary I budget the D×V projection and avoid materializing all [B,N,V] logits when only the final row is required. Weight tying can reuse the input embedding matrix.
D Follow-up pressure test
  1. If z₁=−1 and z₂=−2, which is likelier? Strong answer: token 1; only relative logits matter.
  2. What if prompts are left-padded? Strong answer: ensure final valid position and mask/position handling rather than naive tensor slicing across implementations.
  3. How much memory does [B,N,V] cost? Strong answer: B×N×V×dtype bytes, distinct from model parameters.
Mechanism → trade-off → concrete verification. Do not hand-wave.
E Production scenario
Incident: An inference API returns degraded answers for variable-length batched requests. Hypotheses: selecting logits at a padding token, incorrect sequence-position indexing, or wrong EOS ID. Instrument: input lengths, attention/padding masks, selected indices, token IDs, vocabulary/model checkpoint version, and reference-logit parity. Mitigation: construct a batch with unequal lengths and compare each item's batched logits to independently run unpadded logits; patch padding/position logic, deploy with regression fixtures. Acceptance: output-token distributions match the canonical implementation within precision tolerance; no batch-dependent text drift.
F Interview takeaways
  • LM head [D,V] produces unnormalized logits; signs are not probabilities.
  • Tie output weight to input embeddings only when architecture permits.
  • Last non-padding position determines the next token; projection and full-sequence logit buffers have costs.


LESSON 02 / 14
Softmax and token probability distributions
Derive stable softmax, probability ratios, entropy, log probabilities, and numerical edge cases.
A Interviewer questions
  1. Why does softmax subtract the maximum logit?
  2. Derive the odds ratio between two tokens from logits.
  3. What happens if every vocabulary candidate is masked?
  4. How would you check whether model probabilities are calibrated?
B Deep technical explanation
Logits can be any finite real scores. Softmax converts their differences into a categorical distribution. For token i and V available tokens, pᵢ = exp(zᵢ) / Σⱼexp(zⱼ). Dividing numerator and denominator by exp(m) with m=maxⱼ zⱼ gives a numerically stable equivalent. Additive shifts zᵢ+c change no probabilities; rescaling logits does.


pᵢ = exp(zᵢ−m) / Σⱼ exp(zⱼ−m),   m=maxⱼzⱼ
log(pᵢ/pⱼ)=zᵢ−zⱼ  (for allowed tokens)


Worked example: logits [2,1,0] yield probabilities approximately [0.665,0.245,0.090]. Exp(2)/exp(1)=e gives the relative odds of the first versus second tokens. log_softmax is preferable when aggregating sequence log-likelihoods because multiplying many small probabilities underflows. Entropy H(p)=−Σpᵢlog pᵢ describes spread, not factual uncertainty, evidence sufficiency, or calibrated confidence.


  1. Suppress invalid candidates with true −∞ logits or a suitably safe mask implementation.
  2. Scale/transform logits as required by decoding strategy.
  3. Find the finite maximum per batch row; exponentiate shifted logits.
  4. Divide by the total finite mass and sample or take argmax.
  5. Use logsumexp to compute stable log probabilities for beam scoring and diagnostics.


Calibration: highly peaked token probabilities do not establish that a full answer is true. To assess confidence on a defined downstream task, measure reliability diagrams, expected calibration error where applicable, selective prediction risk-coverage, and task-specific held-out labels. Edge cases: all −∞ logits cause undefined normalization; NaNs propagate; mixed precision can underflow very small terms; tokenizer-specific special tokens may require masking. A production decoder must verify at least one eligible token remains after hard constraints.
C Interview-ready spoken answer
Softmax converts relative token logits into normalized probabilities. I implement it by subtracting the maximum score to avoid overflow, and use log-softmax for sequence scores. The probability ratio between two allowed tokens is exp of their logit difference. These probabilities are useful for decoding but are not a trustworthy measure of factual correctness or answer-level calibration.
D Follow-up pressure test
  1. Why does subtracting max not change p? Strong answer: common exponential factor cancels.
  2. Would a token probability of 0.99 justify an unsupported medical claim? Strong answer: no, it is conditional model probability, not externally verified truth.
  3. What if the entire grammar mask is invalid? Strong answer: decoder must detect empty eligible set and fail safely.
Mechanism → trade-off → concrete verification. Do not hand-wave.
E Production scenario
Incident: A custom decoder intermittently emits NaNs on long prompts. Hypotheses: raw exp(logits) overflow, all-token hard mask, or invalid postprocessor values. Instrument: min/max/finite logits, allowed-token count, per-row entropy, and normalization sum. Fix: logsumexp-based stable normalization, finite-value guards, and grammar fallback/error semantics that do not silently pick an invalid token. Acceptance: no NaNs under adversarial large-magnitude-logit fixtures and distributions sum to one within tolerance.
F Interview takeaways
  • Stable pᵢ = exp(zᵢ−max z)/Σexp(zⱼ−max z).
  • Log-odds between two tokens equal the logit difference.
  • Confidence in next-token selection does not prove grounded truth.


LESSON 03 / 14
Greedy decoding versus beam search
Distinguish local next-token decisions from approximate sequence-level search and its failure modes.
A Interviewer questions
  1. Give a two-step sequence where greedy decoding misses the most likely complete sequence.
  2. How do beam width, length normalization, and EOS termination influence output?
  3. Why is beam search often unpopular in open-ended chat generation?
  4. What is its time and KV-cache cost?
B Deep technical explanation
Greedy: choose argmaxᵢ P(yₜ=i | y<ₜ,x) at each step. It optimizes each next-token decision, not the sequence probability ∏ₜP(yₜ|y<ₜ,x). Beam search: keep the best W partial hypotheses ranked by accumulated token log-probabilities; expand each with candidate tokens, prune to W, and continue until a termination rule applies. It is an approximate search, not exhaustive global optimization unless exhaustive width is used.


score(y₁:T) = Σₜ log P(yₜ | y<ₜ,x)
illustrative length-adjusted: score_α(y)=score(y)/Tᵅ


Concrete counterexample: the first-step options have P(A)=0.55, P(B)=0.45. After A the best second token has probability 0.33, while after B a terminal token has probability 0.99. Greedy picks A then its best continuation, around 0.1815; a beam that keeps B can find B→EOS with likelihood 0.4455. These are fabricated values illustrating search, not actual model probabilities.


  1. Initialize beam with the prompt, total log-probability zero, and no generated tokens.
  2. For each active hypothesis, run next-token inference and propose candidate successors.
  3. Add log probabilities to parent scores; apply clearly documented length/coverage/constraint scoring.
  4. Preserve finished hypotheses while continuing unfinished ones; implementations differ in how they normalize and when they stop early.
  5. Return a finished hypothesis selected under the chosen rule, checking that a degenerate unfinished beam is not treated as a valid completion.


Engineering costs: with width W, up to W continuations require compute and KV states each step, although shared prefixes can reuse cache storage until branching. Beam search increases latency/memory and can intensify generic or repetitive outputs in open-ended conversation. Length normalization may change ranking and beam pruning. It is useful in constrained translation, transcription, or sequence tasks when likelihood is a reasonable quality proxy. It is not a guaranteed quality improvement; compare against sampling and task metrics rather than treating larger beams as automatically better. Beam size one is greedy only if scoring and special termination handling match.
C Interview-ready spoken answer
Greedy picks the highest-probability next token and can miss a better whole sequence. Beam search tracks multiple partial continuations using summed log probabilities and optional length normalization. That improves approximate sequence search for some constrained tasks but costs more decode compute and KV memory and can worsen blandness in open-ended chat. I decide using task evaluation, not beam width alone.
D Follow-up pressure test
  1. Is beam search guaranteed to beat sampling on human preference? Strong answer: no; likelihood and human utility differ.
  2. What happens to finished EOS beams? Strong answer: retain them as finished and avoid expanding them.
  3. How would you make beams efficient? Strong answer: share common prefix KV, prune early, cap width/length, benchmark latency.
Mechanism → trade-off → concrete verification. Do not hand-wave.
E Production scenario
Incident: A summarization service enables beam width eight to “improve accuracy” and experiences high p95 latency and less diverse outputs. Instrument: output length, beam survival, per-request GPU/KV occupancy, quality paired ratings, repetition, and hallucination rates. Options: restore width one for latency, test smaller beam/length penalty, or add constrained content requirements/evidence verification. Acceptance: paired quality improves on an agreed rubric without exceeding a p95 latency/cost budget; otherwise roll back.
F Interview takeaways
  • Greedy maximizes local probabilities; beam approximates high-scoring full sequences.
  • Beam width multiplies active hypothesis cost, especially KV state.
  • Likelihood is not a universal proxy for factuality, diversity, or helpfulness.


LESSON 04 / 14
Temperature and probability reshaping
Understand the exact logit scaling, entropy behavior, and why temperature is not a reliability switch.
A Interviewer questions
  1. Derive Pᵀ(i) for logits and show what happens as T approaches zero or infinity.
  2. Does temperature=0 always mean perfectly repeatable production output?
  3. Where should temperature sit relative to top-p filtering?
  4. When might high temperature be useful and harmful?
B Deep technical explanation
Temperature transforms relative logits before categorical sampling. For T>0, define pᵢ(T)=exp(zᵢ/T)/Σexp(zⱼ/T). When T<1, logit differences are magnified, making the top alternatives more dominant; T>1 flattens the distribution. For a unique largest logit, T→0⁺ concentrates all mass on its argmax; for T→∞, mass approaches uniform over eligible finite-logit candidates.


log(Pᵀ(i)/Pᵀ(j)) = (zᵢ−zⱼ)/T  (T>0)


Example: logits [2,1,0] at T=1 give about [0.665,0.245,0.090]. At T=0.5, they become approximately [0.867,0.117,0.016]. At T=2, they become approximately [0.506,0.307,0.186]. Temperature changes the relative probabilities but not the rank order of distinct finite logits. If T=0 is supported by an API, it normally selects a greedy path as a special case; you must not divide by zero in the formula.


Combining filters: a pedagogical implementation may apply temperature scaling before deriving the top-p nucleus and apply top-k to remove lower-ranked candidates. Filtering order and whether providers also apply repetition or presence penalties first are provider-specific. Top-k selection is rank-invariant under positive temperature, but top-p set membership is not: p depends on temperature-scaled mass. Verify a provider’s contract before porting presets.


Production: lower T can help consistency in bounded extraction/classification but cannot repair missing information, flawed retrieval, unsupported claims, or a misaligned system instruction. T=0 is not a universal bitwise-determinism guarantee; hardware kernels, nondeterministic reductions, model routing/version changes, ties, or external tool state may change the output. For ideation you may accept wider diversity; for regulated decisions you should use deterministic validation, evidence checks, and task-specific evals regardless of T.
C Interview-ready spoken answer
Temperature divides logits before softmax: low temperature sharpens probability ratios, high temperature flattens them, and a temperature-zero API path typically uses greedy decoding. It controls diversity, not model knowledge or factual validity. I test its interaction with top-p and other processors and do not assume temperature zero makes a distributed serving stack fully deterministic.
D Follow-up pressure test
  1. If T doubles, do candidate ranks change? Strong answer: no among finite logits, only relative probabilities.
  2. If p=0.9 nucleus changes after lowering T, why? Strong answer: probability mass concentrates faster.
  3. What would prove a setting improves consistency? Strong answer: repeated matched evaluations, format validity, semantic agreement, and failure rates.
Mechanism → trade-off → concrete verification. Do not hand-wave.
E Production scenario
Incident: A structured extractor intermittently invents missing values. A team lowers temperature and calls it fixed. Instrument: missing-field false positives, JSON validity, per-field evidence links, null abstention rates, and data slices. Mitigation: enforce schema, define unknown/null, require cited evidence, add deterministic postvalidation, then tune T if needed. Acceptance: accuracy and abstention precision on a held-out set meet thresholds; not merely “outputs look less random.”
F Interview takeaways
  • Temperature divides logits for T&gt;0; T=0 usually means a separate greedy branch.
  • Temperature changes entropy but not token rankings.
  • It is not a hallucination switch or a guaranteed reproducibility control.


LESSON 05 / 14
Top-k and Top-p (nucleus) sampling
Compute candidate filtering correctly and understand dynamic vs fixed support sizes.
A Interviewer questions
  1. For a toy probability vector, compute exact top-k and top-p allowed sets.
  2. Why must top-p include the token that crosses the cumulative threshold?
  3. How does temperature change nucleus membership?
  4. What guard is needed when all candidates have been masked?
B Deep technical explanation
Top-k: keep the k highest-ranked eligible token scores and set others to −∞; renormalize the retained distribution. It imposes a fixed candidate count even when the distribution is extremely sharp or flat. Top-p: sort eligible tokens by descending probability, retain the smallest nonempty prefix whose cumulative original mass is at least p, then renormalize that prefix. It adapts the candidate count to probability concentration.


Sₚ = smallest ranked prefix S such that Σᵢ∈S P(i) ≥ p
P_filtered(i) = P(i) / Σⱼ∈S P(j)   if i∈S; otherwise 0


Example: P=[0.50,0.25,0.15,0.07,0.03]. Top-k with k=2 keeps the first two tokens, which renormalize to [0.667,0.333]. Top-p with p=0.80 retains three tokens because 0.50+0.25=0.75 is insufficient and adding 0.15 reaches 0.90; renormalized mass is approximately [0.556,0.278,0.167]. For p=0.5, only the first token survives. The threshold-crossing token must remain included.


  1. Start from valid logits, apply compatible penalties/masks/temperature per the chosen implementation.
  2. If using top-k, retain the highest k currently eligible tokens.
  3. Compute stable probabilities over remaining candidates.
  4. If using top-p, sort by descending probability and keep the smallest mass-covering prefix.
  5. Normalize again and sample using a controlled random-number generator.


Failure cases: small k can eliminate rare but necessary identifiers, JSON characters, domain terms, or end tokens; high p with a flat tail permits nonsensical low-probability tokens. Top-p can become effectively greedy with a highly peaked distribution. Some implementations use min_p, typical sampling, or nucleus threshold variations; do not assume identical parameter semantics across platforms. Sorting all V logits may be expensive, and top-k/top-p implementations often use partial selection/fused kernels. Compare quality under the actual task rubric and log the exact processor chain for reproducibility.
C Interview-ready spoken answer
Top-k restricts decoding to a fixed k top tokens; top-p chooses the smallest probability-ranked prefix whose cumulative mass reaches p. Both renormalize probabilities before sampling. Top-p adapts candidate count to distribution shape, while top-k does not. I pay attention to the exact temperature/filter order, EOS eligibility, and schema-constrained outputs because overly aggressive filtering can eliminate valid completions.
D Follow-up pressure test
  1. Would top-p=0.8 keep a prefix totaling 0.75? Strong answer: no, include next token crossing threshold.
  2. Can top-k=1 differ from greedy? Strong answer: equivalent token choice under same masks/tie rules, but API edge behavior may differ.
  3. What if EOS falls outside top-k? Strong answer: generation may run until max tokens, requiring budget safeguards.
Mechanism → trade-off → concrete verification. Do not hand-wave.
E Production scenario
Incident: A domain code generator starts producing truncated output after deploying aggressive top-k. Hypotheses: necessary rare syntax tokens have been excluded, EOS is prematurely favored after filtering, or a stop sequence matches too broadly. Diagnose: raw rank of required tokens, per-step filtered support, final stop reason, and parse/test outcomes. Action: tune k/p jointly with grammar-constrained decoding and semantic tests. Acceptance: exact parser validity, task success, and max-token termination rates meet targets at acceptable latency.
F Interview takeaways
  • Top-k fixes count; top-p fixes cumulative probability mass.
  • Always include threshold-crossing token and keep nonempty support.
  • Filtering cannot distinguish truth from plausible prose; calibrate to task.


LESSON 06 / 14
Repetition penalties and decoding failure modes
Distinguish repeated-token score processing from n-gram, lexical, and task-level consistency controls.
A Interviewer questions
  1. Why can repetition penalties damage code generation and exact quotation?
  2. How does a sign-aware repetition penalty modify positive versus negative logits?
  3. What causes looping besides sampling parameters?
  4. How would you trace a repetition regression step by step?
B Deep technical explanation
Repetition is not one defect. It may be a token loop (the the the), repeated n-gram, recursive plan/tool loop, repetitive sentence style, or an intentionally repeated identifier that a task requires. There are several distinct logit processors:


ControlMechanismTrade-off
Repetition penalty rFor seen token i, illustrative: zᵢ←zᵢ/r if zᵢ≥0, else zᵢ←r zᵢ (r>1).Suppresses seen tokens even when valid repetition is required.
Presence penaltySubtract a fixed amount if token appeared at least once.Reduces reuse, ignores frequency.
Frequency penaltySubtract amount proportional to prior token count.Progressively discourages frequent necessary tokens.
No-repeat n-gramHard-mask a token if it would complete a repeated n-gram.Can prohibit valid grammar, labels, or quotations.
Length/stop controlsStop at EOS, safe delimiter, or max tokens.Prevents endless runtime, not necessarily bad content.


Mechanism details: a sign-aware penalty avoids accidentally increasing the probability of a previously seen negative-logit token; the exact formula and whether it covers prompt tokens or only generated output are implementation-specific. Additive frequency penalties modify logits, not probabilities. They should be applied before sampling normalization. Detect repeated text both at token level and normalized sentence/task level because byte/subword boundaries hide semantic loops.


Diagnosis: log token_id, raw and processed logit ranks, cumulative history counts, stop reason, generation length, prompt suffix and temperature/top-p settings; correlate repetition with prompt template, model version, and tool observations. If repeated reasoning is caused by stale context or a controller reissuing tool calls, decoder penalties do not fix the underlying state machine. Prefer constrained planners, state-change checks, or task-specific termination. Evaluation: exact-n-gram repetition rate together with correctness, code compilation, named-entity preservation, and human preference. Lowering repetition at the cost of breaking data fidelity is not an improvement.
C Interview-ready spoken answer
I separate token-level degeneration from application-level loops. Repetition, presence, frequency, and no-repeat n-gram penalties modify candidate logits or masks, but they can damage identifiers, quotations, and source fidelity. I inspect token traces and compare repetition rates with task correctness, and use explicit agent-state/stop logic when the repetition is caused by a workflow loop rather than token sampling.
D Follow-up pressure test
  1. Why does dividing a negative logit by r backfire? Strong answer: makes it less negative and more likely.
  2. Will no-repeat-3gram prevent repeated concepts? Strong answer: not reliably; paraphrases differ at token level.
  3. Where would you apply penalties in a schema decoder? Strong answer: only where they cannot invalidate grammar obligations, with eligibility guards.
Mechanism → trade-off → concrete verification. Do not hand-wave.
E Production scenario
Incident: A financial-report summarizer repeats the same bullet six times after a prompt change. Instrument: token-level run length, repeated 3/4-gram rates, summarization input ordering, output truncation, and model stop reason. Hypotheses: generation loop, duplicated retrieved context, missing EOS, or failure in streaming stop detection. Options: deduplicate inputs, fix stop conditions, tune penalties with exemptions, or impose a finite structured outline. Acceptance: repetition decreases while key numbers, citations, and factual fidelity remain stable or improve.
F Interview takeaways
  • Sign-aware penalties alter logits, not the learned model.
  • Repetition can arise from prompts, retrieval, controller loops, or decoding.
  • Measure accuracy regression as well as repetition reduction.


LESSON 07 / 14
EOS, stop tokens, and stop sequences
Define model token termination, API string matching, streaming boundaries, and completion invariants.
A Interviewer questions
  1. Differentiate an EOS token ID from a user-supplied multi-character stop string.
  2. Why can a streamed stop delimiter straddle two network chunks?
  3. How do max_new_tokens and context-window limits interact?
  4. What happens when stop filtering accidentally removes a structural JSON delimiter?
B Deep technical explanation
EOS is a learned special token ID. At each autoregressive step the model may assign a probability to an end-of-sequence token. When sampled, a decoder stops according to its completion protocol. Chat models may use multiple trained end markers (end-of-message/end-of-turn/tool handoff) whose meanings are determined by model and conversation format. A stop sequence is typically an API-level text string or token pattern checked by the serving layer, and may encode into multiple tokens. A max token budget is an external hard limit; reaching it is not semantic completion.

B Deep technical explanation
Mechanism: the next-token objective rewards likely continuations, not the truth of externally verifiable claims. Answer if   E[utility(answer) | evidence] > E[utility(abstain) | evidence]

"""Module 4: decoding algorithms, context budgets, and stopping.
Educational, dependency-free standard-library reference (not a model).
Run: python module4_decoding_reference.py
"""
from __future__ import annotations

import math
import random
from typing import Callable, Sequence


def softmax(logits: Sequence[float], temperature: float = 1.0) -> list[float]:
    """Numerically stable softmax; -inf logits are explicitly excluded."""
    if temperature <= 0 or not math.isfinite(temperature):
        raise ValueError("temperature must be finite and positive; use argmax for greedy")
    scaled = [x / temperature for x in logits]
    valid = [x for x in scaled if x != -math.inf]
    if not valid:
        raise ValueError("at least one token must be allowed")
    if any(math.isnan(x) or x == math.inf for x in scaled):
        raise ValueError("invalid logits")
    m = max(valid)
    exps = [0.0 if x == -math.inf else math.exp(x - m) for x in scaled]
    z = sum(exps)
    return [x / z for x in exps]


def filter_top_k(logits: Sequence[float], k: int | None) -> list[float]:
    if k is None:
        return list(logits)
    if k < 1:
        raise ValueError("k must be >=1")
    rank = sorted(range(len(logits)), key=lambda i: (-logits[i], i))
    keep = set(rank[:min(k, len(logits))])
    return [x if i in keep else -math.inf for i, x in enumerate(logits)]


def filter_top_p(logits: Sequence[float], p: float, temperature: float = 1.0) -> list[float]:
    """Retain smallest sorted prefix whose probability mass reaches p."""
    if not (0 < p <= 1):
        raise ValueError("top_p must be in (0,1]")
    probs = softmax(logits, temperature)
    rank = sorted(range(len(probs)), key=lambda i: (-probs[i], i))
    keep, mass = set(), 0.0
    for i in rank:
        if probs[i] == 0:
            continue
        keep.add(i)
        mass += probs[i]
        if mass >= p:
            break
    return [x if i in keep else -math.inf for i, x in enumerate(logits)]


def apply_repetition_penalty(logits: Sequence[float], history: Sequence[int], factor: float) -> list[float]:
    """Example sign-aware repetition penalty; implementations may vary."""
    if factor <= 0 or not math.isfinite(factor):
        raise ValueError("factor must be positive")
    out = list(logits)
    for token in set(history):
        x = out[token]
        out[token] = x / factor if x >= 0 else x * factor
    return out


def sample_token(
    logits: Sequence[float], *, temperature: float = 1.0,
    top_k: int | None = None, top_p: float = 1.0,
    rng: random.Random | None = None
) -> int:
    """Illustrative processor order: temperature then top-k then top-p."""
    if temperature == 0:
        # Some APIs implement a temperature=0 greedy special case.
        return max(range(len(logits)), key=lambda i: logits[i])
    processed = filter_top_k(logits, top_k)
    processed = filter_top_p(processed, top_p, temperature)
    probs = softmax(processed, temperature)
    r = (rng or random).random()
    mass = 0.0
    for i, p in enumerate(probs):
        mass += p
        if r < mass:
            return i
    return len(probs) - 1


def greedy_decode(
    logits_fn: Callable[[list[int]], Sequence[float]],
    prefix: Sequence[int], *, eos_id: int, max_new_tokens: int
) -> list[int]:
    tokens = list(prefix)
    for _ in range(max_new_tokens):
        z = logits_fn(tokens)
        tid = max(range(len(z)), key=lambda i: z[i])
        tokens.append(tid)
        if tid == eos_id:
            break
    return tokens


def beam_search(
    logits_fn: Callable[[list[int]], Sequence[float]],
    prefix: Sequence[int], *, eos_id: int,
    width: int, max_new_tokens: int, length_alpha: float = 0.0
) -> list[int]:
    """Toy beam search with terminal beams and optional length normalization.
    length normalization can affect beam pruning; this is a pedagogical version.
    """
    if width < 1 or max_new_tokens < 0:
        raise ValueError("invalid beam parameters")
    # list[(full_tokens, sum_logp, finished, generated_count)]
    beams = [(list(prefix), 0.0, False, 0)]
    def score(row):
        _, logp, _, length = row
        return logp / max(1, length) ** length_alpha
    for _ in range(max_new_tokens):
        expansions = []
        for tokens, logp, finished, length in beams:
            if finished:
                expansions.append((tokens, logp, True, length))
                continue
            probs = softmax(logits_fn(tokens))
            for i, p in enumerate(probs):
                if p > 0:
                    expansions.append((tokens + [i], logp + math.log(p), i == eos_id, length + 1))
        beams = sorted(expansions, key=score, reverse=True)[:width]
        if all(done for _, _, done, _ in beams):
            break
    return max(beams, key=score)[0]


def context_budget(window: int, system: int, history: int, retrieved: int,
                   user: int, reserve_output: int, overhead: int = 0) -> dict[str, int | bool]:
    if min(window, system, history, retrieved, user, reserve_output, overhead) < 0:
        raise ValueError("token counts must be nonnegative")
    used = system + history + retrieved + user + reserve_output + overhead
    return {'used': used, 'headroom': window - used, 'fits': used <= window}


def run_tests() -> None:
    z = [4.0, 2.0, 1.0, -1.0]
    p = softmax(z)
    assert abs(sum(p) - 1.0) < 1e-12
    assert softmax([10000, 9999])[0] > 0.7  # stable large logits
    assert softmax([0, -math.inf]) == [1.0, 0.0]
    assert filter_top_k(z, 2)[2:] == [-math.inf, -math.inf]
    assert sum(math.isfinite(x) for x in filter_top_p(z, 0.9)) == 2
    assert apply_repetition_penalty([2., -2.], [0, 1], 2.) == [1., -4.]
    assert all(sample_token(z, top_k=1, rng=random.Random(i)) == 0 for i in range(20))
    # Greedy gets trapped in a locally high-probability first step.
