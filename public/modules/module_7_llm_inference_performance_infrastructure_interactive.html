LESSON 01 / 16

Prefill vs. decode: computation and data flow

Distinguish bulk prompt processing from one-token incremental inference.

A Interviewer questions

  1. Trace a chat completion from admission through prefill to the final streamed token.
  2. Why does the prefill stage compute K/V for all input tokens but decode only for the newest token?
  3. Where do tokenization, queueing, detokenization and EOS handling show up in TTFT?

B Deep technical explanation

Mechanism & data flow

At request arrival, the router formats chat messages and tokenizes them, queues the request, and assigns a scheduler slot. Prefill runs the prompt through all Transformer layers using causally masked attention. It produces hidden states and K/V tensors for valid prompt positions, inserts their K/V into the cache, and obtains a distribution for the first output token. Decode then loops: sample the next token, run one-token Q/K/V and FFN projections, append new K/V, attend with Q against cached history, stream detokenized bytes, and stop at EOS, stop sequence or length budget. Mixed batches may contain prefill chunks and decoding requests simultaneously. Prompt-prefix caching can avoid recomputing *matching* stable prefixes; it is not universal response caching.

Equations and assumptions

Prefill attention score pairs per head = N(N+1)/2 for full causal N-token input (efficient kernels need not materialize them). Decode step t attends to N+t cached keys. Generation latency ≈ queue + prefill + Σ_t decode(t) + network/stream overhead. The exact first-token reporting boundary is service-defined.

Architecture alternatives

Whole-prompt prefill offers efficient GEMMs but can block decoding if scheduled monolithically. Chunked prefill interleaves work; prefill/decode separation isolates resource allocation but introduces KV transfer.

Implementation & instrumentation

Instrument tokenizer time, prompt length, queue wait, prefill kernel time, KV allocation, per-step decode and network flush. Separate end-of-prefill from first externally delivered token. Guard capacity at admission.

Latency, memory, compute & cost

Prefill has parallel positions and sizable matrix operations; decode is sequential across generated tokens and repeatedly reads weight/KV state. Output length can dominate end-to-end time despite short prompts.

Edge cases & failure modes

Don’t say prefill “generates all tokens”; it computes prompt hidden states and normally initiates the first sample. Cached prefixes must match positions, attention masks, model version and tenancy rules.

C Interview-ready spoken answer

“I split inference into prefill and decode. Prefill processes the prompt in parallel and initializes per-layer KV state, then decode produces tokens sequentially while reusing that cache. That is why prompt length mainly affects TTFT, while output length and cache bandwidth affect ongoing token latency. I instrument queue, prefill and decode separately before optimizing.”

D Follow-up pressure test

  1. If prefill finishes in 200 ms, can external TTFT still be 1.2 seconds?
  2. Why is the final decode result not necessarily emitted immediately?
  3. Can a warm prefix cache bypass all GPU work?

E Production scenario — diagnose, mitigate, validate

Incident: A chatbot has high TTFT but acceptable streamed token rate. Break TTFT into queue, tokenize, prefix-lookup, prefill, first decode and transport; compare warm/cold prompts and cache hits. Decide between admission changes, chunking, prefix reuse and prompt reduction.

Success metrics: Predeclare p95 TTFT and p95 TPOT SLOs, verify accuracy and no cache cross-tenant reuse, and require measurable improvement on matched workloads.

F Interview takeaways

  • Prefill computes all prompt positions; decode adds one position per step.
  • TTFT includes more than GPU prefill.
  • Profile the lifecycle before changing the model.
LESSON 02 / 16

Why prefill is usually compute-bound and decode often bandwidth-bound

Derive arithmetic intensity instead of repeating a slogan.

A Interviewer questions

  1. Use a roofline argument to explain a low-batch decode bottleneck.
  2. What changes the compute/bandwidth balance as concurrent batch size rises?
  3. Why can attention KV reads dominate long-context decoding even with GQA?

B Deep technical explanation

Mechanism & data flow

For a dense linear layer Y=XW, a large prefill input X has many rows, enabling a GPU to reuse W across a large matrix multiplication; math per fetched weight rises. At decode batch one, a thin vector-matrix operation still needs to read most W but does relatively little work per weight. HBM traffic can cap tokens/sec even if tensor cores are mostly idle. Decode also streams historical KV through attention; as context and active sequences grow, KV bytes/step grow. At high concurrency, batched decode turns vectors into GEMMs and raises weight reuse, so “decode is always bandwidth-bound” is not universally true.

Equations and assumptions

Idealized dense matmul: FLOPs ≈ 2·M·K·N; bytes for weights ≈ K·N·b. Weight-only arithmetic intensity ≈ 2M/b FLOP/byte (ignores input/output, caches and fusion). Roofline time ≥ max(FLOPs / achievable_FLOPs_s, bytes / achievable_HBM_B_s).

Architecture alternatives

More batching often boosts total throughput but can raise individual request latency. Quantizing weights reduces bytes but dequantization and unsupported kernels may erase gains. Faster memory devices or better partitioning help bandwidth-bound decode.

Implementation & instrumentation

Collect profiler roofline evidence: SM/tensor-core occupancy, achieved HBM bandwidth, GEMM shapes, kernel launch time and tokens/second at batch sizes 1, 4, 16. Profile attention/MLP separately.

Latency, memory, compute & cost

When effective arithmetic intensity sits below the hardware ridge point (peak compute/peak bandwidth), memory transfer limits a kernel; above it, compute may dominate. Hardware theoretical peaks are upper bounds, not observed performance.

Edge cases & failure modes

An algorithm can move between regimes by batch/sequence length, quantization, kernel fusion, weight residency and parallelism. Keep units straight: GB/s decimal vs GiB/s binary.

C Interview-ready spoken answer

“Prefill runs large GEMMs and reuses weights across prompt positions, so it often reaches a compute-heavy regime. Decode at small batch reads model weights again per new token with little reuse, making it memory-bandwidth-bound. A roofline calculation checks FLOPs per HBM byte; I confirm this with GPU traces, and I recognize that larger decode batches can change the regime.”

D Follow-up pressure test

  1. Compute an optimistic decode tokens/s cap from resident weight bytes and achieved GB/s.
  2. How does GQA modify the KV traffic term?
  3. Why might INT4 throughput be worse than BF16 on a particular GPU?

E Production scenario — diagnose, mitigate, validate

Incident: A deployed 8-bit model uses less VRAM but delivers no token-rate improvement. Profile memory transactions, GEMM kernel selection, dequant kernels and achieved occupancy against BF16; verify both batching and token shapes.

Success metrics: Require matched-output-quality throughput and TPOT measurements across the real input/output length distribution, not weight-size alone.

F Interview takeaways

  • Arithmetic intensity determines the roofline regime.
  • Decode regime depends strongly on batch and context length.
  • Quantization performance is kernel-dependent.
LESSON 03 / 16

TTFT, TPOT, end-to-end latency, and throughput

Treat latency percentiles and throughput as different workload-level quantities.

A Interviewer questions

  1. Define TTFT, TPOT, ITL, request throughput and token throughput precisely.
  2. Explain why average TPOT can hide a single 2-second inter-token stall.
  3. Design a fair benchmark comparing engines with different request lengths and arrival processes.

B Deep technical explanation

Mechanism & data flow

For each user request, record request arrival, queue exit, first streamed output, every subsequent token delivery, and final completed response. TTFT is time from request start to the first observable token, often including processing and network; its definition must be consistent. Inter-token latency (ITL) is elapsed time between consecutive token arrivals. TPOT is commonly output-generation time divided by number of subsequent tokens; implementations vary in denominators, so state the convention. Throughput may mean requests/s, total generated tokens/s, or combined input + output tokens/s. Compare distributions by prompt/output length, concurrent requests, cache hits and cold/warm models.

Equations and assumptions

For output tokens delivered at t₁…tₒ, TTFT=t₁−t_request; ITLᵢ=tᵢ−tᵢ₋₁ for i≥2; TPOT≈(tₒ−t₁)/(O−1) for O>1; response latency=tₒ−t_request. Little’s law L=λW holds under steady stable conditions.

Architecture alternatives

Low TTFT and low TPOT may trade off under scheduler priorities: decode-first protects live streams, while aggressive prefill improves admission and fresh-request TTFT. Tail latency is user-facing, not optional.

Implementation & instrumentation

Use timestamp instrumentation at model server and client for SSE chunks; do not confuse raw tokens with arbitrary byte chunks. Benchmark open-loop offered-load curves as well as fixed-concurrency closed-loop tests.

Latency, memory, compute & cost

At fixed load, increasing active concurrency can improve generated tokens/s until memory, scheduler or HBM saturates; beyond saturation queues and tail latencies explode. Report goodput: rate meeting quality and latency SLO.

Edge cases & failure modes

Token streaming may coalesce multiple tokens; first byte can be metadata rather than text. Cross-provider TTFT measurements may use different clock boundaries.

C Interview-ready spoken answer

“I report TTFT for responsiveness, ITL/TPOT for streaming smoothness, e2e latency for task completion, and token/request goodput at an SLO. I stratify by prompt and output lengths, concurrency, cache state and queueing; a strong average can hide disastrous p99 stalls.”

D Follow-up pressure test

  1. If TTFT improved 20% but p99 ITL tripled, did serving improve?
  2. What does an overloaded open-loop queue look like?
  3. Why are tok/s figures incomparable without context and batch distributions?

E Production scenario — diagnose, mitigate, validate

Incident: A test shows excellent average throughput but users complain of freezes. Compare server inter-token histograms to client chunk timestamps, correlate stalls with prefill admissions and KV evictions, then tune token budgets.

Success metrics: Acceptance requires p95 TTFT, p99 ITL, successful-request goodput and error rates under a representative arrival trace.

F Interview takeaways

  • Measure per-request latency and fleet throughput separately.
  • Tail ITL reveals decode starvation.
  • State benchmark clocks and traffic shape.
LESSON 04 / 16

Why the first token can be slower

Localize first-token delays without claiming each first token is inherently more expensive.

A Interviewer questions

  1. Enumerate first-token path costs and identify which change under prompt caching.
  2. When might the first token be faster than subsequent tokens?
  3. What experiments separate cold-start from long-prompt TTFT?

B Deep technical explanation

Mechanism & data flow

First-token delivery typically requires request validation, prompt construction, tokenization, scheduling, potentially cold model loads or graph capture, full prompt prefill, a first output projection and sampling, then network write. Subsequent steps reuse prompt KV and process only a new input token, but their attention history grows. For very short prompts or heavily loaded mixed traffic, it is possible for TTFT to be small and future tokens to stall due to scheduling or memory pressure. A tokenizer bottleneck does not disappear by deploying FlashAttention.

Equations and assumptions

TTFT = queue + preprocess + cold-start(optional) + prefill + first-token sample/delivery. For full attention prefill compute grows roughly quadratically with N in attention scores; dense projection FLOPs grow linearly with N (for fixed model dims).

Architecture alternatives

Reducing prompt size or leveraging valid prefix cache tackles prefill. Prewarming weights and compilation handles cold starts. Scheduling changes tackle queue delay. Streaming transport must flush appropriately.

Implementation & instrumentation

Run four matched traces: cold/warm model × cache-hit/miss, with short/long prompts. Measure each stage at server and client boundaries.

Latency, memory, compute & cost

A long 32k prompt with 10-token answer is first-token dominated; a 128-token prompt with 4k-token answer is decode dominated. Different optimization budgets follow.

Edge cases & failure modes

Comparing first and later token *latency* is meaningful only under the same concurrency and output streaming semantics. Cache hit is not synonymous with answer hit.

C Interview-ready spoken answer

“First-token latency is often higher because the server must process the prompt and establish KV state before it can start generation. I break TTFT into queue, preprocessing, cold load, prefill and first sample. I then optimize whichever stage dominates, while checking that decode-tail latency and answer quality remain intact.”

D Follow-up pressure test

  1. If TTFT doubles after adding a content filter, should we change model kernels?
  2. Can prompt caching decrease first-token compute for all user prompts?
  3. What causes first-token p99 under bursty arrival?

E Production scenario — diagnose, mitigate, validate

Incident: Following a deploy, cold requests experience 4-second TTFT while warm ones do not. Trace startup/checkpoint IO and CUDA graph warmup; compare prewarmed replica pools vs delayed load.

Success metrics: Validate cold/warm p95 TTFT and cost of idle replicas, with explicit user-facing latency targets.

F Interview takeaways

  • First-token time contains more than inference compute.
  • Prompt length and cold start are separable diagnoses.
  • Optimize the observed stage.
LESSON 05 / 16

KV caching and incremental decode

Calculate work avoided by reusing past keys and values.

A Interviewer questions

  1. Explain precisely which tensors are cached per layer and which are recomputed.
  2. Why does a KV cache not eliminate attention work over historical positions?
  3. Demonstrate cached vs uncached output parity with causal masking.

B Deep technical explanation

Mechanism & data flow

At each decoder layer, the input prompt produces key and value projections for all positions. On subsequent generation steps, previous K/V remain valid because causal self-attention prevents past hidden states from depending on future generated tokens. The new token produces its Q, K and V; its query attends to cached K/V plus current K/V. Keeping caches avoids repeated historical projections and full-prefix Transformer passes. A cache must be keyed to the exact model, positions, attention mask, rope offsets, and request/prefix identity. Paged KV allocators manage where tensors reside, not the mathematical K/V contents.

Equations and assumptions

Per-request KV elements = 2 × n_layers × sequence_tokens × n_kv_heads × head_dim. Multiply by bytes/value and active requests for memory. With a fixed cache, new-token self-attention score work per layer/head is O(T) rather than rerunning full O(T²) attention for every prefix.

Architecture alternatives

Cache choices include dynamic contiguous, static reserved, block-paged, shared-prefix, quantized, sliding and CPU-offloaded variants. Offloading relieves VRAM but adds transfer latency.

Implementation & instrumentation

Validate against an uncached full forward on tiny fixed input using identical weights, positions, causal mask and deterministic sampling; test prefix changes, forks, cancellations and model upgrades.

Latency, memory, compute & cost

KV cost increases linearly with live cached token count for full attention, and memory admission is limited by sum across active sequences, not just maximum sequence length.

Edge cases & failure modes

Reusing K/V across different tenants or altered prompt content can leak context. Naively retaining entire multimodal KV also grows quickly. A cache may improve throughput while reducing max batch due to memory.

C Interview-ready spoken answer

“The cache stores K/V from previous positions at every attention layer. Because causal attention makes those past states independent of future tokens, decode only computes projections for the newest token, then attends against the cached prefix. It removes redundant recomputation, but KV memory still grows with live tokens and must be admission-controlled and isolated.”

D Follow-up pressure test

  1. Calculate bytes for 32 layers, 8 KV heads, 128 width and 16,384 tokens at BF16.
  2. Does disabling the cache reduce peak memory at the cost of recomputation?
  3. How do you catch a wrong RoPE offset after resumed decoding?

E Production scenario — diagnose, mitigate, validate

Incident: Occasional repeated or nonsensical tokens appear only with shared-prefix caching. Reproduce with deterministic seeds and cached/uncached parity; inspect prefix hashes, position metadata and refcounts.

Success metrics: Zero unauthorized cache sharing; bitwise or tolerance-defined parity on reference cases and stable latency/VRAM under concurrent replay.

F Interview takeaways

  • Cache K/V, not every hidden state or attention score.
  • Memory is linear in cached tokens for full attention.
  • Correctness and tenant isolation are core invariants.
LESSON 06 / 16

GPU memory: weights, activations, workspace and KV

Build a realistic serving budget before selecting hardware.

A Interviewer questions

  1. Can an 8B BF16 model fit into a 16-GiB GPU in production? Justify every reserve.
  2. What is the difference between allocated, reserved and free GPU memory?
  3. How do batch, token count, attention layout and quantization alter memory?

B Deep technical explanation

Mechanism & data flow

Weight memory is parameters × stored bits plus quantization scales/zeros, tied weights, padding and miscellaneous tensors. KV memory scales with total active tokens and KV-head dimensions. Inference activations are smaller than in training because no backward graph is kept, but prefill intermediate tensors, logits, attention kernels, temporary workspaces, CUDA graphs, fragmentation and runtime library state still use VRAM. Tensor parallelism shards portions of weights and caches, but interconnect buffers and unsharded modules remain. Budget headroom for output-token growth, requeues and bursts, not just average token count.

Equations and assumptions

VRAM_budget ≥ params×weight_bytes + Σ_requests(2L·Hkv·Dh·Treq·kv_bytes) + prefill_activations + workspaces + allocator_slack + graph_memory. Example: 8B BF16 ≈ 16.0 GB ≈ 14.9 GiB weights alone; 32L/8KV/128/BF16/8,192 tokens = 1 GiB cache.

Architecture alternatives

Quantization lowers weight capacity but can lower quality; GQA lowers KV specifically; paging reduces fragmentation; CPU KV offload swaps bandwidth for memory. All can coexist.

Implementation & instrumentation

Collect actual `memory_allocated`, `memory_reserved`, nvidia-smi process bytes, GPU traces and peak-per-stage usage. Measure at maximum allowed prompt, output and concurrent request mix.

Latency, memory, compute & cost

Peak memory can be greater than the sum of static formulas during prefill. At target utilization U, reserve (1−U) for dynamic spikes and deployment variability rather than treating nominal GPU size as free.

Edge cases & failure modes

“8B” is sometimes approximate and excludes multimodal encoders or heads; INT4 theoretical weights are not necessarily 4 bits/parameter after metadata.

C Interview-ready spoken answer

“I start with weights, exact KV cache shape for active tokens, then peak inference workspaces and allocator/headroom. I do not assume nominal GPU capacity is usable VRAM. I use model-specific telemetry at maximum admitted request mix and enforce a token-based capacity limit to avoid OOM under bursts.”

D Follow-up pressure test

  1. How many GiB are used by 4-bit weights for 70B parameters before metadata?
  2. What reserves would you use for a 48-GiB deployment?
  3. What if requests each grow another 2k output tokens after admission?

E Production scenario — diagnose, mitigate, validate

Incident: Production OOMs appear at only 50% of theoretical request slots. Compare allocated vs reserved memory, token-length distribution, graph captures, fragmentation and workspace spikes.

Success metrics: Admission gate must survive stress at p99 input/output lengths with no OOM and a declared percent VRAM safety reserve.

F Interview takeaways

  • Weights plus KV is necessary but not sufficient.
  • KV is determined by active tokens and architecture.
  • Use real high-water telemetry to set safe admission.
LESSON 07 / 16

Quantization: FP32, FP16, BF16, INT8 and INT4

Understand numerical formats and why fewer bits do not guarantee faster inference.

A Interviewer questions

  1. Compare FP16 exponent limits with BF16 exponent limits.
  2. Why are INT8 and INT4 not drop-in equivalents to floating-point formats?
  3. When should weights, activations and KV cache use different precisions?

B Deep technical explanation

Mechanism & data flow

FP32 has 8 exponent bits and 23 explicit fraction bits; FP16 has 5 exponent and 10 fraction bits; BF16 has 8 exponent and 7 fraction bits. Lower-bit integer quantization maps floating values into discrete codes using scale and possibly zero point, often per tensor, channel or group. Inference dequantizes or uses fused integer GEMM kernels. Weight-only INT4 is common when weights dominate memory, whereas activations and KV may need their own calibration and kernel support. Mixed-precision accumulations matter for numerical stability.

Equations and assumptions

Symmetric quant: q=clip(round(x/s), qmin, qmax), x_hat=s·q. Idealized weight GiB = P·bits/(8·2³⁰), plus scales/zero-points/metadata. BF16 and FP16 both use 2 bytes/value but have different dynamic range/precision.

Architecture alternatives

BF16 is often robust for large activation ranges; FP16 can offer greater mantissa precision near unity but narrower range. INT8 vs INT4 trades compression for quantization error; FP8/FP4 and mixed-kernel variants depend on GPU support.

Implementation & instrumentation

Use representative calibration/evaluation data; compare per-layer outlier distributions and sensitive attention/output heads, run structured-output and reasoning regressions, check actual chosen kernel and quantization metadata.

Latency, memory, compute & cost

Compression of model weights can allow more replicas or longer KV, but dequant arithmetic and unfused kernels can hurt p95 TPOT; different batch sizes may reverse the result.

Edge cases & failure modes

Quantization is not a guaranteed 4× RAM reduction for 16→4 bits due to metadata and runtime overhead, nor a guaranteed speedup. Distinguish accuracy and calibration failure from implementation bugs.

C Interview-ready spoken answer

“Floating formats trade exponent range against mantissa precision; BF16 has FP32-like exponent range at lower precision. INT8/INT4 quantization maps values through learned or calibrated scales. I choose precision separately for weights, activations and KV, then validate quality and *actual* kernel throughput on target hardware.”

D Follow-up pressure test

  1. What is the failure when one attention channel has rare large outliers?
  2. How can W4A16 differ from W8A8?
  3. Why should you benchmark quantized decode at the deployed batch size?

E Production scenario — diagnose, mitigate, validate

Incident: INT4 rollout reduces weight bytes but breaks code-format correctness and worsens p95. Analyze outlier layers, scales, group size and dequant kernel; selectively hold some layers at BF16.

Success metrics: Pass domain golden eval, long-context parity tolerance and p95/throughput SLO before enabling quantized weights.

F Interview takeaways

  • Memory savings and speed are different claims.
  • BF16 and FP16 have different exponent ranges.
  • Precision must be checked by component and workload.
LESSON 08 / 16

Post-training quantization vs quantization-aware training

Choose calibration-only vs retraining-with-quantization based on sensitivity.

A Interviewer questions

  1. What statistics does PTQ calibration collect and how are scales selected?
  2. How does fake quantization in QAT expose the optimizer to quantization error?
  3. When is QAT cost justified over mixed-precision PTQ?

B Deep technical explanation

Mechanism & data flow

Post-training quantization (PTQ) takes a pretrained checkpoint and selects scales/zero points using weight statistics and optionally representative activation traces; deployment runs a quantized/fused graph. In quantization-aware training (QAT), forward operations simulate low-precision rounding/clipping—often via fake-quant operations—while trainable parameters stay in higher precision. Straight-through estimators approximate gradients through discrete rounding. QAT can adapt weight distributions to the quantizer but needs training resources, data and careful verification.

Equations and assumptions

For symmetric per-channel weights W_c, s_c ≈ max|W_c|/(2^{b−1}−1). FakeQuant(W)=s·round(clip(W/s)). Straight-through gradient often approximates ∂FakeQuant/∂W as 1 within clipping range and 0 outside (variant-dependent).

Architecture alternatives

PTQ is cheaper and preferable if quality stays within tolerance; QAT can help aggressive low-bit deployment when data/compute are available. Weight-only and weight+activation PTQ have different calibration needs.

Implementation & instrumentation

Create a representative calibration set from production input distributions; compare per-channel vs per-group scales and quantization-aware finetune only for failing layers. Measure task-level effects, not just weight MSE.

Latency, memory, compute & cost

PTQ requires limited calibration time; QAT adds gradient storage, optimizer state and training cost. Total cost must include serving savings amortized over expected token volume.

Edge cases & failure modes

QAT does not magically restore all low-bit quality; train/serve kernel mismatch or nonrepresentative calibration remains harmful. Beware embedding/outlier layers and embedding-logit ties.

C Interview-ready spoken answer

“I start with PTQ because it avoids retraining. I calibrate scale choices on representative requests and run golden evaluations plus kernel benchmarks. If aggressive precision fails on sensitive tasks, I try per-channel/mixed precision or QAT using fake quantization and straight-through gradients, and only pay that training cost when serving savings justify it.”

D Follow-up pressure test

  1. How would you measure rounding error vs clipping error?
  2. Can you QAT from scratch or only after pretrained PTQ fails?
  3. How do you ensure the fake-quant graph matches production kernels?

E Production scenario — diagnose, mitigate, validate

Incident: A financial extraction model’s numeric correctness drops under INT4 PTQ. Analyze activation outliers and field-level errors; test BF16 exceptions, adjusted group size, then limited QAT if necessary.

Success metrics: Predefine extraction correctness and calibration slices, memory savings and p95 target; reject compression if regression exceeds bounds.

F Interview takeaways

  • PTQ calibrates after training.
  • QAT trains under quantization simulation.
  • Use task quality and deployment economics to choose.
LESSON 09 / 16

Continuous batching and request scheduling

Track changing membership, token budgets and fairness.

A Interviewer questions

  1. Why does static batch padding waste work for variable-length generations?
  2. Design an iteration-level scheduler with a max batched-token budget.
  3. What can starve when decode requests are always prioritized?

B Deep technical explanation

Mechanism & data flow

Static batching waits for all members and pads shorter requests; one long generation delays the entire group. Continuous or in-flight batching reevaluates admissions and completions at every scheduling iteration. New requests enter as capacity frees; finished or canceled sequences leave. The scheduler accounts for active KV blocks, prompt chunks, decode tokens and priority/fairness. A decode-first policy can stabilize existing streams while starving new prompts, so waiting-age limits or weighted fairness are needed. Correctness requires protecting each sequence’s mask, position offsets and KV block ownership.

Equations and assumptions

Iteration token budget: Σ_i decode_token_cost_i + Σ_j prefill_chunk_tokens_j ≤ scheduler_max_tokens. KV admissibility: Σ_requests (current_cached_tokens + reserved_growth) × bytes/token ≤ KV_budget (plus allocator slack).

Architecture alternatives

Static batching can be adequate for homogeneous offline workloads. Continuous batching excels for mixed latency-sensitive online traffic. Priority policies trade starvation risk and service tier isolation.

Implementation & instrumentation

Build a toy scheduler with waiting/running/finished queues; track request IDs, positions, EOS, cancellation, block allocation and preemption. Instrument requests/step, queue wait, preemptions and tokens/step.

Latency, memory, compute & cost

Increased concurrency improves weight reuse up to bandwidth/compute saturation but may increase memory pressure and per-user ITL. Throughput optimum rarely coincides with best solo latency.

Edge cases & failure modes

Blind first-come-first-served can cause head-of-line blocking; greedy decode-first can starve prefill; too-large batches cause KV OOM and thrashing.

C Interview-ready spoken answer

“Continuous batching changes batch membership at decode boundaries rather than waiting for a fixed batch to finish. It improves utilization on variable-length traffic, but the scheduler must budget both compute tokens and KV residency. I evaluate throughput together with queue wait, p99 ITL, fairness, cancellation and preemption.”

D Follow-up pressure test

  1. What happens after a user cancels mid-generation?
  2. How would you prevent one 100k-token prompt from monopolizing GPU time?
  3. How does token-based admission differ from request-count admission?

E Production scenario — diagnose, mitigate, validate

Incident: An inference node experiences high goodput but new users wait minutes. Trace waiting ages and decoder occupancy; add bounded prefills/priority aging and compare SLO by service class.

Success metrics: Admission and scheduling must maintain bounded queue wait, zero memory overcommit and no per-tenant starvation under burst tests.

F Interview takeaways

  • Schedule per iteration, not fixed batch completion.
  • Token budget and KV residency are separate limits.
  • Goodput without fairness is insufficient.
LESSON 10 / 16

Chunked prefill and prefill-decode disaggregation

Diagnose and isolate interference between long prompts and streaming tokens.

A Interviewer questions

  1. How does chunked prefill improve tail ITL in mixed workloads?
  2. What is transferred between prefill and decode workers in a disaggregated deployment?
  3. Under what conditions can disaggregation reduce performance?

B Deep technical explanation

Mechanism & data flow

A naive scheduler runs a long prefill operation before servicing decode streams, causing inter-token stalls. Chunked prefill partitions the prompt into sequential chunks and schedules bounded work between decode iterations; attention for each chunk accesses earlier cached chunks under correct causal masking. Prefill-decode (P/D) disaggregation uses separate worker pools: prefill workers build KV and first-token state, then move or expose KV to decode workers via connectors/network/storage. This permits independent resource profiles, routing and scheduling but adds KV transfer and orchestration overhead.

Equations and assumptions

Chunk budget: prefix = ceil(N / chunk_tokens) chunk operations; each chunk must attend causally to preceding K/V. Rough transfer bytes for disaggregation ≈ 2L·Hkv·Dh·N·kv_bytes (unless compression/shared prefix alters it). Total TTFT may include prefill+KV transfer+remote dispatch.

Architecture alternatives

Chunked prefill is simpler when same GPUs can handle both phases. Disaggregation is useful when phase interference dominates and infrastructure/network permits fast KV transfer. It is not inherently a throughput improvement; system shape matters.

Implementation & instrumentation

Test large/small chunk sizes, KV connector latency, flow control and retry idempotency; record per-stage TTFT and p99 ITL, transfer bytes/s and worker utilization.

Latency, memory, compute & cost

Too-small chunks add overhead; too-large chunks reintroduce stalls. Disaggregation may require high-bandwidth GPU networking and duplicated scheduler/worker capacity.

Edge cases & failure modes

KV transfer compatibility requires matching model version, dtype, cache layout and position metadata. vLLM documentation explicitly notes experimental disaggregated prefill and does not promise increased throughput.

C Interview-ready spoken answer

“Chunked prefill breaks a large prompt into scheduled pieces so ongoing decode streams are not starved. Disaggregation puts prefill and decode on separate workers and transfers KV between them, enabling independent TTFT and ITL tuning. I start with chunks when possible and consider separation only if tail interference justifies transfer and operations cost.”

D Follow-up pressure test

  1. Calculate transfer size for one 16k-token GQA prompt.
  2. How would a KV transfer failure be retried safely?
  3. Why might disaggregation improve p99 ITL but not tokens/sec?

E Production scenario — diagnose, mitigate, validate

Incident: Under mixed 2k–64k prompts, p99 ITL spikes coincide with long prefills. Trial chunked prefill at multiple budgets; if isolation remains insufficient, profile GPU-to-GPU transfer before P/D pools.

Success metrics: Validate p95 TTFT, p99 ITL, useful tokens/s, network utilization and graceful transfer failure under the same arrival trace.

F Interview takeaways

  • Chunking reduces scheduling interference.
  • Disaggregation requires moving KV, not just a text prompt.
  • Throughput improvements are not guaranteed.
LESSON 11 / 16

Speculative decoding: draft models, Medusa, EAGLE, N-grams

Explain exact verification, acceptance and when speculation is counterproductive.

A Interviewer questions

  1. How does draft-and-verify preserve a target model’s output distribution?
  2. Compare Medusa heads, EAGLE hidden-state proposals and N-gram drafting.
  3. What determines the break-even point for speculation?

B Deep technical explanation

Mechanism & data flow

Classic speculative decoding uses a cheaper draft model to propose K tokens autoregressively; a target model evaluates those positions together. Acceptance/rejection is computed from the draft and target conditional distributions, with a correction distribution after rejection; with correct sampling math, the final distribution matches the target. Greedy verification compares argmax paths rather than claiming stochastic exactness. Medusa adds candidate heads/tree proposals to a base model; EAGLE proposes in feature or hidden-state space; N-gram speculation uses matches in recent text or prompt history without a trained draft model. Real systems manage tree masks, cache rollback and acceptance stats.

Equations and assumptions

For conditional per-step acceptance aᵢ, expected accepted prefix length E[A]=Σ_{i=1}^K∏_{j=1}^i aⱼ. Speedup depends on target verification cost, draft cost, accepted tokens and batch/hardware occupancy; A is not the same as generated tokens per iteration (a correction/bonus token may be included).

Architecture alternatives

Model-based drafts work where a small model predicts target-compatible continuations; N-gram drafts help repetitive text/code. Medusa/EAGLE require supported heads/training and kernel integration. Speculation can lose at large batches or poor acceptance.

Implementation & instrumentation

Implement a reference verifier for tiny categorical distributions to test sampling parity statistically, log accepted/proposed ratio, time per verification, rollback and output token rate.

Latency, memory, compute & cost

Accepting multiple tokens per expensive target pass can reduce latency, but overhead and cache traffic may negate it. Report net p95 TPOT and dollar cost rather than “draft acceptance” alone.

Edge cases & failure modes

Using naive accept-on-top-1 in a stochastic sampler changes the target distribution. Failure to undo rejected tentative KV corrupts later output. Tree verification and sampler settings must match.

C Interview-ready spoken answer

“Speculation proposes several tokens cheaply and has the expensive target verify them in parallel. Correct rejection sampling can retain the target distribution; the gain is limited by draft overhead, acceptance and verification efficiency. Medusa, EAGLE and N-grams differ mainly in how candidates are generated. I judge them by end-to-end latency and parity, not proposal count.”

D Follow-up pressure test

  1. Why does N-gram speculation work well for repetitive repository code?
  2. Does a 90% acceptance rate imply a 10× speedup?
  3. How does temperature affect verification correctness?

E Production scenario — diagnose, mitigate, validate

Incident: Speculation speeds benchmark prompts but worsens chat p95. Segment acceptance by domain and sampling settings, compare draft GPU contention and target verification kernels, then dynamically disable speculation for low-yield workloads.

Success metrics: Quality parity/target-distribution validation, p95 TPOT gain and no higher OOM/rollback-error rate are mandatory.

F Interview takeaways

  • Propose, verify, accept/reject, correct.
  • Medusa/EAGLE/N-gram are proposal mechanisms.
  • Sampling parity and true serving cost matter.
LESSON 12 / 16

Tensor, pipeline and data parallelism

Distinguish memory sharding, execution scheduling and replica scaling.

A Interviewer questions

  1. What communication does tensor parallel attention/MLP introduce?
  2. Why does pipeline parallelism need microbatches to achieve utilization?
  3. Which parallelism technique actually increases serving replicas?

B Deep technical explanation

Mechanism & data flow

Tensor parallelism (TP) partitions matrix weight dimensions across GPUs. Column-parallel and row-parallel layers require all-gather or all-reduce at certain boundaries; each token crosses interconnect links. Pipeline parallelism (PP) assigns layer ranges to GPU stages; microbatching can overlap stages but incurs bubbles, activation transfers and stage imbalance. Data parallelism (DP) replicates model-serving workers so different requests run independently; load balancing chooses replicas, each requiring its own compatible weight and KV memory. Expert parallelism shards MoE experts and adds all-to-all routing as a separate consideration.

Equations and assumptions

Idealized TP per-GPU weight ≈ W/P, plus replication/comm buffers. PP bubble fraction for m microbatches across p identical stages ≈ (p−1)/(m+p−1) under a simple synchronous 1F1B-like timing model (not a universal serving formula). Aggregate replicas R ideally offer R×single-replica capacity only until upstream/shared bottlenecks intervene.

Architecture alternatives

TP is used when layers/weights do not fit, often within high-bandwidth NVLink; PP can fit deeper models across devices but may hurt small-batch latency; DP is simplest for scale-out when full replicas fit.

Implementation & instrumentation

Map weight shards and attention head ownership explicitly; test layer collectives, NCCL timeouts and network topology. Profile communication overlap and imbalanced GPU stages.

Latency, memory, compute & cost

Parallelism is not free: interconnect latency, KV partitioning, host synchronization and pipeline bubbles can outweigh compute savings. Model size and context determine the best mix.

Edge cases & failure modes

“Add GPUs = linear speedup” is invalid. Even if weights shard perfectly, embeddings, logits, KV metadata and buffers may not; per-request decode often suffers from collective latency.

C Interview-ready spoken answer

“I choose TP to split wide layers, PP to distribute depth, and DP to scale independent requests. TP adds collectives, PP adds bubbles and activation transfers, DP duplicates weights. I calculate fit and interconnect cost, then benchmark request-level latency and goodput on the topology actually deployed.”

D Follow-up pressure test

  1. Would you use TP=8 across slow Ethernet?
  2. How do you avoid pipeline bubbles with 1 request?
  3. Why might two DP replicas outperform one TP=2 instance for an 8B model?

E Production scenario — diagnose, mitigate, validate

Incident: A 70B model is moved to four GPUs but decode worsens. Inspect all-reduce traces, GPU synchronization, batch size and network topology; compare TP topology or PP layouts.

Success metrics: Require memory fit, target p95 TPOT and aggregate successful tokens/s with no collective failures at peak load.

F Interview takeaways

  • TP = tensor shards; PP = layer stages; DP = request replicas.
  • Communication and bubbles change end-user latency.
  • Hardware interconnect matters as much as FLOPs.

LESSON 16 / 16

Capacity planning, concurrency and inference cost

Build an admission and scale model with uncertainty and explicit SLO gates.

A Interviewer questions

  1. Estimate concurrency from 20 RPS and 3-second mean latency; what assumptions apply?
  2. Build a peak-load KV budget using token lengths rather than request count.
  3. How can autoscaling based only on GPU utilization fail?

B Deep technical explanation

Mechanism & data flow

Start with input/output token distributions, arrival rate by time, average and tail service time, allowed queue wait, model mixture and quality SLOs. Little’s law estimates average in-flight requests for a stable system. Translate active contexts into KV bytes and account for prefill workspace, weight residency and fragmentation. A queue dispatcher admits only requests that fit token/VRAM reservations; autoscaling watches outstanding work, goodput, latency and instance warm-up time, not just averaged GPU occupancy. Separate peak capacity from efficient average batch size.

Equations and assumptions

L = λW for stable long-run flow. Active KV bytes ≈ Σ_r 2·layers·kv_heads·head_dim·(input_r+generated_r)·bytes/value. Capacity tokens ≈ usable_KV_bytes / bytes_per_token. Cost/request ≈ GPU-instance-hours×$/hour / completed_successful_requests, plus API/network/ops.

Architecture alternatives

Queue vs reject decisions: bounded queue protects GPUs but increases TTFT, 429/load shedding preserves SLA for admitted traffic, autoscaling adds warm capacity after startup delay. Route simpler tasks to smaller models where eval proves adequacy.

Implementation & instrumentation

Load-test open-loop Poisson/bursty arrivals and length-heavy tails; log admission denials, wait ages, KV reserved/live tokens, TTFT/TPOT, output failures and replica spin-up. Deploy with canary and rollback thresholds.

Latency, memory, compute & cost

Nonlinearity matters: latency and memory explode near saturation. More decoding requests increase weight amortization but grow KV simultaneously. Plan safety margin against worst expected percentile, not just mean.

Edge cases & failure modes

Linear extrapolation from a batch=1 benchmark fails under mixed prefill. Percentile SLOs cannot be deduced from averages. Do not invent latency numbers without hardware profiling.

C Interview-ready spoken answer

“I derive concurrency from arrival rate and response time, then translate live token distributions into KV memory and compute demand. I benchmark an offered-load curve and pick the largest SLO-compliant goodput, including headroom for bursts and instance warm-up. Admission, priority scheduling, fallback and rollback complete the design.”

  1. What happens to queue wait when offered load exceeds serving capacity?
  2. How would you choose max batched tokens for 95% short prompts and 5% long prompts?
  3. What do you do when the largest single prompt cannot fit?

Success metrics: Zero OOM at expected peak mix and agreed p95 TTFT/p99 ITL with cost per SLO-compliant request reported.

F Interview takeaways

  • Little’s law needs stable throughput, not a magic capacity formula.
  • Reserve against active tokens and growth.
  • Goodput and tail SLO are scaling targets.

module7_inference_reference.py · Python 3 · optional PyTorch
"""Module 7: LLM Inference, Performance & Infrastructure — CPU-friendly reference.

Run: python module7_inference_reference.py
Optional: pip install torch  (enables the tiny causal KV-cache parity test).
Educational estimators and simulations; no GPU speed measurements or speedup claims.
"""
from __future__ import annotations
from dataclasses import dataclass
from math import ceil, exp
import unittest

GIB = 1024 ** 3


def weight_gib(params: int, bits: float, metadata_fraction: float = 0.0) -> float:
    """Ideal nominal packed weights + caller-specified metadata/scale overhead."""
    assert params > 0 and 0 < bits <= 64 and metadata_fraction >= 0
    return params * bits / 8 * (1 + metadata_fraction) / GIB


def kv_gib(*, layers: int, kv_heads: int, head_dim: int,
           active_tokens: int, bytes_per_scalar: float = 2) -> float:
    """Aggregated attention KV storage across all live sequences; excludes allocator overhead."""
    assert min(layers, kv_heads, head_dim) > 0 and active_tokens >= 0 and bytes_per_scalar > 0
    return 2 * layers * kv_heads * head_dim * active_tokens * bytes_per_scalar / GIB


def causal_attention_pairs(n: int) -> int:
    assert n >= 0
    return n * (n + 1) // 2


def roofline_seconds(flops: float, hbm_bytes: float,
                     effective_flops_per_s: float, effective_bytes_per_s: float) -> float:
    """Lower-bound style estimate: assumes perfect overlap of compute and memory traffic."""
    assert min(effective_flops_per_s, effective_bytes_per_s) > 0
    return max(flops / effective_flops_per_s, hbm_bytes / effective_bytes_per_s)


def decode_bw_upper_bound_tokens_s(model_weight_bytes: float,
                                   hbm_bytes_per_s: float,
                                   cache_bytes_per_step: float = 0.0) -> float:
    """Optimistic B=1 upper bound, assuming weights and cache read once per token."""
    assert model_weight_bytes > 0 and hbm_bytes_per_s > 0 and cache_bytes_per_step >= 0
    return hbm_bytes_per_s / (model_weight_bytes + cache_bytes_per_step)


def quantize_symmetric_int8(values: list[float]) -> tuple[list[int], float]:
    """Per-tensor symmetric PTQ toy; not production calibrations or packing."""
    maxabs = max([abs(v) for v in values], default=0.0)
    scale = maxabs / 127.0 if maxabs else 1.0
    return [max(-127, min(127, round(x / scale))) for x in values], scale


def dequantize(q: list[int], scale: float) -> list[float]:
    return [x * scale for x in q]


@dataclass(frozen=True)
class Request:
    name: str
    prompt_tokens: int
    max_new_tokens: int
    generated: int = 0
    prefilled: int = 0

    def __post_init__(self):
        assert self.prompt_tokens > 0 and self.max_new_tokens > 0
        assert 0 <= self.generated <= self.max_new_tokens
        assert 0 <= self.prefilled <= self.prompt_tokens


class TokenBudgetScheduler:
    """Toy chunked-prefill + one-token decode scheduler. NOT a serving engine.

    A step spends up to `token_budget` tokens across currently active requests.
    Prioritizes existing decoding sequences to protect inter-token latency,
    then prefills queued requests in chunks. No real GPU parallelism modeled.
    """
    def __init__(self, token_budget: int, max_active_tokens: int):
        assert token_budget > 0 and max_active_tokens > 0
        self.token_budget = token_budget
        self.max_active_tokens = max_active_tokens
        self.requests: list[Request] = []

    def admit(self, request: Request) -> bool:
        reserved = sum(r.prompt_tokens + r.max_new_tokens for r in self.requests)
        if reserved + request.prompt_tokens + request.max_new_tokens > self.max_active_tokens:
            return False
        self.requests.append(request)
        return True

    def step(self) -> list[str]:
        from dataclasses import replace
        remaining = self.token_budget
        events = []
        new_requests = []
        for r in self.requests:
            if r.prefilled == r.prompt_tokens and r.generated < r.max_new_tokens and remaining:
                r = replace(r, generated=r.generated + 1)
                remaining -= 1
                events.append(f'{r.name}: decoded token {r.generated}')
            new_requests.append(r)
        self.requests = new_requests
        new_requests = []
        for r in self.requests:
            if r.prefilled < r.prompt_tokens and remaining:
                take = min(remaining, r.prompt_tokens - r.prefilled)
                r = replace(r, prefilled=r.prefilled + take)
                remaining -= take
                events.append(f'{r.name}: prefilled {take} tokens')
            new_requests.append(r)
        self.requests = [r for r in new_requests if r.generated < r.max_new_tokens]
        return events


def speculative_expected_accepted(draft_probs: list[float]) -> float:
    """Expected verified accepted draft prefix length, for conditional acceptance probs.

    E[# accepted] = sum_{i=1}^K product_{j=1}^i a_j. The output excludes the
    target's correction/bonus token. Independence is NOT required if each a_i
    is explicitly conditional on all earlier drafts having been accepted.
    """
    survival = 1.0
    total = 0.0
    for p in draft_probs:
        assert 0 <= p <= 1
        survival *= p
        total += survival
    return total


def little_law_concurrency(arrival_rps: float, mean_latency_s: float) -> float:
    """Steady state average in-flight requests L = arrival rate * response time."""
    assert arrival_rps >= 0 and mean_latency_s >= 0
    return arrival_rps * mean_latency_s


def cost_per_million_tokens(instance_cost_per_hour: float, useful_tokens_per_s: float) -> float:
    """Amortized compute-only cost; excludes egress, idle overhead and engineering."""
    assert instance_cost_per_hour >= 0 and useful_tokens_per_s > 0
    return instance_cost_per_hour / (useful_tokens_per_s * 3600) * 1e6


def optional_torch_kv_parity_test():
    """Compare causal full-sequence attention against cached token-by-token decode.

    Single head, fixed projections, no positions/dropout, CPU and fp32 for parity.
    """
    try:
        import torch
    except ImportError:
        print('PyTorch not installed: optional KV parity demonstration skipped.')
        return
    torch.manual_seed(3)
    x = torch.randn(1, 7, 12)
    wq, wk, wv = [torch.randn(12, 12) / 12**0.5 for _ in range(3)]
    q, k, v = x @ wq, x @ wk, x @ wv
    logits = (q @ k.transpose(-1, -2)) / 12**0.5
    positions = torch.arange(x.shape[1])
    forbidden = positions[None, :] > positions[:, None]
    logits = logits.masked_fill(forbidden, -float('inf'))
    full = torch.softmax(logits, dim=-1) @ v
    ks, vs, outputs = [], [], []
    for t in range(x.shape[1]):
        ks.append(k[:, t:t+1])
        vs.append(v[:, t:t+1])
        kt, vt = torch.cat(ks, dim=1), torch.cat(vs, dim=1)
        logits_t = (q[:, t:t+1] @ kt.transpose(-1, -2)) / 12**0.5
        outputs.append(torch.softmax(logits_t, dim=-1) @ vt)
    cached = torch.cat(outputs, dim=1)
    assert torch.allclose(full, cached, atol=1e-5), (full - cached).abs().max()
    print('PyTorch: causal attention / cached decode parity passed.')
