What is an AI agent, and how does it differ from a simple LLM call?

Mechanism · architecture · math · failure controls · validation.

A Interviewer questions

  1. Trace a request from user goal through model, tool, observation and final state.
  2. When is an agent unnecessary?
  3. What must remain deterministic outside the model?
  4. How would you prove the improvement on a reproducible evaluation suite without inventing benchmark gains?

B Deep technical explanation

1 · Step-by-step internal flow and observable state

An agent is a closed-loop controller over an environment: a runtime assembles goal and state; an LLM proposes a response or typed action; a policy gateway validates tool, arguments and caller permissions; an executor performs the operation; an observation is recorded; the loop repeats until a verifiable terminal condition or budget stop. One model completion without observation/action feedback is a workflow step, not a full autonomous tool-use loop.

2 · Equations, bounds, symbols & assumptions

Model as partially observable decision process with state s_t, observation o_t, action a_t and transition P(s_{t+1}|s_t,a_t). Practical tool agent is a bounded approximation, not necessarily an RL policy. Total cost C=Σ_t(C_model,t+C_tool,t); retries and dependent steps compound delay.

3 · Alternative architectures and decision criteria

Use a direct LLM call for extraction/summarization; deterministic pipeline for known steps; agent loop when the next action depends on evidence not known up front. An agent is not inherently more accurate.

4 · Production implementation, schemas & instrumentation

Store objective, approved tool list, principal, budgets, message/observation ledger and terminal validator separately. Tool side effects happen only in host application, not because model emitted text.

5 · Token, latency, memory, compute & scaling consequences

Latency increases with sequential LLM/tool round trips, token replays and queueing. Measure per-run success, steps, cost, side-effect errors and p95 latency.

6 · Edge cases, misconceptions, failure & mitigation

Infinite loops, hallucinated tools, unwanted actions, stale observations and prompt injections are dominant risks. Bounded loops, scoped credentials and fail-closed execution mitigate them.

“An agent is a closed-loop controller over an environment: a runtime assembles goal and state; an LLM proposes a response or typed action; a policy gateway validates tool, arguments and caller permissions; an executor performs the operation; an observation is recorded; the loop repeats until a verifiable terminal condition or budget stop. Use a direct LLM call for extraction/summarization; deterministic pipeline for known steps; agent loop when the next action depends on evidence not known up front. Infinite loops, hallucinated tools, unwanted actions, stale observations and prompt injections are dominant risks. I would instrument the full run and verify the result using replay a permission-stratified task set; require zero unauthorized side effects, measurable task completion, bounded p95 duration and approved-output fidelity.”

D Follow-up pressure tests

  2. Compute a bound or resource trade-off from explicit assumptions: Model as partially observable decision process with state s_t, observation o_t, action a_t and transition P(s_{t+1}|s_t,a_t).
  3. What is your rollback / recovery sequence after an ambiguous external side effect? What telemetry distinguishes the hypotheses?

A strong response must demonstrate: precise data flow; agent/model/executor trust boundaries; estimates with assumptions; failure classification; measurable experiments rather than unsupported optimism. Do not confuse a code schema with permissions or checkpointing with exactly-once side effects.

E Production scenario · instrument → diagnose → repair → verify

Incident: An invoice assistant emails a payment request without checking billing records. Separate the model-generated intent from authorized send action; enforce invoice lookup and human approval before dispatch.

AI Agent Memory

Mechanism · architecture · math · failure controls · validation.

A Interviewer questions

  1. Design short- and long-term memory for a multi-tenant agent.
  2. How can memory make performance worse?
  3. How do you support right-to-delete and corrections?
  4. How would you prove the improvement on a reproducible evaluation suite without inventing benchmark gains?

B Deep technical explanation

1 · Step-by-step internal flow and observable state

Agent memory exists in at least four layers: working context for current reasoning, checkpointed task/conversation state, persistent user/project facts and historical episode records. A retrieval policy selects memory based on relevance, freshness, source and authorization; a write policy determines what may become durable.

2 · Equations, bounds, symbols & assumptions

One retrieval objective: score(m,q)=α·relevance(m,q)+β·recency(m)+γ·confidence(m)−δ·privacyRisk(m). Weights are policy parameters, not model-internal constants. Memory precision and stale-memory rate matter more than raw stored fact count.

3 · Alternative architectures and decision criteria

Window summaries are cheap; structured database state fits transactional tasks; vector memory enables semantic recall; graph memory tracks relations. Do not conflate a KV cache with persistent agent memory.

4 · Production implementation, schemas & instrumentation

Memory record: {tenant,principal,kind,source,created_at,expires_at,confidence,version,content}. Permission checks apply at retrieval and writes; add deletion, provenance and conflict resolution.

5 · Token, latency, memory, compute & scaling consequences

Cross-session search adds retrieval latency and storage; repeated embedding and unbounded history raise cost. Cache stable summaries but invalidate on edits and ACL changes.

6 · Edge cases, misconceptions, failure & mitigation

Confident false memories, cross-user leakage, forgotten corrections and polluted episodic logs cause failures. Verify consequential memories against authoritative sources before acting.

Harness Engineering in AI

Mechanism · architecture · math · failure controls · validation.

A Interviewer questions

  1. Draw the minimum harness around an LLM to edit files safely.
  2. Which correctness properties must be independent of model obedience?
  3. How do you evaluate harness improvements without model confounding?
  4. How would you prove the improvement on a reproducible evaluation suite without inventing benchmark gains?

B Deep technical explanation

1 · Step-by-step internal flow and observable state

A harness is all non-weight software surrounding the model: prompt/context assembly, tool catalog and dispatcher, state machine, checkpoints, permission enforcement, sandboxing, failure recovery, observability, verification and evaluation. The model proposes; the harness turns proposals into safe, reproducible actions.

2 · Equations, bounds, symbols & assumptions

End-to-end reliability is limited by product of conditional stage success probabilities under an independence approximation: P(success)≈∏_i p_i. Actual stages are dependent, so use traced end-to-end tests.

3 · Alternative architectures and decision criteria

A thin harness improves speed for narrow read-only tasks; a durable policy-rich harness is needed for side-effecting, long-running enterprise agents. Avoid adding orchestration layers that do not remove a measured failure.

4 · Production implementation, schemas & instrumentation

Wrap every tool with typed validation, explicit principal, deadline, idempotency key, structured result, replay log and risk-based approval. Persist commit status independently from LLM messages.

5 · Token, latency, memory, compute & scaling consequences

Harness overhead increases initial complexity, but can reduce destructive incidents and retry waste. Budget queueing, serialization and sandbox startup, not only model latency.

6 · Edge cases, misconceptions, failure & mitigation

A clever system prompt cannot replace authorization, idempotency or rollback. Side-effect replay after crash is a classic harness defect.

LESSON 05 / 54 · INTERVIEW ENGINEERING

Explain the ReAct (Reasoning + Acting) agent architecture.

Mechanism · architecture · math · failure controls · validation.

A Interviewer questions

  1. Walk through a three-step ReAct trace with actual observations.
  2. Why might ReAct perform worse than fixed chains?
  3. How would you detect no progress?
  4. How would you prove the improvement on a reproducible evaluation suite without inventing benchmark gains?

B Deep technical explanation

1 · Step-by-step internal flow and observable state

ReAct alternates language-model deliberation with actions and external observations: goal → proposed tool call → execution → observation → updated choice. Modern systems usually encode actions as structured tool calls rather than parsing fragile textual “Action:” lines. Observations are untrusted data and are appended only after validation.

2 · Equations, bounds, symbols & assumptions

At each step choose a_t ~ π(a|goal,history_t); history_{t+1}=history_t⊕observation(tool(a_t)). Terminate on final answer validated, no useful action, error, time, steps or cost cap.

3 · Alternative architectures and decision criteria

from __future__ import annotations
from dataclasses import dataclass, field
from typing import Any, Callable
from hashlib import sha256
import json
import unittest


class AgentError(Exception):
    pass


@dataclass(frozen=True)
class Identity:
    tenant: str
    user: str
    allowed_tools: frozenset[str]


@dataclass(frozen=True)
class Tool:
    name: str
    mutating: bool
    required: frozenset[str]
    executor: Callable[[dict[str, Any]], dict[str, Any]]


def canonical_hash(value: Any) -> str:
    return sha256(json.dumps(value, sort_keys=True, separators=(',', ':'),
                             ensure_ascii=False).encode('utf-8')).hexdigest()


@dataclass
class Budget:
    capacity: int
    spent: int = 0
    reservations: dict[str, int] = field(default_factory=dict)

    @property
    def available(self) -> int:
        return self.capacity - self.spent - sum(self.reservations.values())

    def reserve(self, call_id: str, amount: int) -> None:
        if amount < 0 or call_id in self.reservations or amount > self.available:
            raise AgentError('BUDGET_DENIED')
        self.reservations[call_id] = amount

    def settle(self, call_id: str, actual: int) -> None:
        reserved = self.reservations[call_id]
        if actual < 0 or actual > reserved:
            raise AgentError('BAD_USAGE')
        self.reservations.pop(call_id)
        self.spent += actual


@dataclass
class EffectLedger:
    committed: dict[str, dict[str, Any]] = field(default_factory=dict)

    def execute_once(self, effect_id: str, fn: Callable[[], dict[str, Any]]) -> dict[str, Any]:
        if effect_id not in self.committed:
            self.committed[effect_id] = fn()
        return self.committed[effect_id]


@dataclass(frozen=True)
class Approval:
    owner: str
    action_hash: str
    expires_at: int


def approval_for(user: str, tool: str, args: dict[str, Any], version: int,
                 expires_at: int) -> Approval:
    return Approval(user, canonical_hash([tool, args, version]), expires_at)


def check_approval(approval: Approval | None, user: str, tool: str,
                   args: dict[str, Any], version: int, now: int) -> bool:
    return bool(approval and approval.owner == user and approval.expires_at >= now
                and approval.action_hash == canonical_hash([tool, args, version]))


class Harness:
    """Host-side policy gate; caller's principal is never supplied by model arguments."""
    def __init__(self, tools: list[Tool], ledger: EffectLedger | None = None):
        self.tools = {t.name: t for t in tools}
        self.ledger = ledger or EffectLedger()

    def run_tool(self, who: Identity, tool_name: str, args: dict[str, Any],
                 *, effect_id: str | None = None, approval: Approval | None = None,
                 version: int = 1, now: int = 0) -> dict[str, Any]:
        tool = self.tools.get(tool_name)
        if tool is None or tool_name not in who.allowed_tools:
            raise AgentError('TOOL_DENIED')
        if set(args) != set(tool.required):
            raise AgentError('SCHEMA_DENIED')
        # All domain tools in this example take a tenant key; bind it from the host.
        if args.get('tenant') != who.tenant:
            raise AgentError('TENANT_DENIED')
        if tool.mutating:
            if not effect_id or not check_approval(approval, who.user, tool_name,
                                                    args, version, now):
                raise AgentError('APPROVAL_DENIED')
            return self.ledger.execute_once(effect_id, lambda: tool.executor(args))
        return tool.executor(args)


@dataclass
class AgentState:
    run_id: str
    phase: str = 'PREPARE'
    steps: int = 0
    max_steps: int = 4
    trace: list[str] = field(default_factory=list)
    terminal: bool = False

    def progress(self, action: str, new_evidence: bool = True) -> None:
        if self.terminal or self.steps >= self.max_steps:
            self.terminal = True
            raise AgentError('STEP_LIMIT_OR_TERMINATED')
        self.steps += 1
        self.phase = 'OBSERVE' if new_evidence else 'STAGNANT'
        self.trace.append(action)
        if not new_evidence or self.steps >= self.max_steps:
            self.terminal = True
            self.phase = 'TERMINATE'


def should_retry(code: str) -> bool:
    return code in {'TIMEOUT_READ', 'RATE_LIMIT', 'TRANSIENT_503'}


def choose_memory(records: list[dict[str, Any]], tenant: str, now: int) -> list[str]:
    return [r['fact'] for r in records if r['tenant'] == tenant
            and r['expires'] >= now and r['verified']]


def event_once(event_id: str, seen: set[str]) -> bool:
    if event_id in seen:
        return False
    seen.add(event_id)
    return True


def task_success_rate(outcomes: list[bool]) -> float:
    return sum(outcomes) / len(outcomes) if outcomes else 0.0


def critical_path_ms(durations: dict[str, int], dependencies: dict[str, list[str]]) -> int:
    cache: dict[str, int] = {}
    visiting: set[str] = set()

    def finish(name: str) -> int:
        if name in visiting:
            raise AgentError('GRAPH_CYCLE')
        if name in cache:
            return cache[name]
        visiting.add(name)
        if name not in durations:
            raise AgentError('UNKNOWN_NODE')
        val = durations[name] + max((finish(d) for d in dependencies.get(name, [])),
                                    default=0)
        visiting.remove(name)
        cache[name] = val
        return val

    return max((finish(node) for node in durations), default=0)
