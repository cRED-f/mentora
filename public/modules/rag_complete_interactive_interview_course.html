What is Retrieval-Augmented Generation (RAG), and why is it important?

Mechanism → proof → architecture → debugging → measurable decisions.

A Interviewer questions

  1. Describe the two independent pipelines of a production RAG system.
  2. When can a correct retriever still produce a wrong answer?
  3. When is RAG the wrong choice despite poor model knowledge?

B Deep technical explanation

1 · Step-by-step mechanism / data flow

A RAG answer is conditioned on an external, versioned corpus: ingest authorized documents, extract structured content, index searchable units, turn the user question into one or more queries, retrieve and optionally rerank permitted evidence, assemble a bounded context, and generate an answer with source identifiers. Retrieval extends the model’s available evidence without updating weights. The LLM is still probabilistic and may ignore or misread correct evidence.

2 · Equations, symbols and invariants

P(a|q,D)≈Σ_{z∈TopK(q,D)}P_η(z|q,D)P_θ(a|q,z). This is the classic latent-document intuition, not the exact formula for every modern prompt-assembled RAG system. η is retrieval, θ generation; retrieval recall upper-bounds document-grounded answerability.

3 · Architecture, options and when they win

Use a small exact SQL query for structured facts, full-context reading for small stable sources, RAG for large/frequently updated corpora, and fine-tuning for behavior/style. The alternatives solve different bottlenecks.

4 · Implementation, APIs and instrumentation

Represent evidence as (tenant, doc_id, version, chunk_id, page, offsets, modality, permissions, body, checksum); trace query→filters→candidate IDs→rerank→prompt→claims. Return no-supported-answer when evidence is inadequate.

5 · Latency, compute, memory, cost and scaling

Cost includes ingestion + index footprint + embedding jobs, query retrieval, optional reranker and generated tokens. Retrieval can reduce prompt size, but tool calls and multi-stage reranking add latency.

6 · Edge cases, misconceptions and mitigation

RAG is not a guarantee of truth, freshness or authorization. If chunks are wrong, filters leak, or synthesis is unsupported, the result fails even when the embedding score is high.

C Interview-ready spoken answer

“RAG separates evidence acquisition from synthesis. I ingest versioned, permissioned documents, retrieve and rerank relevant passages, then require grounded answers with traceable citations. I evaluate retrieval and generation separately; a higher similarity score is not proof of correctness.”

D Follow-up pressure test

  1. Where does authorization belong relative to ANN search?
  2. How would you estimate the upper bound from retrieval recall?
  3. Which artifacts are required to reproduce a wrong answer?

Strong response must show: typed boundaries, evidence IDs, a reproducible trace, stated assumptions, complexity or resource math, and an explicit measurable test. Unsupported “we improved quality” claims do not count.

E Production scenario · investigate → repair → validate

Incident and diagnosis: A support assistant invents a refund date. Compare retrieval evidence with source policy version, inspect prompt context, and label the defect as missing evidence vs generation misinterpretation before changing architecture.

Instrumentation: Trace request ID, principal and ACL revision, source and index generation, relevant candidate ranks, evidence spans, prompt context IDs, response claims, stage timings and error classes. Validate first failing stage against a gold example.

Options and trade-offs: Use a small exact SQL query for structured facts, full-context reading for small stable sources, RAG for large/frequently updated corpora, and fine-tuning for behavior/style. The alternatives solve different bottlenecks. Cost implications: Cost includes ingestion + index footprint + embedding jobs, query retrieval, optional reranker and generated tokens. Retrieval can reduce prompt size, but tool calls and multi-stage reranking add latency.

Acceptance and rollback: Prove grounded answer accuracy, citation support, retrieval recall@k, abstention correctness, and p95 latency on a permission-stratified gold set. Measure before/after on identical cases, include adversarial and user-segment slices, set severity gates before deployment, canary, then rollback on regressions. No illustrative values are represented as real outcomes.

F Interview takeaways

  • A RAG answer is conditioned on an external, versioned corpus: ingest authorized documents, extract structured content, index searchable units, turn the user question into one or more queries, retrieve and optionally rerank permitted evidence, assemble a bounded context, and generate an answer with source identifiers.

  • RAG is not a guarantee of truth, freshness or authorization.
  • Separate retrieval quality from final grounded task success; never substitute model confidence for authorization.

Explain the architecture of a basic RAG system.

Mechanism → proof → architecture → debugging → measurable decisions.

A Interviewer questions

  1. Design separate ingest and query paths with an atomic cutover.
  2. Which operations can run concurrently on the request path?
  3. What can be rolled back independently of the model?

B Deep technical explanation

1 · Step-by-step mechanism / data flow

Offline path: file/source connector → parser/OCR/table extraction → normalization → hierarchical chunks → embeddings and lexical index → metadata/ACL snapshot → atomic publish. Online path: authenticated request → rewrite/decompose → ACL-filtered BM25 and ANN → fusion → rerank → deduplicate → context pack → grounded generation → citation validation. Keep online and offline independently scalable.

2 · Equations, symbols and invariants

Approximate critical-path latency L≈L_auth+L_query+max(L_lexical,L_dense)+L_fusion+L_rerank+L_prompt+L_model; stage overlap and queueing alter the actual result. Ingest SLA is measured separately as source-commit→searchable.

3 · Architecture, options and when they win

Simple FAQ can omit rewriting/rerank; difficult enterprise evidence benefits from hybrid retrieval and a reranker. Agent orchestration is optional, not the default architecture.

4 · Implementation, APIs and instrumentation

Maintain transactional publication pointers to an index generation. Query only generation IDs marked ready; preserve access controls through all fanouts and cache keys. Log stage durations and retrieved version IDs.

5 · Latency, compute, memory, cost and scaling

Use asynchronous concurrent retrieval branches and bounded candidate pools; avoid invoking an LLM before cheaper exact match or caching paths when they suffice.

6 · Edge cases, misconceptions and mitigation

A partial reindex can mix old/new chunks; prompt templates can lose offsets; vector-store post-filtering may return too few permitted hits. Validate promotion and per-user access.

What are chunking strategies, and how do you choose the right chunk size?

Mechanism → proof → architecture → debugging → measurable decisions.

A Interviewer questions

  1. Why might 512 tokens outperform 128 for policy QA?
  2. How would you tune overlap without inflating duplicates?
  3. What test detects evidence split across chunk boundaries?

B Deep technical explanation

1 · Step-by-step mechanism / data flow

Chunking determines both retrieval granularity and answer completeness. A segmentation job first preserves semantic boundaries (section, paragraph, table, code block), then enforces token budgets; each unit stores location, heading path, token count, parent ID and ACL lineage. Tune chunk length and overlap using the query distribution, not a magic number.

2 · Equations, symbols and invariants

With document length T, chunk size c, overlap o and stride s=c−o>0, rough count n≈max(1,ceil((T−o)/(c−o))). Storage inflation is approximately c/(c−o) for long text; this ignores boundary adjustments and metadata.

3 · Architecture, options and when they win

Small chunks increase precise matching but lose nearby definitions. Large chunks preserve evidence but increase distractors/cost. Parent-child retrieval gives small search targets and larger answer context.

4 · Implementation, APIs and instrumentation

Segment with tokenizer-aware, layout-aware parsing. Evaluate c∈{128,256,512,1024} as illustrative candidates, overlap and parent expansion on a frozen dataset with entity and table boundary cases.

5 · Latency, compute, memory, cost and scaling

More chunks grow ANN records and embedding bill; overlap duplicates candidate hits; larger retrieved chunks increase prefill tokens and can impair context utilization.

6 · Edge cases, misconceptions and mitigation

Blind fixed windows split footnotes, headers, tables and equations. Ensure a section heading is retained in context metadata, not blindly repeated into the entire text.

Compare fixed-size chunking, semantic chunking, and recursive chunking.

Mechanism → proof → architecture → debugging → measurable decisions.

A Interviewer questions

  1. Explain why semantic chunking may be worse on tabular PDFs.
  2. How would you make the comparison fair?
  3. When would a fixed-size baseline be sufficient?

B Deep technical explanation

1 · Step-by-step mechanism / data flow

Fixed-size token windows cut predictably; recursive chunking respects a hierarchy of separators before falling back to token breaks; semantic chunking detects topic changes using embeddings, boundaries or discourse structure. Semantic segmentation itself can be brittle when text has domain jargon, templates or short headings.

2 · Equations, symbols and invariants

For semantic adjacent sentences u_i,u_{i+1}, boundary candidate when 1−cos(e_i,e_{i+1})>τ. Threshold is corpus-dependent; the embedding similarity is not a universal discourse-break oracle.

3 · Architecture, options and when they win

Use recursive/layout-aware as a robust baseline. Semantic chunking makes sense when semantic units vary substantially and quality gain justifies preprocessing. Fixed-size windows work well for homogeneous raw text.

4 · Implementation, APIs and instrumentation

Preserve parent document and source offsets. Build three indexes with the same embedding model/retriever, hold total retrieval budget constant, and compare equivalent gold queries.

5 · Latency, compute, memory, cost and scaling

Semantic chunking adds embedding/segmentation compute at ingest; fixed-size creates more fragments near separators; recursive strategies vary output sizes.

6 · Edge cases, misconceptions and mitigation

Paragraph boundaries do not equal facts; semantic boundaries can orphan table headers and captions. Do not report improved relevance without query-level testing.

from __future__ import annotations
from collections import Counter
from dataclasses import dataclass
from math import log, sqrt
from typing import Sequence
import unittest

@dataclass(frozen=True)
class Chunk:
    doc_id: str
    version: int
    chunk_id: str
    text: str
    tenant: str
    groups: frozenset[str]
    effective_from: int
    effective_to: int | None = None

@dataclass(frozen=True)
class Principal:
    tenant: str
    groups: frozenset[str]


def allowed(chunk: Chunk, principal: Principal, at: int) -> bool:
    """Mandatory permission gate: NEVER ask a model to grant access."""
    return (chunk.tenant == principal.tenant and
            bool(chunk.groups & principal.groups) and
            chunk.effective_from <= at and
            (chunk.effective_to is None or at < chunk.effective_to))


def tokenize(text: str) -> list[str]:
    return text.lower().split()  # Toy tokenizer, replace for production.


def bm25_scores(query: str, docs: Sequence[Chunk], k1: float = 1.2,
                b: float = 0.75) -> dict[str, float]:
    """Small corpus BM25 implementation; relies on unique chunk_id values."""
    if not docs: return {}
    tokens = [tokenize(d.text) for d in docs]
    lengths = [len(t) for t in tokens]
    avgdl = sum(lengths)/len(lengths)
    n = len(docs)
    df = Counter(w for t in tokens for w in set(t))
    scores = {}
    for d,t,length in zip(docs,tokens,lengths):
        tf = Counter(t)
        value = 0.0
        for w in set(tokenize(query)):
            if not tf[w]: continue
            idf = log(1 + (n-df[w]+.5)/(df[w]+.5))
            value += idf * tf[w]*(k1+1)/(tf[w]+k1*(1-b+b*length/max(avgdl,1)))
        scores[d.chunk_id] = value
    return scores


def cosine(a: Sequence[float], b: Sequence[float]) -> float:
    if len(a) != len(b) or not a: raise ValueError('dimension mismatch')
    denom = sqrt(sum(x*x for x in a))*sqrt(sum(y*y for y in b))
    return sum(x*y for x,y in zip(a,b))/denom if denom else 0.0


def rrf(rankings: Sequence[Sequence[str]], k0: int = 60) -> list[tuple[str,float]]:
    scores: dict[str,float] = {}
    for ranking in rankings:
        for rank, document in enumerate(dict.fromkeys(ranking), 1):
            scores[document] = scores.get(document,0)+1/(k0+rank)
    return sorted(scores.items(), key=lambda pair:(-pair[1],pair[0]))


def colbert_maxsim(query_vectors: Sequence[Sequence[float]],
                   doc_vectors: Sequence[Sequence[float]]) -> float:
    if not query_vectors or not doc_vectors: return 0.0
    return sum(max(sum(x*y for x,y in zip(q,d)) for d in doc_vectors)
               for q in query_vectors)


def recall_at_k(ranked_ids: Sequence[str], relevant: set[str], k: int) -> float:
    return len(set(ranked_ids[:k]) & relevant)/len(relevant) if relevant else 0.0


def precision_at_k(ranked_ids: Sequence[str], relevant: set[str], k: int) -> float:
    return len(set(ranked_ids[:k]) & relevant)/k if k>0 else 0.0


def mrr(ranked_lists: Sequence[Sequence[str]], relevant: Sequence[set[str]]) -> float:
    assert len(ranked_lists)==len(relevant)
    if not ranked_lists: return 0.0
    values=[]
    for ranking, gold in zip(ranked_lists,relevant):
        next_rank=next((i for i,x in enumerate(ranking,1) if x in gold),None)
        values.append(1/next_rank if next_rank else 0.0)
    return sum(values)/len(values)


def ndcg_at_k(relevances: Sequence[int], k: int) -> float:
    def dcg(seq):return sum((2**r-1)/log(i+2,2) for i,r in enumerate(seq))
    actual=dcg(relevances[:k])
    ideal=dcg(sorted(relevances,reverse=True)[:k])
    return actual/ideal if ideal else 0.0


def kv_bytes(layers:int, heads:int, head_dim:int, tokens:int,
             batches:int, bytes_per: int) -> int:
    """K+V elements across active requests, excluding allocator metadata."""
    return 2*layers*heads*head_dim*tokens*batches*bytes_per

    """Keep distinct document-version chunks; do not merge across versions."""
    by_key={}
    for c in chunks:
