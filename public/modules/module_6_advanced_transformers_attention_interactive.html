LESSON 01 / 14
Dense vs. sparse Transformer architectures
Separate sparse parameter activation from sparse token-to-token attention.


A Interviewer questions
  1. Can a Transformer be sparse in its MLP but dense in its attention?
  2. What is actually reduced by top-k experts: resident weight bytes, multiply-adds or both?
  3. Under what hardware conditions can a nominally cheaper sparse model be slower?


B Deep technical explanation
Mechanism & data flow
The decoder block contains attention, an MLP and norms. A dense FFN computes every weight for every token. In sparse MoE, a lightweight gate chooses a subset of multiple FFN experts per token while the attention block may remain dense across all valid tokens. Separately, sparse attention limits which token pairs can interact. These are orthogonal optimizations. Router scores are usually computed from each token hidden state; selected FFNs run, their outputs combine, and residual connections pass the result to the next layer. Train/inference dispatch may need token regrouping by expert.
Algorithms and mathematics
For N tokens, d hidden, E FFNs, top-k experts, expert FFN cost C: dense-E all experts = O(N·E·C), top-k = O(N·k·C) + router/dispatch. Attention still O(N²·d_head·heads) for full prefill. Parameter storage remains roughly proportional to E, not k.
Architecture & alternatives
A single dense FFN has predictable scheduling and often wins for small models or low-concurrency serving. Sparse MoE can raise total capacity without proportional per-token FFN FLOPs. Sparse attention targets sequence-length cost, not parameter utilization.
Implementation or pseudocode
Profile gate logits, load distribution, capacity overflow, all-to-all transfers, kernel launch count and active expert weight fetches separately. Compare equal-quality models, not just total parameter labels.
Compute, memory, latency and cost
MoE saves per-token arithmetic relative to executing all its experts, but requires all expert weights to be resident or fetched; weight bandwidth, network traffic and low expert batch sizes can dominate decode latency.
Failures, misconceptions and mitigations
Calling MoE “sparse attention” is a category error. Sparse expert FLOPs do not imply lower GPU VRAM than a smaller dense model. Small batch sizes may underutilize routed GEMMs.


C Interview-ready spoken answer
“There are two distinct sparsities: MoE activates a subset of MLP parameters per token, whereas sparse attention restricts token interactions. MoE lowers expert compute per token relative to evaluating every expert but retains the total expert weight footprint. I decide using measured token throughput, expert utilization, memory capacity and network communication—not parameter count alone.”


D Follow-up pressure test
  1. Why might a 40B-total MoE not fit where a 14B dense model fits?
  2. How can attention remain quadratic while MoE layers are sparse?
  3. What does an expert-parallel all-to-all do to p99 latency?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: A new top-2 MoE has lower theoretical FLOPs but p95 latency worsens on eight GPUs. Instrument CUDA traces, per-expert tokens, all-to-all bytes and idle time; compare local vs distributed expert placement, batching and router skew. Try dense fallback or grouped dispatch; validate quality and p95 under real batch distributions.
Success criteria: Acceptance: non-inferior task score, p95 within product SLO and lower cost/request at observed concurrency; define thresholds before deployment.


F Interview takeaways
  • MoE sparsifies FFN activation; sparse attention sparsifies token pairs.
  • Total parameters are not active parameters.
  • Communication and small GEMMs can erase theoretical savings.
LESSON 02 / 14
Mixture of Experts: routing and load balancing
Track exactly which experts receive tokens and why routing collapses.


A Interviewer questions
  1. Derive top-2 expert routing and explain dispatch and combine operations.
  2. Why do equal router probabilities not ensure balanced expert compute?
  3. What training and serving failures come from expert capacity overflow?


B Deep technical explanation
Mechanism & data flow
Given token representation x, gate computes E logits. For each token select top-k experts, turn selected scores into normalized weights, dispatch token x to those experts, execute FFN_e(x) and weighted-sum the outputs. In training, only selected experts receive meaningful input gradients from that token; router parameters learn through the selected scores and any auxiliary/alternative load objectives. Expert choice, shared experts and token choice alter where capacity constraints sit. In expert-parallel inference, dispatch typically requires communication to GPUs holding relevant experts.
Algorithms and mathematics
s_e=xW_gate[:,e]; S=TopK(s,k); g_e=exp(s_e)/Σ_{j∈S} exp(s_j) for e∈S; y=Σ_{e∈S}g_e FFN_e(x). Load: n_e=Σ_tokens 1[e selected]. Capacity factor ≈ allocated_slots/(expected routed tokens per expert).
Architecture & alternatives
Top-1 saves FFN work and communication but risks lower routing flexibility. Top-2 offers mixing at twice expert execution. Auxiliary load balancing adds optimization pressure but may harm task loss; bias-based balancing strategies trade control for a different training signal.
Implementation or pseudocode
Implement vectorized grouping by expert ID, scatter/gather with index maps, and deterministic overflow handling; measure dropped tokens, auxiliary losses and expert skew. Numerical toy routers illustrate logic, not distributed production throughput.
Compute, memory, latency and cost
Memory ≈ shared weights + E×expert weights, independent of top-k. Work ≈ shared compute + k×FFN work; wall time also includes gate, gather, all-to-all and uneven expert queues.
Failures, misconceptions and mitigations
A hot expert saturates while others idle; naive top-k can create token drops when capacities are hard. Router instability may come from overconfident logits, noise or skewed domain mix. Monitor per-expert token histograms on real traffic.


C Interview-ready spoken answer
“A token passes through a router, selects k expert FFNs and combines their outputs with router weights. The savings are in activated expert compute, not weight storage. Load balance is an operational constraint: I measure skew, overflow, communication and quality alongside FLOPs, and I avoid assuming a balancing loss guarantees uniform serving load.”


D Follow-up pressure test
  1. How would you handle 90% of tokens choosing one expert?
  2. Why is token-dropping especially problematic in user-facing generation?
  3. How does routing interact with expert parallelism and network topology?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: After a traffic-domain shift, expert 3 receives most routed tokens and causes timeouts. Graph per-expert assignments, queue length and token overflow; reproduce with a domain-stratified batch. Options: increase capacity, rebalance experts with validated training, alter placement, or route to dense fallback.
Success criteria: Acceptance: no unacceptable token drops, controlled expert imbalance and p99 within SLO without domain-quality regression.


F Interview takeaways
  • Top-k selects experts per token per layer.
  • Expert load skew is both modeling and systems behavior.
  • Routing auxiliary loss and deployed p99 must be measured separately.
LESSON 03 / 14
MHA vs. MQA vs. GQA
Derive how KV sharing changes cache shape, bandwidth and quality.


A Interviewer questions
  1. Why does GQA leave query-head count unchanged but reduce KV storage?
  2. What are precise Q,K,V tensor dimensions for 32 query heads and 8 KV heads?
  3. When might MQA lose quality compared with MHA?


B Deep technical explanation
Mechanism & data flow
In MHA each query head owns distinct K and V projections. MQA keeps the usual query heads but shares one KV head across them. GQA partitions query heads into groups, each using one KV head. Before scaled dot-product attention, the KV head is broadcast logically or repeated to match group queries. The query projection and final output dimension need not change. During autoregressive decode, reuse cached K,V from the prefix, computing only current Q,K,V.
Algorithms and mathematics
Q ∈ R[B,Hq,Tq,D], K,V ∈ R[B,Hkv,Tk,D]; Hq mod Hkv=0; group factor G=Hq/Hkv. KV bytes = B×L×T×2×Hkv×D×bytes_per_element. MHA Hkv=Hq; MQA Hkv=1.
Architecture & alternatives
MHA offers head-specific KV expressiveness but high decode bandwidth. MQA saves most KV bytes but can sacrifice accuracy on some tasks. GQA is intermediate. MLA compresses a joint KV latent and is not simply “more extreme GQA.”
Implementation or pseudocode
Use tensor reshape/group mapping rather than permanently duplicating KV cache: head h looks up KV index floor(h/G). Check positional embeddings, masks and layer count before comparing actual models.
Compute, memory, latency and cost
At fixed Hq, D, layers, dtype and context, moving from 32 KV heads to 8 cuts KV bytes by 4×; memory reduction can raise concurrent batch capacity. Attention arithmetic may not fall by the same factor.
Failures, misconceptions and mitigations
Wrong head ordering silently mixes groups; repeating K,V physically in persistent cache destroys expected memory savings. Incompatible head-count conversion is not a trivial checkpoint surgery; retraining or uptraining may be needed.


C Interview-ready spoken answer
“MHA stores K and V per query head. MQA shares one KV head across all query heads; GQA shares a smaller set of KV heads, one per query group. Cache memory is linear in KV-head count, so GQA reduces decode bandwidth and improves concurrency while usually retaining more head diversity than MQA. I quantify cache savings and test quality on long-context and retrieval-sensitive tasks.”


D Follow-up pressure test
  1. Compute per-layer cache bytes for B=8,T=4096,Hkv=8,D=128,bf16.
  2. Why does GQA help the decode phase more than a large prefill matrix multiplication?
  3. Which tensor operations accidentally materialize repeated K/V?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: Under high concurrency, a serving process OOMs despite modest model weight memory. Calculate cache reserve by layer and active tokens; compare MHA/GQA architectures, then validate attention kernel head mapping and query correctness.
Success criteria: Acceptance: predicted vs actual peak GPU memory within an agreed tolerance; output regression suite and p95 token latency stay within bounds.


F Interview takeaways
  • KV memory scales with Hkv, not Hq.
  • MHA→GQA reduces cache, not necessarily proportionate FLOPs.
  • Correct head-group mapping is critical.
LESSON 04 / 14
KV cache and incremental decoding
Understand prefill state, cache updates and causal invariants.


A Interviewer questions
  1. Show why decoding without a cache recomputes past K,V unnecessarily.
  2. Explain tensor shapes in the first prefill and third decode step.
  3. Why can a malformed position offset break RoPE and generation quality?


B Deep technical explanation
Mechanism & data flow
In prefill, every prompt token passes through all decoder layers to compute layer-specific K,V; they are stored. Each subsequent generation step computes K,V only for the new token, appends them to each layer cache, forms a query for the current token, reads all allowed cached keys and values and emits one new position. Each layer has its own K,V cache. Causality is enforced by cache growth and any local attention constraints; exact attention to the prefix still reads linearly more prior tokens as it grows.
Algorithms and mathematics
Cache[layer].K ∈ R[B,Hkv,T,D]; similarly V. Without cache, repeated full-prefix Transformer forwards inflate computation; with cache, each generated step has O(T·Hq·D) attention dot-products plus per-token projections/FFNs (roughly) and O(T·Hkv·D) cache footprint.
Architecture & alternatives
KV caching is essential for low-latency autoregressive inference. Prefix caching can share prefill states for identical prefixes if tokens, models, adapters and position semantics match. Recompute may win when memory is scarce and reuse is limited.
Implementation or pseudocode
Store per-layer cache object keyed by request and positions. Track prompt length, decode position, pad masks, rotary offsets and cache reuse identity. Test next-token logits of cached vs uncached forward within numeric tolerance.
Compute, memory, latency and cost
Capacity grows with active cached tokens and batch, often more than with request count alone. One 32k-token conversation can use cache comparable to many small conversations; cache reads are a major decode bandwidth cost.
Failures, misconceptions and mitigations
Reusing stale KV after changing system prompt/model version silently corrupts behavior. Padding/position mismatch, prompt-branch sharing without copy-on-write and beam reorder bugs frequently cause output divergence.


C Interview-ready spoken answer
“Prefill computes and stores each layer’s keys and values for the prompt. Decode then appends only the new position and attends over the cached prefix instead of recomputing earlier projections. This trades growing memory and bandwidth for lower incremental compute; I validate equivalence to a full-prefix causal forward pass and track cache identity and position offsets.”


D Follow-up pressure test
  1. Why does KV cache not make attention cost independent of context length?
  2. How do beam search and branch forks share prefix KV safely?
  3. How would you detect a cache correctness regression after an optimization?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: Answers change after enabling prefix reuse for multi-tenant chat. Inspect cache key composition, exact token IDs, policy version and cache sequence masks. Reproduce cached-vs-no-cache logits; disable unsafe sharing and enforce namespace/version keys.
Success criteria: Acceptance: exact-prefix cache isolation tests pass with documented floating-point tolerance; no cross-tenant content mixing.


F Interview takeaways
  • KV stores layer-specific states, not a summarized user memory.
  • It saves recomputation but context reads and memory still grow.
  • Cache versioning and positional correctness are non-negotiable.
LESSON 05 / 14
KV cache memory estimation and compression
Estimate the true per-request memory budget and explain compression methods.


A Interviewer questions
  1. Compute KV bytes for a specified GQA model and concurrency.
  2. Distinguish KV quantization, eviction, offload and latent compression.
  3. Why might lower KV precision damage retrieval even if ordinary chat seems fine?


B Deep technical explanation
Mechanism & data flow
KV allocation depends on layers, batch slots, cached tokens, KV head count, head dimension, K+V and element bytes. Quantizing K,V to 8/4 bits decreases storage but usually requires scale/zero-point metadata, per-block granularity and supported kernels. Eviction reduces cached history (possibly changing model semantics); CPU/NVMe offload keeps history but adds movement latency. Learned MLA stores compressed latents for K,V, plus separately encoded position terms in some designs.
Algorithms and mathematics
KV_bytes ≈ 2×L×B×T×Hkv×Dh×s. Example L=32,B=8,T=4096,Hkv=8,Dh=128,s=2 → 4,294,967,296 bytes = 4 GiB. A 16-token-block allocator can waste at most 15 token slots per active sequence for the final block.
Architecture & alternatives
First lower Hkv through architecture (GQA/MLA) if selecting a model; then evaluate compatible cache quantization and paging; eviction/windowing only if application tolerates loss of remote-token access.
Implementation or pseudocode
Build a memory budget that subtracts model weights, runtime reserved memory, activations, kernels, allocator fragmentation and safety margin. Cache compression must be tested on long-range exact recall and numeric/code precision.
Compute, memory, latency and cost
Peak KV may grow with concurrent active tokens and best-of-N branches. Quantization adds dequantization and sometimes numerical error; offload adds PCIe/network bandwidth; smaller tokens per block reduce waste but increase metadata overhead.
Failures, misconceptions and mitigations
Common errors: omit factor 2 for K and V, multiply by Hq instead of Hkv, mistake GB for GiB, ignore padding/branch duplication or claim cache compression is free in latency/quality.


C Interview-ready spoken answer
“I size KV with 2×layers×batch×tokens×KV-heads×head-dim×bytes per element. Compression choices have different failure modes: lower-bit cache changes numeric precision, eviction changes accessible context, offload adds bandwidth and latency, MLA requires a compatible model architecture. I forecast the peak active-token distribution and test long-context quality before changing a serving pool.”


D Follow-up pressure test
  1. Derive usable concurrency given 20 GiB remaining for KV and a prompt-length distribution.
  2. Does quantizing to int4 always yield a 4× reduction vs bf16? Account for metadata.
  3. How would you catch a long-distance recall regression caused by cache eviction?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: A new longer prompt template produces GPU OOMs during peak traffic. Attribute bytes to model and KV by request token count; enforce admission based on projected cache, consider GQA/quantization/paging and queue workloads with bound waiting.
Success criteria: Acceptance: load test to p99 prompt length without OOM, required long-range recall unaffected, p95 TTFT/TPOT within contract.


F Interview takeaways
  • Factor two means keys plus values.
  • KV quantization ≠ eviction ≠ learned compression.
  • Use active-token accounting, not merely total requests.
LESSON 06 / 14
FlashAttention, tiling and online softmax
Explain exact attention with lower HBM traffic.


A Interviewer questions
  1. Derive an online stable softmax update over two key tiles.
  2. Does FlashAttention remove O(N²) attention arithmetic?
  3. Why can materializing S×S attention hurt despite enough GPU FLOPs?


B Deep technical explanation
Mechanism & data flow
Naive attention forms QKᵀ, writes a large score matrix to HBM, normalizes with softmax and rereads it to multiply V. FlashAttention tiles Q, K and V so blocks fit on-chip SRAM; for each query row it maintains running maximum m, normalizer l and weighted output accumulator o. When a new key tile arrives, rescale previous accumulators to a common max, incorporate the tile and continue. At the end return o/l. This yields mathematically exact scaled attention up to floating-point ordering, without materializing a full NxN probability matrix.
Algorithms and mathematics
For old (m,l,u) and tile logits z_j: m′=max(m,max_j z_j); α=exp(m−m′), w_j=exp(z_j−m′); l′=αl+Σ_j w_j; u′=αu+Σ_j w_j V_j; output=u′/l′. Standard full attention compute remains O(N²d); auxiliary score-memory can drop from O(N²) to approximately linear-size working storage.
Architecture & alternatives
FlashAttention attacks IO complexity, not the number of token pairs for exact global attention. Sliding-window/block-sparse methods reduce pairs, changing information flow. Fused kernels may be unavailable for certain dtype/mask/dropout layouts.
Implementation or pseudocode
Use a supported scaled-dot-product attention kernel and verify backend selection, mask semantics, dtype, head dimension and dropout. Compare to a high-precision reference with tolerances and gradient checks; profile HBM traffic and SRAM occupancy.
Compute, memory, latency and cost
At long sequences the NxN score tensor can dominate memory even when activations are small. Tiling reduces reads/writes to HBM and can boost throughput, but speedup depends on GPU, shape and kernel support.
Failures, misconceptions and mitigations
Numerical bugs in the rescaling factor cause NaNs or wrong output. “Exact” does not promise bit-identical floating-point results. Some masks or model architectures trigger slow fallback kernels.


C Interview-ready spoken answer
“FlashAttention computes exact scaled attention in tiles, keeping softmax statistics and output accumulators on chip. It uses an online log-sum-exp update to avoid writing the NxN scores to HBM. The arithmetic still scales quadratically for global attention, but IO and activation memory improve. I validate mask parity, backend selection and wall-clock latency on target sequence lengths.”


D Follow-up pressure test
  1. Write the update when prior max is 2, tile max is 4.
  2. Why is computing softmax independently per tile wrong?
  3. Can FlashAttention alone make 1M-token context computationally cheap?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: A large-prompt endpoint OOMs in attention but weights fit. Profile peak allocations and kernel choice; compare SDPA backends with exact causal mask. Deploy fused attention with correctness and per-shape performance guardrails.
Success criteria: Acceptance: attention-output parity within chosen tolerance, no NaN on stress test and lower measured peak memory at target sequence lengths.


F Interview takeaways
  • IO-aware exact attention still touches quadratic token pairs.
  • Online softmax merges tiles with running max and denominator.
  • Check whether the fast kernel is actually selected.
LESSON 07 / 14
Sliding Window Attention and sparse attention
Separate limited receptive field from persistent long-range reasoning.


A Interviewer questions
  1. Compute nonzero attention pairs for a causal window of width W.
  2. How can stacking W-local layers expand receptive field without global attention?
  3. When does local attention fail despite a nominally long context limit?


B Deep technical explanation
Mechanism & data flow
Causal sliding-window attention lets a token read only the most recent W positions (including itself); its QK scores are banded. Stacking several layers allows information from earlier tokens to propagate through intermediate representations, but distant exact references can still degrade. Other sparse patterns include strided, global, block-local and dilated attention; each changes reachable token pairs. Some hybrids add a few global layers while the rest use windows.
Algorithms and mathematics
Pairs ≈ Σ_{t=1}^N min(t,W) = W(N−W+1)+W(W−1)/2 for N≥W; full causal ≈ N(N+1)/2. Approx prefill attention arithmetic O(N·W·d) rather than O(N²·d) when kernels exploit sparsity.
Architecture & alternatives
Global attention preserves direct pairwise access; local windows save compute and bound cache in window-aware inference; retrieval can supply distant facts rather than relying on attention propagation.
Implementation or pseudocode
Construct mask where query i permits key j only if 0≤i−j<W. Enforce at both training and decoding; check cached token eviction matches actual model attention pattern.
Compute, memory, latency and cost
Local attention caps per-layer active KV at W tokens; end-to-end cost may still be dominated by FFNs, IO, or some global layers. If an implementation materializes a full NxN mask, theoretical sparse savings will not appear.
Failures, misconceptions and mitigations
Trusting theoretical receptive field as reliable factual recall is a mistake. Information from early positions may be compressed or lost; benchmark needle-in-haystack over varied offsets and distractors.


C Interview-ready spoken answer
“Sliding-window attention restricts each position to W recent tokens, so optimized prefill attention scales approximately as N·W instead of N². Layers can relay information farther, but direct long-range access is lost. I select it when local dependencies dominate and validate recall across positions rather than equating context capacity with usable memory.”


D Follow-up pressure test
  1. Is W=512 enough for a contract citation 10k tokens earlier?
  2. Why might full attention still win at 256 tokens?
  3. What changes when some layers are global and others local?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: A document assistant misses a clause 15k tokens earlier after windowed inference rollout. Instrument answer errors by document offset; compare full-context, windowed and retrieval-assisted baselines; route high-evidence tasks differently.
Success criteria: Acceptance: document grounding recall@k and citation correctness pass long-distance slices with bounded latency/cost.


F Interview takeaways
  • Sliding windows reduce attention pairs, not model parameter size.
  • Layer propagation is not guaranteed exact recall.
  • Sparse kernel efficiency must be profiled.
LESSON 08 / 14
Attention sinks and streaming attention
Explain why retaining a few initial positions can stabilize windowed streaming.


A Interviewer questions
  1. What exactly is an attention sink and why does it often arise at initial tokens?
  2. Does a sink token preserve forgotten factual content?
  3. How do you select sink tokens without sacrificing live window capacity?


B Deep technical explanation
Mechanism & data flow
StreamingLLM observed that some heads allocate disproportionate mass to first tokens even when these are not semantic evidence. The first positions can function as stable attention sinks, allowing softmax mass to go somewhere. Naively evicting everything outside the recent window removes them and can destabilize generation. A streaming cache can retain a small prefix of initial KV tokens and the most recent W tokens, while evicting the middle. Careful position handling is required: physical cache indices and logical position IDs should not be conflated.
Algorithms and mathematics
Retained positions: {0,…,S−1} ∪ {max(S,t−W+1),…,t}. Cache slots roughly S+W rather than entire t; per-layer bytes ≈ 2×Hkv×Dh×(S+W)×dtype bytes.
Architecture & alternatives
Attention sinks are a streaming stability technique, not a true infinite-memory mechanism. RAG, hierarchical summaries or external state are preferable if early details must remain retrievable after eviction.
Implementation or pseudocode
Keep immutable sink prefix K,V; maintain rolling cache with correct rotary/positional conventions for the model; stress-test streaming chats much longer than training context. Validate output after every eviction boundary.
Compute, memory, latency and cost
Bounded cache supports prolonged generation with capped memory, but old content beyond retained sinks/windows becomes inaccessible to direct attention. The time spent reading a window stays bounded, yet quality depends on task.
Failures, misconceptions and mitigations
Misleading phrase: “trained with 4M context.” StreamingLLM demonstrates stable streaming language modeling, not arbitrary precise recall over a 4M-token record. Lost mid-history facts still require retrieval.


C Interview-ready spoken answer
“Attention sinks are initial positions that absorb attention mass even without useful semantics. StreamingLLM retains those positions plus a recent window to preserve stability while bounding cache growth. It cannot answer questions about arbitrary evicted details, so I pair it with explicit memory/retrieval when the task requires long-horizon facts.”

  1. What experiment separates sink stabilization from true information retention?
  2. Can a small sink cache solve compliance recall over a month-long transcript?
  3. What happens to RoPE position IDs after physical cache eviction?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: A streaming assistant becomes incoherent after its first KV eviction. Compare recent-window-only and sink+recent output under matched token budget; audit position IDs and long-run perplexity versus factual recall.
Success criteria: Acceptance: stable token-level quality over the expected streaming duration; document-known limitations for inaccessible history.


F Interview takeaways
  • Attention sink ≠ semantic summary.
  • Sink+recent fixes a stability mode, not all long-context tasks.
  • Track logical positions independently of memory allocation.
LESSON 09 / 14
PagedAttention and KV block management
Trace logical token offsets into noncontiguous physical KV blocks.


A Interviewer questions
  1. How does a block table allow noncontiguous memory for a logical sequence?
  2. Why is paging not the same as reducing bytes per token?
  3. How does reference-counted prefix sharing work during sequence forks?


B Deep technical explanation
Mechanism & data flow
PagedAttention, introduced with vLLM, partitions each sequence’s logical KV into fixed-size token blocks. The scheduler requests physical KV blocks on demand; per-sequence block tables map logical indices to physical GPU memory that need not be contiguous. Attention kernels gather the mapped blocks. Full blocks can be shared for identical prefixes and are reference-counted; a writer forks via copy-on-write when a shared block would be modified. Paging reduces fragmentation and over-reservation, not the intrinsic K/V values stored per token.
Algorithms and mathematics
Logical block b=floor(token_idx/block_size); offset=token_idx mod block_size; physical_block=table[request,b]. For B tokens/block, unused slots per sequence are in [0,B−1] in the last allocated block (ignoring other allocator overhead).
Architecture & alternatives
Contiguous allocation is simple but suffers variable-length reservations. Paged allocations maximize usable active KV capacity, especially with mixed request lengths and beam/prefix sharing. Offloading is independent of paging.
Implementation or pseudocode
Track block ownership, reference counts, allocation/free events and versioned prefix hashes. Unit-test noncontiguous blocks, fork mutation, request cancellation, eviction and tenant isolation. Do not directly expose block IDs in user space.
Compute, memory, latency and cost
Worst-case internal fragmentation is B−1 token slots per active sequence; smaller B reduces tail waste but enlarges block tables and index overhead. The cache element bytes still follow the KV formula.
Failures, misconceptions and mitigations
Use-after-free, leaked references or improper copy-on-write can corrupt responses or leak tenant context. Fragmentation metrics and peak reserved bytes may disagree; inspect allocator traces.


C Interview-ready spoken answer
“PagedAttention treats KV storage like paged memory: the attention sequence is logically contiguous, but its physical KV blocks are not. A block table translates indices, enabling demand allocation and shared prefixes with copy-on-write. It improves utilization of available cache memory, not the amount of KV data each token mathematically requires.”


D Follow-up pressure test
  1. If block size is 16 and a sequence has 33 tokens, how many blocks and unused slots?
  2. Why would prefix-sharing require copy-on-write?
  3. How can paging improve batching even when no arithmetic is saved?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: A batch scheduler runs out of allocatable contiguous KV despite unused GPU bytes. Measure fragmentation, active-token load and reservation overhead; turn on block paging and test cancellation and shared-prefix branch isolation.
Success criteria: Acceptance: zero cross-request corruption in concurrency tests; improved completed requests/sec subject to unchanged SLO.


F Interview takeaways
  • Paging addresses fragmentation and sharing.
  • Logical-to-physical mapping is central.
  • Correct reference counts and isolation are safety-critical.

Long-context scaling and compute/memory trade-offs
Plan context length, throughput, and reliable recall jointly.


A Interviewer questions

  2. How do prefill, decode and serving concurrency scale differently?
  3. What does a good long-context benchmark measure beyond needle retrieval?


B Deep technical explanation
Mechanism & data flow
Long-context system design spans prefill quadratic global attention, decode linear attention over cached prefix, KV memory linear in cached tokens, position extrapolation, model training distribution and retrieval accuracy. Techniques solve different dimensions: fused attention lowers score IO, GQA lowers KV bandwidth, paging improves utilization, local attention reduces pair count, RoPE scaling may support longer positions, hierarchical retrieval prevents flooding the prompt. Choose raw long context for small, bounded corpus with strong positioning quality; RAG for selective evidence, privacy and freshness; staged analysis for many-document and multi-hop tasks; sliding windows for local streaming.
Implementation or pseudocode
Stress at P50/P95/P99 input lengths, distractor positions, multi-hop and source contradictions. Measure TTFT, TPOT, GPU reserved/allocated bytes, task accuracy by offset and truncation rate.
Compute, memory, latency and cost
The arithmetic model excludes softmax kernel efficiency, FFNs and cache IO; treat it as sizing sanity check. Long prompts may require chunked prefill, prefill/decode scheduling or disaggregation to avoid tail latency.
Failures, misconceptions and mitigations
Common trap is optimizing only nominal max length. Silent truncation, middle-position degradation and lost access controls in retrieval pipelines can break real applications.

“Long context is a three-axis problem: prefilling all pairs, storing KV for all cached tokens, and retrieving the right evidence at distant positions. LESSON 11 / 14
Reasoning-oriented models and inference-time compute
Budget search, verification and generated reasoning without assuming monotonic gains.


A Interviewer questions
  1. Differentiate more reasoning tokens from stronger base weights.
  2. When does best-of-N sampling beat longer single-path reasoning?
  3. Why can larger test-time budgets degrade performance?


B Deep technical explanation
Mechanism & data flow
Reasoning systems can allocate additional test-time compute through longer internal reasoning traces, multiple sampled candidate solutions, tree search, tool execution or external verifiers. More sampled tokens increase autoregressive decode cost and KV. Best-of-N uses a selector or verifier to choose among candidates; success depends on score quality and candidate diversity. RL on verifiable rewards can incentivize model behaviors used during reasoning, but it does not change the fundamental autoregressive Transformer math by itself.
Algorithms and mathematics
If independent candidate success probability is p, chance at least one of N succeeds is 1−(1−p)^N; this is an optimistic upper bound on final selected-answer success without a perfect selector. Generate cost roughly N×per-path output tokens (before sharing prefill).
Architecture & alternatives
For deterministic verifiable problems, sampling+verification may dominate a long unverified trace. For strict latency, one short path or a small model can be preferable. Tool-augmented reasoning introduces external execution and error-handling costs.
Implementation or pseudocode
Select based on difficulty classifier or cheap confidence proxy, apply a hard token/tool/time budget, ensure correct answer parsing, and prevent verifier prompt leakage. Keep latency and success stratified by problem difficulty.
Compute, memory, latency and cost
Budget increases candidate count, output tokens and branch KV. Shared prefix caching reduces repeated prefill; branch scheduling adds memory and contention.
Failures, misconceptions and mitigations
Independent success is an unrealistic assumption if generations are correlated; the selector can reward fluent but wrong answers. More thinking may loop or overcorrect. Report final verified task success, not self-reported confidence.


C Interview-ready spoken answer
“Inference-time scaling buys extra attempts or computation: a model may reason longer, sample branches, call tools or verify solutions. Gains depend on candidate diversity and verifier reliability and are not guaranteed with more tokens. I route hard requests to extra compute only when marginal task-success gain exceeds latency and cost.”

Success criteria: Acceptance: statistically supported success-rate lift on difficult heldouts with cost/request and p95 within agreed constraints.


F Interview takeaways
  • Reasoning traces are not proof of correctness.
  • Candidate diversity and verifier quality govern best-of-N.
  • More tokens can make results worse or just cost more.

Recursive Language Models (RLMs)
Treat large input as an external environment that can be inspected programmatically.


A Interviewer questions
  1. Why is the RLM concept more accurately a recursive inference strategy than a new attention layer?
  2. How does code-based slicing reduce context pressure?
  3. What happens when recursive subcalls lose context or repeat work?


B Deep technical explanation
Mechanism & data flow
In the 2025 Recursive Language Models work, a model uses a controller to inspect a long prompt or data artifact as an external environment instead of packing it all into the immediate model context. It may write operations to search, subset, summarize or transform the stored text and recursively invoke the LLM on smaller pieces. Intermediate results return to the controller which integrates them. Recursive scope, call limits and evidence provenance matter; the model cannot reason about bytes never visited unless its tool chooses them.
Algorithms and mathematics
Total work ≈ Σ_i tokens(subcall_i)×model_cost + controller/tool overhead. The maximum context per individual call can remain below C even if external data length N≫C; this is an orchestration property, not a change to per-call Transformer attention.
Architecture & alternatives
RAG retrieves indexed evidence efficiently when the query has a clear retrieval signal. RLM-style recursive exploration can suit complex aggregation, long code/data inspection and hierarchical analyses but incurs controller and subcall variance.
Implementation or pseudocode
Use immutable source handles, line/offset references, deterministic slicing tools and recursion depth/token budgets. Record tool traces, subcall inputs, source provenance and partial outputs. Avoid executing untrusted generated code without a sandbox.
Compute, memory, latency and cost
Additional tool calls and recursive LLM requests may cost more and have long-tail latency. Cache repeated subresults; parallelize independent queries only when correctness permits.
Failures, misconceptions and mitigations
Failure cases: missed relevant slice, circular recursion, false summaries, prompt injection from source content, and uncertain provenance. “Arbitrarily long” means the controller can access long external input, not guaranteed exhaustive reasoning.


C Interview-ready spoken answer
“RLMs keep huge inputs outside the model context and let a controller inspect them by code and recursive LLM calls. This is inference orchestration over externally stored text, not a magically larger attention window. I limit recursion, enforce source boundaries and judge completeness of accessed evidence before trusting the final answer.”

LESSON 14 / 14
Diffusion Language Models vs autoregressive generation
Explain masked iterative refinement without assuming a free parallel-speed advantage.


A Interviewer questions
  1. What is the forward corruption process in a masked diffusion LM?
  2. How does iterative denoising differ from causal left-to-right sampling?
  3. When is parallel token updating genuinely faster end-to-end?


B Deep technical explanation
Mechanism & data flow
Masked discrete diffusion language models such as LLaDA train on text corrupted by masking a selected fraction of token positions. A model predicts original tokens at masked locations under the corruption distribution. Generation starts from many masked positions and repeatedly predicts replacements or remasks uncertain positions over a schedule, allowing non-left-to-right editing. This differs from autoregressive factorization p(x)=∏p(x_t|x_<t). The number of refinement steps, predictions per step, remasking policy and conditional guidance determine latency and quality.
Algorithms and mathematics
Autoregressive: log pθ(x₁:N)=Σ_t log pθ(x_t|x_<t). Illustrative masked diffusion training: sample mask fraction τ, sample Mτ, minimize E[Σ_{i∈Mτ}w(τ)·(−log pθ(x_i|corrupted x,τ))]; weighting and exact objective vary by diffusion formulation.
Architecture & alternatives
AR generation naturally streams one token at a time with KV reuse; diffusion can update tokens in parallel but performs multiple full-sequence denoising passes. DLM may help controllable editing or bidirectional refinement; serving kernels and task quality decide feasibility.
Implementation or pseudocode
Implement a toy masked denoising loop with a fixed-length sequence and confidence remasking. Verify no gold-token leakage in train targets and benchmark final accuracy under varying step counts.
Compute, memory, latency and cost
An N-token diffusion sample with K denoising steps can still cost K Transformer passes over N positions; do not infer speedup from predicting several tokens at once. AR decode uses incremental KV but has sequential dependency.
Failures, misconceptions and mitigations
DLM outputs can oscillate under remasking; stopping too early reduces coherence. Evaluation must cover perplexity comparability caveats, controllability, end-to-end tokens/sec and factual accuracy—not architectural novelty alone.


C Interview-ready spoken answer
“Autoregressive models emit one token conditioned on earlier tokens; masked diffusion models iteratively denoise a corrupted token canvas and can update many positions per step. The trade-off is between sequential cached decode and repeated full-sequence refinement. I compare actual quality/latency at matched hardware and budgets, and I do not treat diffusion as guaranteed faster.”


D Follow-up pressure test
  1. What is the cost of 12 denoising passes over a 2k-token output?
  2. Why is AR-style KV caching less straightforward during bidirectional revisions?
  3. How would you measure output stability vs refinement steps?


E Production scenario — instrument, diagnose, mitigate, validate
Incident: A DLM prototype predicts many tokens per iteration but has worse wall-clock p95 than the existing AR API. Profile full-sequence passes, batch size and token-edit ratio; reduce steps or revert if quality cannot be retained.
Success criteria: Acceptance: quality on held-out generation and edit tasks at least as good, with documented end-to-end latency and memory within SLO.


F Interview takeaways
  • Diffusion over text commonly uses masking/reconstruction, not Brownian motion.
  • Parallel position updates do not imply fewer total FLOPs.
  • Measure end-to-end performance against cached AR decoding.

"""Module 6: Educational attention/MoE/streaming mechanisms.
Run: python module6_transformer_optimization_reference.py
CPU-compatible; no external checkpoints required. Not a production attention kernel.
"""
import math
import torch
from torch import nn
import torch.nn.functional as F


def kv_cache_bytes(layers:int, batch:int, tokens:int, kv_heads:int, head_dim:int, element_bytes:int=2)->int:
    """K and V, not activation/allocator/weight bytes. All values nonnegative."""
    vals=(layers,batch,tokens,kv_heads,head_dim,element_bytes)
    assert all(isinstance(x,int) and x>=0 for x in vals)
    return 2*layers*batch*tokens*kv_heads*head_dim*element_bytes


def grouped_query_attention(q:torch.Tensor,k:torch.Tensor,v:torch.Tensor,causal=True):
    """q[B,Hq,Tq,D], k,v[B,Hkv,Tk,D]. For full prefill Tq=Tk.
    This *reference* repeats K/V in a temporary, not a serving KV cache.
    """
    B,Hq,Tq,D=q.shape
    _,Hkv,Tk,Dk=k.shape
    assert v.shape==k.shape and D==Dk and Hq%Hkv==0
    assert not causal or Tq==Tk, 'Full causal sequence only; decode needs position offsets'
    g=Hq//Hkv
    kb=k.repeat_interleave(g,dim=1)
    vb=v.repeat_interleave(g,dim=1)
    logits=q@kb.transpose(-2,-1)/math.sqrt(D)
    if causal:
        mask=torch.ones(Tq,Tk,device=q.device,dtype=torch.bool).tril()
        logits=logits.masked_fill(~mask,float('-inf'))
    return logits.softmax(-1)@vb


def online_softmax_weighted(q:torch.Tensor, k:torch.Tensor,v:torch.Tensor,tile:int=3):
    """One query [D] over keys [T,D], values [T,Dv]; exact tiled online softmax."""
    assert q.ndim==1 and k.ndim==v.ndim==2 and k.size(1)==q.numel() and k.size(0)==v.size(0)
    m=-float('inf')
    ell=torch.zeros((),dtype=q.dtype)
    u=torch.zeros(v.size(1),dtype=q.dtype)
    for start in range(0,k.size(0),tile):
        zs=(k[start:start+tile]@q)/math.sqrt(q.numel())
        new_m=max(m,zs.max().item())
        alpha=0. if not math.isfinite(m) else math.exp(m-new_m)
        w=(zs-new_m).exp()
        ell=alpha*ell+w.sum()
        u=alpha*u+w@v[start:start+tile]
        m=new_m
    return u/ell


class TinyTop2MoE(nn.Module):
    """An educational token-choice router; not capacity-limited or distributed."""
    def __init__(self,d:int=8,num_experts:int=4,top_k:int=2):
        super().__init__()
        self.router=nn.Linear(d,num_experts,bias=False)
        self.experts=nn.ModuleList([nn.Sequential(nn.Linear(d,2*d),nn.SiLU(),nn.Linear(2*d,d)) for _ in range(num_experts)])
        self.top_k=top_k

    def forward(self,x):
        assert x.shape[-1]==self.router.in_features
        flat=x.reshape(-1,x.shape[-1])
        selected_logits,indices=self.router(flat).topk(self.top_k,dim=-1)
        weights=selected_logits.softmax(-1)
        # Gather each expert's result for selected token positions.
        # This loop is intentionally clear rather than fast.
        out=torch.zeros_like(flat)
        for e,expert in enumerate(self.experts):
            for slot in range(self.top_k):
                chosen=(indices[:,slot]==e).nonzero(as_tuple=True)[0]
                if chosen.numel():
                    out=out.index_add(0,chosen,weights[chosen,slot,None]*expert(flat[chosen]))
        return out.reshape_as(x),indices


class BlockTable:
    """Reference mapping for logical tokens to physical KV blocks; no GPU memory allocator."""
    def __init__(self,block_size=4):
        self.block_size=block_size
        self.blocks=[]
        self.physical={}
        self.next_id=30

    def append(self,token):
        t=sum(len(self.physical[b]) for b in self.blocks)
        if t%self.block_size==0:
            phys=self.next_id;self.next_id+=7  # Deliberately non-contiguous IDs
            self.blocks.append(phys);self.physical[phys]=[]
        self.physical[self.blocks[t//self.block_size]].append(token)

    def read(self,token_index):
        phys=self.blocks[token_index//self.block_size]
        return self.physical[phys][token_index%self.block_size]


def streaming_positions(total:int,sinks:int,window:int):
    """Union of initial sink and trailing recent logical positions."""
    return sorted(set(range(min(sinks,total)))|set(range(max(0,total-window),total)))
