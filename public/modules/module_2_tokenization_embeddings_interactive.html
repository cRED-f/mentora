LESSON 01 / 10
Tokenization: why language becomes IDs
Trace text → tokenizer → discrete token IDs → embedding lookup, and identify the information the interface can lose.

    
A Interviewer questions
  1. An LLM consumes integers rather than strings. What converts the bytes in a request into model input?
  2. Does one token equal one word, character, or Unicode code point?
  3. Why can two visually identical strings tokenize differently?
  4. Which invariants must hold between a model and its tokenizer?

    
B Deep technical explanation
Core mechanism. Neural layers operate on numerical arrays. A tokenizer defines a finite vocabulary V and an encoding procedure that maps input strings (possibly after normalization and pre-tokenization) to integer token IDs t₁,…,tₙ. A vocabulary entry may represent a full word, subword, whitespace-containing substring, punctuation, one byte, or special control token. IDs are identifiers, not meaningful scalar measurements.


encode: text → (t₁,…,tₙ),  tᵢ ∈ {0,…,|V|−1};  X = E[t] ∈ ℝⁿˣᵈ


  1. Normalize if configured: Unicode normalization/case folding may change characters; exact behavior depends on tokenizer. Avoid assuming normalization happens.
  2. Pre-tokenize if configured: split or mark boundaries around words, digits, punctuation, and whitespace. Regex rules differ across families.
  3. Subword segmentation: apply learned merge rules (BPE), vocabulary scoring (WordPiece or unigram), or another method.
  4. Map to IDs and insert special tokens: apply BOS/EOS, chat role delimiters, padding, or multimodal markers according to the template and model.
  5. Lookup embeddings: retrieve learned vectors for each ID, then supply position information and Transformer layers.


Round-trip nuance. Byte-complete encodings can reconstruct original UTF-8 bytes for ordinary text when no lossy normalization or cleanup intervenes. Unknown-token replacement or Unicode normalization may destroy exact reversibility. Decoding from tokens need not perfectly recreate the input across all tokenizers.


Operational implications. Context limits, API bills, KV-cache allocation, and attention work depend on token counts, not character counts. The model must use its exact trained vocabulary, merge ordering, special-token IDs, and chat template. A tokenizer mismatch can produce valid-looking IDs that mean different strings to the model, damaging quality without crashing.


Compute surface
Embedding lookup costs O(n·d) reads; standard full attention has O(n²·d) attention arithmetic (ignoring implementation-specific kernels), so token inflation can be disproportionately expensive.
Failure surface
Normalization mismatches, accidental addition of role tokens, surrogate handling, and OOV policy cause prompt-length variance or semantic corruption.

    
C Interview-ready spoken answer
The tokenizer is a model-specific encoding contract. It segments text into vocabulary pieces, assigns integer IDs, and the embedding table maps those IDs to vectors. Tokens are not equivalent to words or characters. The segmentation affects context length, cost, and sometimes correctness; tokenizer versions, special-token conventions, and input templates must stay aligned with the model.

    
D Follow-up pressure test
  1. What if the user inserts an invisible Unicode control character? Strong answer: inspect normalization, display/log safely, and avoid assuming visual equality.
  2. Why can't I replace a production tokenizer with a supposedly better one without touching the model? Strong answer: IDs, embedding rows, and output head have learned semantics.
  3. How do you separate a tokenizer failure from a retrieval or model-reasoning failure? Strong answer: inspect serialized text, token IDs, offsets, and a controlled baseline.
Strong response criteria appear in each prompt. State assumptions and explain how you would verify claims.

    
E Production scenario
Incident: Prompt costs double after a template update, while business traffic remains unchanged.
Instrument: Raw byte size (privacy-safe aggregate), input token count, chat-template version, fraction of special tokens, language, prompt sections, and p95 prefill latency. Compare paired requests under old/new encoders; do not log sensitive raw prompts indiscriminately.
Diagnose: The wrapper may duplicate conversation history or insert large role prefixes; an encoder version mismatch may split formerly common strings more often.
Correct: Roll back version drift; budget tokens before inference; regression-test canonical messages and Unicode edge cases. Acceptance: Exact token-ID fixture matches for supported templates, unchanged semantic tests, and prompt-token distribution returns to the validated baseline (no fabricated thresholds).

    
F Interview takeaways
  • Token IDs index a finite learned vocabulary; they are not words or magnitudes.
  • Token count directly affects context, cost, and latency.
  • Model and tokenizer are a versioned pair, including special tokens and templates.



    
LESSON 02 / 10
Byte Pair Encoding: training, merges & encoding
Derive greedy frequency merges, apply their learned rank ordering to unseen strings, and examine byte-level variants.

    
A Interviewer questions
  1. Walk me through training one round of BPE using pair counts.
  2. Why does greedy BPE not always produce globally minimal token count?
  3. What is the difference between character BPE and byte-level BPE?
  4. What happens to unknown vocabulary terms under byte-level BPE?

    
B Deep technical explanation
Training. Begin with a base alphabet of symbols: in a word-based teaching example, characters plus an end-of-word boundary; in GPT-style byte-level systems, potentially the 256 raw byte values combined with specific pre-tokenization rules. Count adjacent pairs inside the units permitted by preprocessing, choose the most frequent pair, introduce a new symbol for the concatenation, replace nonoverlapping occurrences, and record that merge. Repeat until a vocabulary or merge budget is reached.


pair* = argmax₍a,b₎ Σs∈corpus count((a,b) adjacent in s)


Toy example: low low lower contains repeated l·o, o·w, and l·o·w patterns. After merging l+o→lo, we recount pairs, perhaps then merge lo+w→low. Exact tie results depend on the specified tie-breaking rule; the lab makes that rule deterministic and visible.


Inference. The encoder starts from the tokenizer's initial symbols, then performs only learned merges, respecting their rank/order and preprocessing. Some implementations choose the currently highest-priority adjacent merge iteratively; optimized tokenizers use heaps or rank-based algorithms. Do not relearn frequencies from a user's prompt at inference time. Greedy highest-frequency training is not the same as finding the globally shortest segmentation for arbitrary future text.


Illustrative training cost: O(M·N) for naïve rescan of N symbols over M merges; optimized counts update locally.


Byte-level benefits and limits: A full set of 256 initial byte tokens allows encoding arbitrary UTF-8 sequences without an [UNK] token. It does not imply efficient segmentation: rare multi-byte characters may require many tokens. Spaces, newlines, regex boundaries, and special-token treatment remain model-specific. Raw byte BPE, byte-to-Unicode remapping, and SentencePiece byte fallback are distinct engineering choices.


Implementation traps: pair counts must be weighted by word occurrence frequency when training on compressed word-count corpora; overlapping pairs cannot be merged twice in one pass; merge ranks are reproducibility-critical; Unicode code points and UTF-8 bytes are different alphabets; and adding merges usually changes IDs or segmentation unless vocabulary mapping is coordinated.


Illustrative pseudocode
symbols = initialize_symbols(corpus)
merges = []
repeat M times:
    pair = most_frequent_adjacent_pair(symbols)
    if pair does not exist: break
    symbols = replace_nonoverlapping(symbols, pair)
    merges.append(pair)  # ordered ranks

encode(text):
    tokens = initialize_symbols(text)
    for pair in merges:
        tokens = replace_nonoverlapping(tokens, pair)
    return token_ids(tokens)

    
C Interview-ready spoken answer
BPE starts with an initial alphabet, repeatedly counts adjacent symbol pairs, merges the most frequent pair, and stores an ordered merge table. At inference we apply the learned merges to new text; we never compute a fresh corpus vocabulary per user request. Byte-level BPE can represent any UTF-8 string, but rare scripts and emojis may still expand into many tokens, affecting latency and context budgets.

    
D Follow-up pressure test
  1. Why don't BPE merge ranks imply a global optimal segmentation? Strong answer: local greedy merges, fixed rules, and preprocessing constraints.
  2. How do you handle ties and corpus-frequency weights? Strong answer: deterministic rule plus weighted pair counting.
  3. Can a tokenizer always round-trip all Unicode? Strong answer: only under the chosen normalization, byte coverage, decoding, and error policies.
Strong response criteria appear in each prompt. State assumptions and explain how you would verify claims.

    
E Production scenario
Incident: A tokenizer retrain using new domain records unexpectedly changes thousands of production prompts.
Diagnosis: Compare old/new merge tables, vocab IDs, token counts and semantic task outcomes on a fixed evaluation suite, segmented by language and prompt template. Determine whether the model's input/output embedding matrices were resized and adapted.
Mitigation: Treat tokenizer+weights+template as one deployable artifact; train/adapt embeddings for new IDs and assess regressions. Avoid swapping tokenizers into frozen models as a drop-in performance fix.
Acceptance: Versioned fixtures reproduce exact IDs; task quality is non-inferior on agreed slices; token-efficiency improvement is reported with confidence intervals and no hidden regression in rare-language subsets.

    
F Interview takeaways
  • BPE merges frequent adjacent symbols, preserving a fixed training-derived order.
  • Byte coverage avoids OOV replacement, not long token sequences.
  • Tokenizer changes require model compatibility and downstream evaluations.



    
LESSON 03 / 10
WordPiece, SentencePiece & byte-level strategies
Distinguish the segmentation algorithm from the tokenizer framework and from its base alphabet.

    
A Interviewer questions
  1. Is SentencePiece a competitor algorithm to BPE?
  2. How does WordPiece choose subwords at encoding time?
  3. Why do WordPiece vocabularies often include ##-prefixed continuation tokens?
  4. What is the practical difference between an unknown-token system and byte fallback?

    
B Deep technical explanation
Three different axes are often conflated: (1) vocabulary-learning algorithm (BPE, WordPiece, unigram language model), (2) input units (bytes, Unicode characters, normalized text), and (3) tokenizer implementation/framework (e.g., SentencePiece). SentencePiece can train unigram or BPE segmenters directly from raw sentences with whitespace represented explicitly, often as ▁; it is not a single alternative algorithm.


ApproachTraining intuitionTypical encoding ruleImportant edge
BPEMerge frequent neighboring symbolsApply stored merge ranksDepends on base symbols and pre-tokenizer
WordPieceSelect subword vocab by probabilistic/likelihood-inspired criterion; details vary across implementationsGreedy longest-match-first within a word in standard BERT-style implementationsUncovered word may collapse to [UNK]
SentencePiece unigramFit pruned probabilistic vocabularyFind likely segmentation via dynamic programming/Viterbi, possibly samplingNormalization and fallback configuration matter
Byte-level BPEBPE over byte-derived initial symbolsRanked byte-level mergesArbitrary bytes encodable; long sequences still possible


WordPiece example (illustrative vocabulary): Suppose play, ##ing, and ##er exist; playing can be play + ##ing. ## denotes continuation within the word, not literal input characters. If a word has no complete decomposition using valid pieces, BERT-like encoders may produce one [UNK] for the entire word, losing identity of individual characters. Some variants use other fallbacks, so verify the actual model.


SentencePiece example: The token ▁New can explicitly encode a word boundary. Its normalization pipeline can make Unicode behavior different from a GPT-style regex pre-tokenizer. Unigram segmentation selects the most probable sequence of pieces, not necessarily the fewest tokens. Stochastic segmentations can be used for training augmentation when configured.


Unigram decoding: s* = argmax₍s∈Seg(x)₎ Σu∈s log P(u)


Selection: Evaluate compression, reversibility, multilingual coverage, stable templates, special-token safety, implementation latency, and alignment with the model's training data. A popular library's name alone says nothing about its fallback guarantees.

    
C Interview-ready spoken answer
BPE, WordPiece, and unigram language modeling are vocabulary/segmentation approaches, while SentencePiece is a toolkit that supports several algorithms and treats spaces as ordinary input symbols. BERT-style WordPiece commonly uses longest-match continuation pieces and may emit an unknown token for an uncovered word. Byte-level encoders avoid unknown bytes but can be inefficient on uncommon text. I select the actual tokenizer using measured coverage and model compatibility, not labels alone.

    
D Follow-up pressure test
  1. Would a SentencePiece BPE tokenizer necessarily avoid OOV? Strong answer: no; inspect byte fallback, character coverage, normalization.
  2. Why might longest-match WordPiece differ from merging by BPE ranks? Strong answer: distinct inference algorithms.
  3. How would you evaluate tokenization across 20 languages? Strong answer: distributions and task metrics, Unicode fixtures, and fair shared content.
Strong response criteria appear in each prompt. State assumptions and explain how you would verify claims.

    
E Production scenario
Scenario: A document indexing team observes that biological identifiers and names disappear from downstream QA.
Diagnose: Serialize the source text and compare tokenizer output for the exact identifiers. If a WordPiece encoder emits [UNK], information is lost before the Transformer ever sees it; if byte BPE creates many tokens, information remains but may be truncated later.
Remediate: Preserve original exact strings in lexical indexes and structured metadata; add appropriate domain-adapted encoders only after confirming compatible model training.
Validate: Exact-identifier recall, percent unknown tokens, token counts by domain slice, and downstream answer exact-match on held-out data.

    
F Interview takeaways
  • SentencePiece is not synonymous with unigram, nor with byte fallback.
  • Distinguish reversible byte fragmentation from irreversible [UNK].
  • Whitespace and Unicode normalization can be part of the learned contract.



    
LESSON 04 / 10
Vocabulary size, efficiency & unknown handling
Quantify compression and memory consequences without mistaking fewer tokens for better semantics.

    
A Interviewer questions
  1. Why doesn't maximizing vocabulary size always reduce inference cost?
  2. How do you quantify token efficiency fairly across languages?
  3. How do you estimate added embedding memory when growing a vocabulary?
  4. What tests catch silent unknown-token information loss?

    
B Deep technical explanation
Compression versus coverage. More vocabulary entries generally allow frequently occurring strings to be represented as larger pieces, reducing sequence length for the corpus they fit. But each new vocabulary row needs a learned vector, and often a corresponding output projection row. Rare-token embeddings may be poorly trained. Vocabulary growth can increase final vocabulary projection/softmax work, especially without specialized kernels or weight tying.


Input embedding parameters = |V|·d; memory (weights only) = |V|·d·bytesPerElement


Example: ΔV = 32,000, d = 4,096, bf16 → 32,000 × 4,096 × 2 = 262,144,000 bytes ≈ 250 MiB


If the output projection is untied, another comparable matrix may be needed. Training with Adam also allocates gradients and optimizer states. The above is only input embedding weights, not a full training memory estimate.


Metrics: tokens per document and per language; bytes/token on the same raw text set; tokens per semantic unit or reference text; unknown-token rate; p50/p95/p99 length inflation; truncation rate; and downstream task success. Interpret bytes/token cautiously: UTF-8 characters in different scripts naturally use different byte lengths. Comparing raw tokens per character without accounting for script and normalization may be misleading.


Very small vocabulary
Fewer parameters, robust reuse of fragments, but long sequences create more attention/KV-cache traffic.
Very large vocabulary
Potentially shorter sequences on familiar strings, but larger embedding/head costs and poorer statistics for rare token rows.


Unknown-token handling: closed character/subword alphabets may use [UNK]; full byte initial alphabets represent any UTF-8 byte sequence; byte fallback in character-based systems acts only if enabled and implemented. Unknown terms are not the same as unknown tokens: a model can process a novel word's bytes while lacking conceptual knowledge of it.


Latency trade-off: approximate full-attention arithmetic grows like O(n²·d), but flash-style implementations can change memory traffic without eliminating dense attention arithmetic. Decode KV-cache memory grows O(n·L·Hkv·dhead), so tokenizer inefficiency affects serving concurrency.

    
C Interview-ready spoken answer
A larger vocabulary can shorten sequences but increases embedding and often output-head size, while rare entries may be poorly estimated. I evaluate byte coverage and token length distributions on real multilingual and domain-specific traffic, plus downstream task quality. Unknown-byte avoidance does not mean the model understands every word, and fewer tokens alone do not prove a better system.

    
D Follow-up pressure test
  1. Is bytes per token a fair cross-language metric? Strong answer: only with script-aware context and task measures.
  2. What extra GPU memory is required to add 32k tokens with tied versus untied LM heads? Strong answer: show d×V×dtype and optimizer-state assumptions.
  3. Does FlashAttention remove quadratic arithmetic? Strong answer: no; mainly improves IO behavior for dense attention.
Strong response criteria appear in each prompt. State assumptions and explain how you would verify claims.

    
E Production scenario
Incident: Same-length translated reports overflow a 16k-token limit in one language but not another.
Measure: Pair translations, normalization and prompt templates, total IDs, bytes/token, completion budget, and truncation frequency; split by language.
Fix options: Use a better supported multilingual model/tokenizer pair, content-aware chunking, document retrieval, or reserved output budgets. Retrofitting new tokenizer IDs into a frozen model is not a safe quick fix.
Acceptance: Lower truncation and restored answer quality on translated gold questions at explicit p95 latency and cost budgets; publish per-language results rather than averages hiding the tail.

    
F Interview takeaways
  • Vocabulary is a capacity-versus-sequence-length trade-off.
  • Compute embedding-memory math in bytes, and state tying assumptions.
  • Measure actual task performance, not token compression alone.



    
LESSON 05 / 10
Token embeddings: IDs to trainable vectors
Explain the embedding lookup, gradient updates, and why token vectors alone are not sentence meaning.

    
A Interviewer questions
  1. What is the exact operation that maps token ID 17 to a vector?
  2. How are embedding rows learned during language-model training?
  3. Why do identical token IDs have the same initial embedding yet different contextual hidden states?
  4. How can a token embedding matrix serve as an output head?

    
B Deep technical explanation
Embedding lookup is an indexed gather, not an external semantic search. With a vocabulary of V tokens and model width d, the embedding parameter matrix E ∈ ℝ^(V×d) has one row per token ID. For a token sequence t of length n, the input tensor is X[i,:]=E[tᵢ,:]. A one-hot-vector matrix multiplication is mathematically equivalent but wasteful in implementation.


X = one_hot(t)·E  ≡  gather(E, t) ; X shape = [n, d]


Learning. Rows begin random or otherwise initialized and are updated by gradients from the language-model objective. The model is not handed a semantic dictionary of tokens. Tokens that appear in similar and useful predictive contexts often develop related representations, but their geometry depends on the objective, training data, architecture, and anisotropy. The embedding of a subword is not guaranteed to have a standalone stable natural-language meaning.


Contextualization: the row for bank is initially identical regardless of sentence. After attention and feed-forward mixing, hidden states for river bank and bank loan can diverge. Never conflate static input token embeddings with contextual token representations or task-trained sentence embeddings.


Gradients and weight tying: if a token ID appears in a batch, the input embedding gather delivers a gradient to its selected row(s). But when the same matrix is tied to the output projection, language-model logits h·Eᵀ can produce gradients across many output rows. So “only selected embedding rows are updated” is not generally true for tied output weights.


LM logits z = hWoutᵀ + b ; with tied weights Wout = E (dimension-compatible designs)


Production concerns: input dtype, quantization, vocabulary resizing, padding-vector conventions, optimizer states, and device placement. If token IDs change order, even identical-looking model weights can map words to incorrect vectors. Initial token embeddings are not sufficient evidence for semantic similarity; use task-aligned contextual embedding models when doing retrieval.

    
C Interview-ready spoken answer
Token embedding is a learned lookup table indexed by tokenizer IDs. It outputs d-dimensional vectors that are then contextualized by Transformer blocks. The input row for a token is the same wherever it occurs, but attention creates context-dependent hidden states. Embeddings are optimized through the training loss; they may share weights with the vocabulary output head, changing how gradients and memory are distributed.

    
D Follow-up pressure test
  1. What is the tensor shape for batch size B and sequence n? Strong answer: [B,n,d], accounting for padded/packed layouts.
  2. Why isn't the raw embedding for 'apple' a reliable search vector? Strong answer: subword token vs contextual/task representation.
  3. How would a swapped tokenizer silently break lookup? Strong answer: index-to-string semantics no longer align.
Strong response criteria appear in each prompt. State assumptions and explain how you would verify claims.

    
E Production scenario
Incident: An engineer adds 500 medical tokens to a model but sees degraded answer quality.
Trace: Confirm tokenizer additions, embedding/head dimensions, initialization of new rows, whether the head is tied, number of training examples per new token, and optimization of those parameters.
Options: Prefer preserving old tokenization if vocabulary mismatch risk is high; otherwise train new rows with appropriate data and evaluate general-domain regression and specialized terminology separately.
Acceptance: No ID collisions, all new IDs in range, stable decoding, and measured performance on both specialized and general held-out tasks.

    
F Interview takeaways
  • Embedding input = indexed table lookup, not a search model.
  • Static token embeddings differ from contextualized hidden states.
  • Weight tying affects memory and gradient paths.



    
LESSON 06 / 10
Embedding dimensions, geometry & representation
Calculate parameter and activation memory, explain similarities, and separate token-vector geometry from retrieval embeddings.

    
A Interviewer questions
  1. Why doesn't increasing embedding dimension necessarily improve accuracy?
  2. Derive embedding memory and compare it with activations for a long batch.
  3. What do cosine similarity and dot product imply if vector norms differ?
  4. Can the model use low-rank or factored embeddings without losing the external token interface?

    
B Deep technical explanation
Model width. An embedding maps each discrete token ID into d_model coordinates. These coordinates are learned features, not 4,096 individually human-labeled meanings. Model width influences the sizes of Q/K/V and MLP projections, residual streams, and activation memory. Tying dimensions across modules simplifies residual addition but is not mandated by every architecture.


Embedding weights: V·d; input activations: B·n·d·s bytes (s = bytes per stored element)


Illustration: V=64k,d=2048,bf16 → 64,000×2048×2=262,144,000 bytes ≈250 MiB


A batch of 8 sequences × 4,096 tokens × 2,048 width × bf16 adds 8×4096×2048×2 = 134,217,728 bytes = 128 MiB just for one such activation tensor, excluding attention state, gradients, and temporary buffers. A serving system must account for weights, KV cache, and kernels separately.


Geometry: cos(a,b)=a·b/(||a||·||b||) ignores magnitude; dot(a,b) depends on both angle and norm. If all vectors are normalized, cosine and dot-product ranking coincide. Raw token embeddings are often anisotropic and not optimized to encode sentence semantic similarity.


Alternatives: factorized embeddings decompose a large V×d matrix into V×r and r×d, saving parameters if r ≪ d. Product quantization or other low-precision representations may save memory at an accuracy/decode-complexity cost; rank/precision choices must be evaluated.


Debugging: unusual token norms, untrained rows, out-of-range IDs, pad-token leakage, and tokenizer/version mismatch can cause severe failures. Use targeted probes and task evaluations rather than overinterpreting 2D projection plots: PCA/t-SNE visualizations can distort global distances.

    
C Interview-ready spoken answer
Embedding width sets the dimensionality of the model's initial residual representation. A V-by-d embedding table costs Vd parameters; activations scale with batch size, sequence length and width. Larger width expands capacity but increases memory and matrix costs. For similarities, cosine removes vector magnitude while dot product retains it. I validate geometry with task-level tests instead of assuming static token embeddings form a clean semantic search space.

    
D Follow-up pressure test
  1. How many MiB for 64k×2048 bf16 embeddings? Strong answer: 250 MiB using 2²⁰ bytes per MiB.
  2. Why do cosine and dot rankings differ before normalization? Strong answer: varying norms.
  3. If you factor embeddings, when does it save weights? Strong answer: Vr+rd versus Vd, with r(d+V)<Vd.
Strong response criteria appear in each prompt. State assumptions and explain how you would verify claims.

    
E Production scenario
Incident: A deployment runs out of memory after doubling model width; the team blames only embeddings.
Profile: Separate input/head parameter allocations, attention/MLP projection weights, activations, KV cache, batch-size distributions, allocator fragmentation, and precision.
Remedy: Quantify the actual largest component, reduce concurrency or KV usage if dominant, consider supported quantization/factoring, and profile latency/quality impacts rather than assuming table size explains OOM.
Acceptance: Reproducible peak-memory model matches profiler within a documented tolerance under representative batches, with sustained quality and p95 latency targets.

    
F Interview takeaways
  • Count matrix parameters separately from batch activations and KV cache.
  • Dimension boosts cost and capacity, not guaranteed semantic quality.
  • Static token-vector similarity is not a substitute for trained retrieval embeddings.



    
LESSON 07 / 10
Why Transformers need position information
Prove the permutation issue and distinguish absolute and relative location schemes.

    
A Interviewer questions
  1. Without a position signal, which aspect of token ordering can self-attention recover?
  2. What does permutation equivariance mean for position-free self-attention?
  3. Is a causal mask by itself a full position representation?
  4. Where in the pipeline can positional information enter?

    
B Deep technical explanation
Mechanism. Plain self-attention performs the same projection and matching operation for each input position. With no positional signal or position-dependent mask, permuting the input token rows permutes the output rows in the same way; self-attention has no built-in preference for order.


SelfAttention(PX) = P·SelfAttention(X)  (without position-dependent mask; P is a permutation matrix)


The softmax attention formula uses content-based Q and K products; absent position, dog bites man and man bites dog contain the same token multiset, yet require different interpretation. Positional methods inject index/relative-distance information so that the model can distinguish such arrangements.


Important nuance: a strictly causal mask does break arbitrary permutation equivariance by exposing differing prefix sets. So the statement “decoder self-attention has no order signal whatsoever without embeddings” is too strong. Nevertheless, causal visibility alone is a limited/implicit position cue; explicit or structured positional mechanisms improve the representation of relative and absolute order.


Where position enters: (a) add a position vector to input token embeddings; (b) modify Q/K projections with RoPE; (c) add relative position bias to attention logits; (d) use other learned or fixed relative mechanisms. These are architectural alternatives, not ingredients that must all coexist.


Additive: xᵢ = E[tᵢ] + pᵢ ;   Relative logit bias: score(i,j)=qᵢ·kⱼ/√dₖ + b(i−j)


Cost: additive position vectors add one vector per token; attention-relative methods may require computing biases or rotations but often integrate efficiently into fused kernels. Position mechanism, context length, and training distribution jointly determine long-range performance. “Theoretically supports n positions” does not mean calibrated accuracy at that n.

    
C Interview-ready spoken answer
Without positional information, unrestricted self-attention is permutation equivariant: reordering inputs simply reorders outputs. A decoder causal mask supplies a limited structural order cue, but explicit positional methods are still useful for distinguishing sequence locations and distances. We can add position vectors, bias attention scores by relative distance, or rotate queries and keys with RoPE. The choice affects extrapolation and computation.

  2. Do all Transformers add positional embeddings to the input? Strong answer: no, RoPE and relative-bias schemes modify attention.
  3. How do you test position sensitivity? Strong answer: order-swapped controlled inputs at matched lengths.

  • Position-free unmasked self-attention is permutation equivariant.
  • Causal masking complicates that claim; qualify it precisely.
  • Position can enter inputs, Q/K rotations, or attention logits.



    
LESSON 08 / 10
Learned vs. sinusoidal positional embeddings
Write the sinusoid equations and reason about limits of trainable position tables.

    
A Interviewer questions
  1. Derive the sinusoidal positional vector and its dimension pairing.
  2. What changes when you input position 20,000 into a 4,096-row learned absolute position table?
  3. Does sinusoidal encoding guarantee extrapolation to unseen context lengths?
  4. Why can pairs of sinusoidal frequencies help represent relative displacement?

    
B Deep technical explanation
Learned absolute positional embeddings use a trainable table P∈ℝ^(Lmax×d), with xᵢ=E[tᵢ]+P[i]. This has simple implementation and lets the training objective adapt positions, but a standard table has a fixed maximum row index; using unseen indices needs interpolation, extension, or an architecture change. Table cost is Lmax×d parameters.


Sinusoidal encoding from the original Transformer uses fixed sin/cos features at geometrically spaced wavelengths (for even d):


PE(pos,2i) = sin(pos / 100002i/d)
PE(pos,2i+1) = cos(pos / 100002i/d), for i=0,…,d/2−1


Each two-dimensional pair rotates with angular frequency ωᵢ=10000^(−2i/d). Basic trigonometry gives sin(a+b) and cos(a+b) as linear combinations of sin/cos at a. This makes relative offsets accessible to a suitable downstream function; it does not automatically solve all extrapolation or ambiguity problems, especially beyond trained ranges.


Example d=4, position 2: frequencies are ω₀=1 and ω₁=1/100, producing [sin 2, cos 2, sin 0.02, cos 0.02]. Adjacent coordinates are paired; switching their order is a convention issue only if consistently implemented throughout training and inference.


ChoiceParametersAdvantageConcern
Learned absolute tableLmax×dFits seen positionsFinite row limit / length shift
Fixed sinusoidal0 for position tableComputable for arbitrary indicesLong-context generalization not guaranteed
RoPE / relative biasVariant dependentRelative structure in attentionKernel support and scaling strategy


Debugging: verify off-by-one positions, padding offsets, caching position IDs, left-padding, and packed sequences. A model might produce numerically valid logits with wrong relative positions and silently lose accuracy.

    
C Interview-ready spoken answer
Learned positional embeddings add a trainable vector from a finite position table. Sinusoidal encodings add deterministic sin/cos features at different frequencies, so position vectors can be computed outside the training length. Their algebra supports relative offsets, but a mathematical encoding defined for longer positions is not proof the trained model generalizes there. I'd validate position IDs, padding, and length-shift quality before claiming extended context support.

    
D Follow-up pressure test
  1. Compute d=4 PE at pos=2. Strong answer: [sin 2, cos 2, sin .02, cos .02].
  2. Would interpolation of learned tables alone make a 4k model reliable at 32k? Strong answer: no; controlled eval and often adaptation needed.
  3. What is memory overhead of a 32k×4096 fp16 learned table? Strong answer: 256 MiB weights; check units.
Strong response criteria appear in each prompt. State assumptions and explain how you would verify claims.

    
E Production scenario
Incident: Quality falls after a serving change from right-padding to left-padding.
Hypothesize: Position IDs now include pad offsets differently; cache lengths do not align with the continuation; or attention masks changed.
Inspect: For equivalent actual token sequences, compare attention masks, effective position IDs, initial hidden-state checksum, and logits against a reference path.
Fix: Construct positions from non-pad token count according to model conventions and align prefill/decode. Acceptance: Matched logits within precision tolerance on fixtures, plus stable downstream quality across padded batch shapes.

    
F Interview takeaways
  • Learned position tables have finite indices; sinusoids can be evaluated anywhere.
  • Long-context mathematical definedness ≠ extrapolation reliability.
  • Position-ID bugs frequently masquerade as decoding or model-quality regressions.



    
LESSON 09 / 10
Rotary Position Embeddings (RoPE)
Work through Q/K rotation pairs, prove the relative-distance dot-product property, and discuss long-context caveats.

    
A Interviewer questions
  1. Why rotate queries and keys rather than adding a position vector to token embeddings?
  2. Show mathematically why RoPE attention depends on relative displacement.
  3. What does the RoPE base parameter change?
  4. What fails when you naively extend a RoPE-based model far beyond its trained range?

    
B Deep technical explanation
Operations. In RoPE-based attention, project residual states into Q and K, partition a configured rotary subdimension into 2D pairs, and rotate each pair by a position-dependent angle. Values V are normally not rotated by standard RoPE. For pair index m, frequency ωₘ=base^(−2m/d_rot); at sequence position p, the angle is p·ωₘ.


R(θ) = [[cos θ, −sin θ],[sin θ, cos θ]];
q'ₚ = R(pωₘ)qₚ ; k'ₛ = R(sωₘ)kₛ


(q'ₚ)ᵀk'ₛ = qₚᵀR((s−p)ωₘ)kₛ


Derivation: R(a)ᵀR(b)=R(b−a), because rotations are orthogonal. Thus the positional contribution to Q/K compatibility depends on the relative index difference, rather than requiring an absolute-position lookup row. Rotating both positions by a common offset leaves each pair's dot product unchanged if Q/K content vectors are held fixed. In an actual causal Transformer, shifting tokens and masks may change contextual content, so this algebra is not a full-system output invariance claim.


Implementation: reshape Q/K to heads, rotate configured components (interleaved vs. split-half layouts vary), ensure the cached keys retain their original absolute position rotations, and use the current continuation position when appending a query. Position-ID mistakes cause long-response quality degradation despite otherwise correct KV caching.


Advantages: no learned absolute table is necessary, and the mechanism gives a useful relative phase structure. Trade-offs: high-frequency phase aliasing, training-length distribution shift, choice of RoPE base, numeric precision, kernel layout, and attention-head rotary fractions influence long-context behavior. Position interpolation and RoPE scaling are adaptation strategies, not universal fixes.


Illustrative pair rotation
def rotate_pair(x0, x1, pos, omega):
    theta = pos * omega
    return (x0*cos(theta) - x1*sin(theta),
            x0*sin(theta) + x1*cos(theta))

q_rot = rotate_pair(*q, query_position, omega)
k_rot = rotate_pair(*k, key_position, omega)
score = dot(q_rot, k_rot) / sqrt(d_head)

    
C Interview-ready spoken answer
RoPE rotates pairs of query and key coordinates by angles proportional to token position, with multiple frequencies across a head. Since the transpose of one rotation times another equals a rotation by their difference, the resulting Q–K dot product encodes relative position. It avoids a finite learned absolute position table, but trained context limits and cache-position correctness still matter. Extending length requires evaluation and possibly a scaling strategy.

    
D Follow-up pressure test
  1. If you add 100 to both position IDs, must the entire model output stay identical? Strong answer: only the isolated RoPE pair score for fixed content is invariant; not the entire causal computation.
  2. What happens if cached K is rotated at position 4, then re-rotated as position 5? Strong answer: phase mismatch and corrupted attention.
  3. Why is RoPE not the same as learned positional embeddings? Strong answer: alters Q/K angular geometry after projection, not additive input vectors.
Strong response criteria appear in each prompt. State assumptions and explain how you would verify claims.

    
E Production scenario
Incident: Short completions are accurate, but after thousands of generated tokens an assistant begins repeating or misusing distant facts.
Profile: Compare full-sequence reference decoding against incremental KV-cache decoding, log safe position-index traces and head configuration, verify RoPE base/scaling parameters in serving artifacts, and test boundary lengths.
Possible root causes: offset/rotation mismatch in cached keys, wrong rotary-dimension layout, phase errors after sliding-window truncation, or distribution shift beyond training length.
Fix: Correct position bookkeeping, use a verified kernel/reference implementation, and evaluate any length-extension strategy on controlled retrieval/reasoning tasks. Acceptance: Cache versus full-pass logits agree within precision tolerance for in-range fixtures; long-context task metrics meet explicitly agreed thresholds.

    
F Interview takeaways
  • RoPE rotates Q/K 2D pairs; standard V does not receive the rotation.
  • Relative-position property is an exact dot-product identity for fixed content.
  • Cache position alignment and long-context generalization are separate concerns.



    
LESSON 10 / 10
Diagnosing multilingual, code & domain tokenization failures
Use exact-token instrumentation to distinguish fragmentation, truncation, and information destruction.

    
A Interviewer questions
  1. Why can the same number of visible characters produce radically different token counts?
  2. How do you separate out-of-vocabulary replacement from fragmentation?
  3. Why do code and structured identifiers stress general-purpose tokenizers?
  4. When would you retrain a tokenizer, fine-tune the model, or avoid modifying the weights?

    
B Deep technical explanation
Failure taxonomy. (1) Fragmentation: uncommon text turns into many byte/subword tokens; content is still encodable but expensive. (2) Lossy fallback: [UNK] erases distinctions. (3) Normalization collisions: different Unicode strings map to the same normalized representation, sometimes by design. (4) Boundary mistakes: tokenizer or pre-tokenizer splits identifiers, indentation, whitespace, escape sequences, or numbers in ways that harm structured extraction. (5) Truncation: the prompt is shortened after token-budget enforcement, silently dropping critical context. (6) Training coverage: even perfect encoding does not imply conceptual knowledge.


Examples: Bangla, Devanagari, CJK text, emojis with skin-tone modifiers and zero-width joiners, chemical formulae, invoice IDs, source code symbols and mixed-case identifiers can have high token expansion under a tokenizer trained predominantly on other distributions. Their actual counts depend on the chosen tokenizer; never attribute one toy count to production models.


  1. Capture a privacy-safe reproduction: escaped original string, UTF-8 byte count, code-point count, visually rendered example, normalization form and tokenizer artifact hash.
  2. Inspect output: token IDs and their decoded bytes/pieces, [UNK] count, continuation markers and post-template prompt length.
  3. Slice the data: p50/p95 tokens per document by language, domain and document type, and truncation rate at the real context budget.
  4. Trace the effect: compare downstream exact-match, citation fidelity, code compilation or name-entity recall against a stable gold set.
  5. Apply the minimal remedy: preserve exact terms in lexical search, adjust pre-tokenization only in a compatible model pipeline, use chunking/retrieval, choose a multilingual/code-specialized model, or retrain/adapt tokenizer and model jointly when ROI justifies it.


Evaluation design: report paired examples, bootstrap confidence intervals for quality and length outcomes where appropriate, monitor p95 latency, model memory and token charges, and set hard correctness thresholds for IDs and code. More aggressive merges may shorten text yet worsen representation learning if data for a newly minted token is scarce.

C Interview-ready spoken answer
I'd debug multilingual or domain-specific failures by inspecting the exact string-to-token mapping before changing the model. I'd distinguish reversible fragmentation from unknown-token replacement, normalization collisions, and budget truncation. Then I'd measure token inflation and downstream task accuracy by language or domain. The safest fix is often retrieval, preserved exact text, or a compatible specialist model rather than swapping the tokenizer under frozen embeddings.

    
D Follow-up pressure test
  1. If a tokenizer has no [UNK], why can entity extraction still fail? Strong answer: fragmentation, truncation, inadequate learning, or model behavior.
  2. How would you prove an improved tokenizer is actually better? Strong answer: fair paired quality and costs, and retrained compatible weights.
  3. Why is code indentation special? Strong answer: whitespace/control tokens can be semantically meaningful, so cleanup must not be assumed safe.
Strong response criteria appear in each prompt. State assumptions and explain how you would verify claims.

    
E Production scenario
Scenario: A code assistant is deployed for a mixed Bangla/English developer team. p95 prompt tokens rise and exact function names occasionally change in generated edits.
Instrument: Token histograms by language and file type, identifier span offsets, parse/compile success, round-trip tokenizer fixtures, truncation position, and error concentration in comments vs. executable code.
Remediation order: (1) ensure stable tokenizer/model pair and correct chat template; (2) preserve code verbatim and remove only genuinely redundant prompt material; (3) reserve input/output budgets; (4) evaluate code-focused and multilingual-compatible models; (5) consider tokenizer retraining only with aligned model adaptation.
Acceptance: Task success measured by tests, exact-identifier preservation, lower validated length tails, and no worsening on paired language slices. Report numerical results only after experiment.

    
F Interview takeaways
  • Inspect exact IDs, byte reversibility, normalization, and context truncation.
  • More tokens ≠ necessarily worse semantics, but usually higher system cost.
  • Never treat a new tokenizer as drop-in compatible with old model weights.
